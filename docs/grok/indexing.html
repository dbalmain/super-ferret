Indexing options

Algorithms and data structures you could implement, including ones no desktop search app ships. Density preferred over raw QPS. Personal scale: under five million files, hundreds of GB. Boolean, phrase, and regex are all first-class. You will write the codecs; this page is the menu.

Measured bits/int are from Pibiri & Venturini CSUR 2020 (Gov2 / ClueWeb / CCNews) unless noted. Personal-scale file search with path-clustered IDs compresses better than ClueWeb and closer to Gov2.

How to use this

The landscape report is what others built. This one is what Super Ferret can build. Several options are not in Recoll, Lucene, or old Ferret — VictoriaLogs-style blooms, Cox trigrams, partitioned Elias-Fano, RAM name tables. The load-bearing choice is whether body text is inverted at all. That is opened as a real question, with numbers.

The density question

You asked for a denser index even if queries are slightly slower, and named VictoriaLogs. VL is not a Lucene with better compression. It does not build term postings of the message. “Automatically indexes all fields” means: tokenize each block, put unique tokens in a bloom (~2 bytes/token), ZSTD the column, skip blocks the bloom rejects, scan the rest. The only inverted index is of low-cardinality streams (host, app, container).

Desktop files are not nginx logs. Grouping by (extension, directory prefix) recovers some of that repetition. Common queries (TODO, error, fn) will not skip. Needles will. Phrase becomes a scan of surviving blocks. Regex still needs n-grams — VL blooms are tokens, not trigrams, and cannot skip foo.*bar.

Invert the body, bloom-and-scan it, or both?

A. Classic inverted postings (PEF or SIMD-BP128 blocks of 128, optional interpolative positions). Recoll / Lucene / Ferret lineage.

Space, extracted English: roughly 3–9 bits per posting (docIDs only) plus 2–4× if you store positions (IR-book folklore, confirmed by every positions-on/off toggle). FTS5’s own knob on 1636 MiB of email: 134 / 340 / 743 MiB for presence / column / full positions. Phrase is exact. rare_symbol is O(df). the is a fat list.

Buys the mental model you already shipped in Ferret. Costs the thing VL exists to avoid. Forecloses “index ≈ compressed extracted text.”

B. Bloom + scan, no body postings. Type-grouped 2 MiB blocks of extracted UTF-8, per-block token bloom, ZSTD. Stream-analogue = (ext, dir-prefix), not per-file.

Space: compressed text (often 3–10× on prose, worse on already-compressed code) + ~2 bytes per unique token per block. Valialkin’s back-of-envelope vs Elasticsearch: 2 B/unique-token vs ≥8 B/occurrence. A worked VL part: 5.6 GiB uncompressed-equivalent → 513 MiB (~11×). Vendor disk-vs-ES “up to 15×” is marketing; TrueFoundry’s 500 GB/7d logs: Loki 501 GB vs VL 318 GB (−37%).

Buys VL density. Costs: common tokens scan the type-column; phrase is adjacency-on-scan; you still need Cox for regex. Forecloses Recoll-class "to be or not to be" without reading those blocks.

C. Hybrid (recommended)

  • RAM filenames + name trigrams (Everything / plocate).
  • Columnar metadata, dict/int encoded (VL columns).
  • Body stored compressed, type-grouped, with per-block token blooms (VL datadb).
  • Sparse inverted index for rare terms and for code identifiers — not for English function words.
  • Cox trigram index, budget ≤0.3× corpus, for regex and substring.
  • Positions only where phrase is a product requirement (filenames, maybe code tokens); not on body English.

Buys density where VL is right and O(df) where VL is wrong. Costs two query paths. Forecloses a single-codec textbook engine — which is fine, you are not shipping a library.

Recommendation: C. Change it if phrase-over-body must match Recoll on stopword-heavy quotes (take A) or if you refuse to invert body terms at all (take B). On NVMe, scanning a few hundred MB of compressed *.rs for TODO is acceptable; scanning 40 GB of mixed extracted PDF text for invoice is not, which is why grouping by type is mandatory in B and C.

What VictoriaLogs actually does

Primary: FAQ, columnar internals, lib/logstorage/{indexdb,bloomfilter,tokenizer,datadb}.go.

A log line is a flat map[string]string plus a timestamp. Low-cardinality labels are stream fields; everything else is a regular column. One UTC day = one partition. Parts are an LSM: in-memory → small disk → big disk, merge up to 15 similarly sized parts, ≥1.7× size multiplier or skip (write-amp control).

part/ metadata.json min/max ts, rows, bloom shard count metaindex.bin in RAM: stream range, time range → index.bin index.bin block headers (stream, rows, pointers) timestamps.bin delta/varint then ZSTD values.binN columnar values, typed bloom.binN per (block, column) token bloom message_values.bin _msg message_bloom.bin columns_header*.bin type, min/max, offsets

Value types, tried in order: dict if ≤8 distinct and ≤256 B total; packed uint/int/float; IPv4 as 4 bytes; ISO8601 as int64 ns; else string. Const columns live in the header. Blooms: 6 hashes, 16 bits/unique token, xxhash64, tokens = [A-Za-z0-9_]+ (a whole CJK sentence becomes one token — wrong for desktop). Query: time → partition, stream filter → indexdb (true inverted index of streams), metaindex skip, bloom, decompress surviving columns, per-row bitmap.

What maps: grouping similar objects, columnar metadata, bloom-as-negative-index, LSM parts, type-specialized encoding, projection so the UI does not touch content columns. What does not: daily time partitions of file content; per-file streams (path cardinality is millions); CJK tokenizer; assuming needle queries dominate.

Layers of a desktop index

Three different jobs get mashed together in every disappointing Linux search app:

  1. Names. Millions of short strings, prefix and substring, updated live. RAM is the right medium at 5M files (~400–750 MB with paths). Everything already measured this.
  2. Metadata. mtime, size, extension, mime. Columnar + a small inverted or BKD for ranges. Not postings of English.
  3. Bodies. Huge vocabulary, selective terms, phrase, regex. This is where A/B/C above lives.

Web-search literature (billions of docs, RAM-resident postings, thousands of QPS) is the right source of algorithms. Several of its axioms invert here: space beats decode speed once the list is in page cache; boolean/phrase dominate ranking; regex is not a plugin; ingest is extractor-bound, not encoder-bound; updates are file-granular save-storms. DocIDs fit in 24 bits (5M < 2²³). That fact leaks into every codec.

Filenames

RAM table, Everything-style

Record: name blob + parent id + optional 8-byte size/mtime. Sorted names share prefixes. Official Everything: 250k files → 35 MB RAM / 14 MB disk; 1M → ~100 MB / 45 MB. Community: 8M with size+mtime → ~700 MB. Build from a sequential metadata read, not find. Persist a snapshot; journal/fanotify for live updates; overflow → subtree walk. Linux has no USN; overflow handling is the whole game.

FSearch already did this with DynamicArray + parent_idx. At your scale, do not mmap a PEF of names and congratulate yourself. As-you-type wants RAM.

Name trigrams (plocate / Cox on paths)

Substring *Invoice* and regex on names: overlapping 3-grams → TurboPFor/PEF docids → verify. Short needles scan. This is small (names are tiny) and should exist even if body search is bloom-only.

Tries

ART (Leis et al., ICDE 2013), HAT-trie, crit-bit: good in-RAM prefix maps. A front-coded sorted path column is enough for ~/src/foo/** if paths are sorted. Substring still needs trigrams. A suffix array on 5M × 40-byte names is ~800 MB to answer a query a 20 MB trigram index answers.

Intersection is galloping nextGEQ on the longer list, driven by the shorter. An encoding that cannot nextGEQ without decoding the whole list is a non-starter for boolean search, no matter how small. That single fact knocks out “just gzip the docid array.”

Assign docIDs path-sorted (or graph-bisection later, PISA-style). Clustered IDs make every delta codec denser. RecGraph / recursive graph bisection is 20–40% smaller postings after a rebuild — highest-leverage density trick once the first index works.

VByte: 7 data bits + continuation. Floor of 8 bits/int. Lucene still uses it for short lists and skip metadata. StreamVByte separates control bytes so SIMD can shuffle payloads (Lemire, Kurz, Rupp 2018).

Simple family: selector + packed payload in a 32/64-bit word. One large gap poisons the word. Fine if you want no SIMD and density close to PFor.

FOR / PFor: block of 128, bit-width from the max. PFor patches exceptions. Lucene 4.1 shipped packed-int blocks (FOR, not interpolative); later codecs added PFor-like flavors. Tantivy: d-gap + SIMD bitpack of 128, remainder varint, skip of last-docid-per-block. Interpolative was never Lucene’s default; Xapian is the interpolative shop, and only on positions.

BIC: recursively encode the midpoint given known bounds (Moffat & Stuiver 2000). Clustered runs cost almost nothing. Sequential decode is a recursive bit-reader. At personal scale the space win over PEF is ~0.2 bits/int on Gov2 — maybe 10–20 MB on a 5M-doc index. Probably not worth the tax on docIDs. Still defensible for position lists, which is why Glass does that.

Elias-Fano / PEF: split high/low bits; high bits as a unary-gap bitvector with select. Quasi-succinct, no clustering assumption. PEF (Ottaviano & Venturini SIGIR 2014) partitions into chunks, encodes each over its local universe, dense chunks become bitmaps, endpoints another EF. Linear-time (1+ε)-optimal partition. This is PISA’s opt index. If Super Ferret inverts medium/long lists, PEF is the dense adult option; SIMD-BP128+skips is the simple adult option.

Old Ferret is VInt d-gaps + skip every N. That is the 2005 answer. Replace it. Keep the skip interval as a first-class parameter.

Bitmaps

A posting list is also a bitvector of length N with n ones. At 5M docs that is 625 KB uncompressed per term — insane for rare terms, excellent above ~10% df.

Roaring (Chambi, Lemire et al.): 2¹⁶-sized chunks; array if ≤4096 values (16 bits each), bitmap if denser (8 KB), run containers for consecutive ranges. 4096 × 2 B = 8 KB is the exact threshold. 64-bit roaring is for offsets/hashes, not 5M docIDs. Lucene uses roaring for liveDocs and filter caches, not for scored postings. Meilisearch uses roaring for everything and pays for it in size. Wang et al. SIGMOD 2017: use roaring for bitmaps; do not use WAH/EWAH/Concise in a new system.

When: deletion bitmaps; dense filters (extension, mime, year); in-memory AND of several filters. Not the only posting format.

Lucene BlockTree: FST of prefixes → on-disk block of 25–48 front-coded terms. Better than a giant FST of all terms. Lucene 10.3 moved the in-block structure toward a trie. Pulse/inline lists with df < 8 into the dictionary (saves a seek). That is Lucene 2 “pulsing,” and old Ferret could grow it.

Positions, phrases, snippets

Positions: per (term, doc), monotone token indexes, encoded like a posting list. IR-book: a positional index is 2–4× a docID-only index. First thing to drop if the index does not fit. Needed for phrase and proximity. Common-term phrases (to be) are the expensive ones — doc-intersection is huge and you actually walk positions.

Next-word indexes (Bahle, Williams, Zobel SIGIR 2002): +10–26% space for faster two-word phrases. A 1999–2004 answer; SSD + block skips mostly defanged it. Spend that space on trigrams instead.

Three snippet strategies:

  1. Store compressed extracted text (zstd). Recoll 1.24+ did this because Glass positions were too slow for snippets. +10–20%.
  2. Re-read the file. Free for UTF-8 source; wrong for PDF (extracted text is not the file).
  3. Re-extract at query time. Slow; extractor bugs become snippet bugs.

Recommendation: store zstd’d extracted text for PDF/Office/email; re-read code and plain text. Token positions for fields where phrase is required; skip char offsets in v1. Recoll’s pre-1.25 “walk positions” path is the cautionary tale.

Regex and substring

Russ Cox, 2012, Regular Expression Matching with a Trigram Index. Mandatory. Implementation: github.com/google/codesearch.

Why 3: too few 2-grams (postings huge), too many 4-grams (key explosion). Index overlapping 3-grams → sorted file ids. Reject invalid UTF-8, very long lines, too many distinct trigrams. ~20% of corpus.

From each regexp compute emptyable / exact / prefix / suffix / match. Concatenation and alternation have exact rules; information-saving moves about-to-be-discarded prefix/suffix/exact grams into the match query; information-discarding keeps sets bounded. Always recheck with a linear-time engine (RE2 / Rust regex). /Google.*Search/ becomes AND of Goo oog ogl gle Sea ear arc rch. ab[cd]e becomes (abc AND bce) OR (abd AND bde). No 3-char literal → ANY → scan.

Zoekt stores offsets per trigram (~3.5× corpus) and picks the two rarest grams. Wrong density trade for you; steal “pick rare grams, not all of them.” livegrep’s suffix array is 3–5× RAM and static. GitHub Blackbird’s sparse grams are for 15 billion documents. qgrep’s 4-gram Bloom per compressed chunk makes the ANY fallback a fast scan, not a 200 GB read. Use that.

CJK trap: a UTF-8 CJK character is 3 bytes, so a byte trigram is a unigram. For CJK content, use character bigrams (Japanese IR tradition) plus UTF-8-aware character trigrams for regex. Recoll’s default CJK n-grams exist because morphological segmenters are an extra dependency. Do not copy VL’s “whole CJK sentence = one token.”

Columnar fields, BKD, stored docs

Two access patterns: given docID, get field (sort, UI columns) → columnar / Lucene DocValues / Tantivy fast fields. Given a range, get docIDs (mtime between, size > 1 MB) → BKD or a roaring per bucket.

Numerics pack to ceil(log max) bits. Low-cardinality strings (ext, mime): dictionary + ordinals. Unique paths: you are almost storing the original column — front-code and/or FSST (Boncz, Neumann, Leis: 1-byte codes, random access per string, ~2× on short strings). zstd is the wrong codec for millions of short paths because of its block nature.

BKD (Lucene 2015): k-d tree of packed points, 512/leaf, one copy of each point. 1D mtime/size ranges prune by min/max. Combined with index-sort-by-mtime, last-7-days is one region of docIDs. Do not use BKD for extension — a roaring per value ANDs faster. Keep both: BKD for the range query, doc values for retrieve/sort.

Lucene stored fields: chunk-compressed documents. Elastic has been moving those chunks toward zstd. This is the original-document store if you have one. Do not put mtime here; you will regret every sort.

DocIDs should be segment-local 0..maxDoc-1. Never let a user-facing id be the posting docID. Path and content hash live in columns. Deletes are a roaring liveDocs per segment; reclaim at merge. A WAL of (path, reason) is enough to not miss events across crash — content is still on the filesystem. Do not WAL extracted text. FTS5 automerge=8, crisismerge=16, segments of 50k–200k docs is enough at this scale. Hundreds of GB of files is not hundreds of GB of postings if content is external and positions are opt-in.

VL’s mergeset is the same LSM idea with empirically tuned 1.7× merge multiplier. Steal that write-amp control.

Ingest, watchers, extractors

Linux: fanotify on the mount if you can; inotify per directory otherwise (max_user_watches). Debounce 200–500 ms by path; editors write file.tmp + rename. A save-storm becomes one reindex of the final inode. IN_Q_OVERFLOW means you missed events: subtree walk, do not pretend. NFS: inotify is unreliable; periodic walk.

Three threads, not one:

  1. Watcher: enqueue paths only.
  2. Extractor pool: bounded, niced, one file at a time, hard timeouts, memory caps, cache by content hash. PDF bombs are a real file.
  3. Indexer: tokenize, write. Never block on extraction.

Every native parser (especially PDF, OLE, image codecs) runs in a helper: seccomp default-deny, Landlock read of the target file + lib dirs, no network, RLIMIT_AS + RLIMIT_CPU, parent watchdog. Spawn pdftotext / antiword inside that jail; do not link poppler. LocalSearch is the model; Recoll’s rlimits-only helpers are not. 2 s soft / 15 s hard per file; OCR/STT/LibreOffice on a colder pool. ionice class 3, nice, maybe a cgroup. Pinot pauses on battery; Recoll has an AC-only script. Do both.

A Python/PDF extract of a 50-page PDF is 100–1000× the cost of encoding its postings. The write path should be simple and crash-safe, not the fastest encoder on the planet.

Plugin hooks

Core model: a document is a bag of named fields; each field has an analyzer and an index option (docs / docs+freqs / docs+pos / trigrams / columnar / BKD / bloom+scan / none). Plugins add fields and extractors, not storage engines.

  • Email: one document per message. Fields from/to/subject/body/msgid/date. Attachments as children with parent=msgid. Dedup by msgid. Never index a 20 GB mbox as one doc.
  • OCR: extra field body_ocr, not an overwrite of body, so a query can exclude noisy text. Cache by image hash forever. Default off. Explodes index size and wrecks trigram selectivity.
  • Reverse image: do not put vectors in the inverted index. HNSW sidecar keyed by docID (Malkov & Yashunin). Fine for 10⁵–10⁶ images. DiskANN when it no longer fits in RAM. Not in the NRT loop; rebuild offline. Query: ANN → candidate ids → liveDocs ∩ boolean.
  • Speech-to-text: extra field body_asr, same economics as OCR.

Do not build in v1: impact-ordered primary index, WAH, corpus suffix array, Glass-style mutable PEF, stemming by default, stopwords by default, char offsets, next-word index, 64-bit roaring for docIDs, linking Tantivy/Xapian/poppler.

Build later if a profile says so: PEF as default instead of FOR (when disk < RAM), interpolative on remaining position lists, WAND (when 5-term prose is slow), FSST on paths, CJK tokenizer, sparse n-grams.

Ranking, short: boolean + recency + path-depth is a complete function for “find that file.” Filename hit ≫ body hit. Exact basename ≫ path substring. BM25 on a body field is fine when the query is several uncommon tokens (k1≈1.2, b≈0.75). DFR is why people think Xapian is smart; it is not why you would pick it. No LTR, no PageRank.
