Decision record

Answers that scoped this survey, plus the one architectural question the research actually opened.

This page is the durable record of choices that would otherwise live only in chat. Answered items stay here with the tradeoff that produced them.

Answered · option 1

1. What should this survey primarily inform?

1. Build Super Ferret. Existing apps are competitive intel. Reports go deep on engines, index structures, and options nobody ships.

2. Pick an existing Linux app. A buyer’s guide.

3. Both equally.

Answer: 1. Nothing on Linux does exactly what you want; you expect to build. Recoll is the feature ceiling, not a candidate to install and stop.

Answered · option 1

2. Rough corpus size?

1. Personal workstation. Tens to a few hundred GB, under ~5 million files.

2. Power user / multi-disk. 1–10 TB.

3. Archive / NAS. 10+ TB.

Answer: 1. NAS-scale search, if it happens, gets its own design around those files. Super Ferret stays general and does not have to survive 100 million files.

Answered · 1, 2, 5 first; 3 and 4 as plugins

3. Which content classes are first-class?

  1. Office / PDF / plain text — always on.
  2. Source code — regex as a real query type over ~/src.
  3. Email (maildir / mbox / PST) — plugin later.
  4. Scanned PDFs / OCR — plugin later.
  5. Media metadata (EXIF, ID3, duration) — first wave, cheap.

Answer: Ship 1, 2, 5. Leave hooks so 3, 4, reverse-image, and speech-to-text can arrive as plugins without rewriting the index. Reverse-image and STT are vector/ASR sidecars, not extra posting lists.

Answered · option 1, with a queue

4. How fresh does the index need to be?

1. Near-real-time. inotify / fanotify; updates in seconds.

2. Periodic.

3. Hybrid watch + batch archives.

Answer: 1, with coalescing. Burst creates queue; the indexer is a niced, low-priority process and should not spoil interactivity. Save-storms become one reindex of the final inode.

Answered · option 1

5. Linux survey scope — apps, engines, or both?

Answer: Both. Recoll / Baloo / FSearch as products; Xapian / Lucene / Tantivy / FTS5 / PISA / VictoriaLogs as architecture intel. Ferret (dbalmain/ferret) is prior art you wrote: a Lucene-shaped inverted index, MIT, C + Ruby. Super Ferret is not a port of that format. You would enjoy rewriting it in Rust for stability, but it is the wrong density trade for this job. VictoriaLogs is the density reference that did impress you.

Answered · option 1

6. License constraint if Super Ferret is built?

Answer: Permissive. You will not link a search library. The point of the survey is to learn the algorithms well enough to implement them. GPL tools (poppler pdftotext, antiword) are fine as subprocesses. Xapian, Recoll, FSearch, plocate, rga are competitors, not dependencies.

Still open — opened by the research

Should body-text search be inverted postings, VictoriaLogs-style bloom + scan, or a hybrid?

This is the only question the overnight pass actually changed. Filename search wants Everything-class RAM structures. Regex wants Russ Cox trigrams. Body text is where density and query shape fight.

A. Classic inverted index (PEF or block-FOR postings, optional positions). Recoll / Lucene / old Ferret. Phrase is exact. Common terms are still O(df). Index of extracted text is typically 0.3–1× that text, plus more if you store snippets.

Buys: phrase, BM25, the mental model you already have. Costs: the thing VictoriaLogs exists to avoid — a posting for every occurrence. Forecloses: “the index is barely larger than compressed extracted text.”

B. Bloom + scan of compressed columns (VictoriaLogs). Tokenize each block, keep a ~2 byte/unique-token bloom, ZSTD the text, skip blocks that cannot match, scan the rest. No term postings of the body.

Buys: the density you liked in VictoriaLogs (vendor claims up to 15× less disk than Elasticsearch on logs; a worked part was ~11×). Costs: TODO / error / fn will not skip; phrase is a scan; regex still needs a separate n-gram index. Forecloses: O(df) lookup of a rare term is still fast, but common-term queries become sequential decompress of the matching type-group.

C. Hybrid (recommended). RAM filenames + Cox trigrams for regex. Columnar metadata (path, ext, mtime, size) with dict encoding. Body stored as type-grouped compressed text with per-block token blooms. A sparse inverted index only for rare terms (or only for filenames / code identifiers), not for every English word.

Buys: density where VL is right (repetitive extracted text), inverted lookup where VL is wrong (needles, identifiers). Costs: two query paths to implement and test. Forecloses: a single-codec textbook engine.

Recommendation: C. The fact that would change it: if you decide phrase-over-body must be as fast as Recoll on "to be or not to be" without scanning, take A and spend the space. If you decide you will never invert body terms at all, take B and accept that TODO across 20 GB of Rust is a sequential decompress of the *.rs column — which is still fine on NVMe if that column is a few hundred MB compressed.
