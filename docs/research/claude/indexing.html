Index Structures for Local Search

An options catalogue for a desktop search engine: every structure that could carry the load, priced in bytes of index per byte of text first and in query latency second. This page does not recommend; it lays out the ground so that the recommendation on the architecture page can be checked against it.

The four axes, and why most comparisons only show two

Every structure below is a point in a four-dimensional space, and the published comparisons for almost all of them project onto two dimensions and drop the other two silently. The four:

The reason to state this up front is that the two axes normally omitted are the two that eliminate the most candidates here. A plain suffix array is disqualified on density (4–5× the text estimate). An r-index is disqualified as the live structure on update cost, not on density, where it is the best option on the page. Neither of those verdicts is visible in the comparison tables those structures are usually presented with.

Key finding

The measured baseline changes what these axes are worth. On the target corpus, a hard regex with no extractable literal over the gitignore-pruned tree completes in 0.05 s measured — the exact query shape a trigram index exists to accelerate. At this scale the index's job is not to beat the CPU at matching; it is to avoid reading bytes on a cold cache. Read every latency column below against that: the density column is the one that still means something.

One consequence worth stating before the catalogue starts: the exclusion policy dominates every structure choice on this page. 87% of files and 96% of bytes in the measured corpus are build output measured; a wrong exclusion rule costs roughly 25× the index, which is more than the entire spread between the best and worst codec here.

Two rows carry an asymmetry that the bits/posting column alone hides. Binary interpolative coding is the smallest practical scheme known on clustered postings and is disqualified from the hot path anyway: decode is inherently sequential and recursive, with no known practical vectorisation and no random access without decoding a whole subtree. That makes it a cold-tier codec — an archival segment tier where you never nextGEQ — not a top-k codec. Roaring is the opposite: not competitive on the size of a sparse rare term's list, near-optimal on dense filter sets, and unbeatable on set operations. R6's split is explicit: compressed document-ordered postings (FOR/PFOR/EF) for ranked term postings, Roaring for boolean filter fields — tombstones, extension buckets, directory-scope filters.

Elias-Fano, in enough detail to implement

Given a monotonically non-decreasing sequence of n values from universe [0, u), split each value's binary representation. The low l = ⌈log₂(u/n)⌉ bits go into a contiguous fixed-width array — O(1) random access. The high bits go into a single bitvector of length n + 2^(⌈log₂u⌉−l), written unary-differentially: for element i with high part h_i, set B[h_i + i] = 1. Because the input is sorted, h_i is non-decreasing, the bitvector has exactly n ones, and counting zeros-before-each-one recovers every high part.

Total space is n·l + n + o(n) bits, which Elias and Fano proved is at most 2 bits/element above the information-theoretic optimum paper — about 2 + log₂(u/n) bits per element. For a term in m of N documents this is exactly the right asymptotic: it gets better as the term gets commoner, degrading gracefully where naive delta+VByte blows up.

nextGEQ(x) is Elias-Fano's killer feature for query processing, and the reason it pairs with both leapfrog intersection and block-max WAND. Compute h = x >> l; use a select-on-zeros structure over the high bitvector to jump straight to the h-th group of ones, skipping every zero-run before it; then scan forward through the ones, comparing low bits. The select structure costs o(n) extra bits. Because intersections walk with steadily increasing targets, sequential calls from a retained cursor amortise to O(1) in practice — you only fall back to a global select when the jump is large.

Partitioned Elias-Fano (Ottaviano & Venturini, SIGIR 2014 2) exists because plain EF's bound is tight only when the sequence is uniformly distributed over the universe, and real postings lists are bursty. PEF splits a list into variable-length chunks, each re-based to its own local universe, EF-encodes each independently, and stores a top-level EF-encoded array of chunk endpoints; boundaries are chosen by dynamic programming to minimise total encoded size. nextGEQ becomes: EF-search the endpoint index for the chunk, then nextGEQ within it. The paper reports PEF matching or beating the previously best schemes in space while being nearly as fast sequentially and much faster for skipping paper.

Hole in the ecosystem

There is no widely-adopted, actively-maintained standalone partitioned Elias-Fano crate unknown. Implementing PEF as a thin layer over sucds::EliasFano per chunk is the realistic path. Note also that neither tantivy nor Quickwit use EF as their primary postings codec — tantivy defaults to block VInt/bitpacking via the bitpacking crate, and EF-like techniques appear in tantivy's columnar crate for sparse fast-fields instead. That columnar crate is the best working Rust EF reference to crib layout decisions from.

Block layout, and why 128 is the number

Lucene groups postings into blocks of 128 docs (Lucene99PostingsFormat, back through the ForUtil codecs to 4.1) upstream. Each full block is bit-packed with a single bits-per-value chosen for the block's max delta — FOR/PFOR-style, so decode is a tight SIMD-able unpack loop; a final partial block falls back to vInt. Skip data records, at skipInterval^level, the (docID, freq-ptr, pos-ptr, payload-ptr) tuple needed to jump into the corresponding streams. 128 is the number to copy if you want a codec that is SIMD-bitpackable and well-trodden — and it is the same granularity block-max scores must be stored at, which couples this choice to the pruning algorithm below.

Segments, tombstones, and what an update actually costs

Any index supporting incremental update without full rebuild is built as immutable, independently-searchable segments — an LSM tree by another name. Deletes and updates are a per-segment tombstone bitset (Lucene's liveDocs upstream); an update is logically delete-old plus insert-new. The cost model that matters:

The thing to act on

Choose the storage rung before the codec. Dropping positions is a 3–10× cut on the postings tier; the entire spread from VByte to partitioned Elias-Fano is roughly 2–4× on a stream that is already the smaller one. If you implement exactly one codec, implement Elias-Fano over sucds, because it also hands you the nextGEQ that leapfrog AND and block-max WAND both need.

Lucene's .tim/.tip build the dictionary as a minimal acyclic finite-state transducer: input is term bytes, output is a file pointer or term-id. Because it is a transducer and not merely an FSA, shared suffixes merge the same way shared prefixes do upstream. The Rust equivalent is BurntSushi's fst crate, which implements exactly this — an ordered set/map FST with automaton-based search.

Why an FST and not a hash map

An FST is a DFA over the term-byte alphabet. Enumerating every term matching a query automaton Q — a wildcard compiled to a DFA, a regex compiled to a DFA, or a Levenshtein automaton for fuzzy — is a product-automaton walk: step both machines on the same byte, continue only where both have a live state, report only where the FST is final and Q is accepting.

The comment in the middle is the load-bearing part. A dead DFA state prunes a whole subtree unvisited, so cost is proportional to matching paths, not to vocabulary size. A hash-table dictionary cannot do this at all. This is the concrete reason to prefer an FST over a hash map even though the hash map wins on pure exact-term lookup, and it is the same mechanism fst's Levenshtein type uses for fuzzy search today.

MARISA tries are conceptually interchangeable with FSTs for this use, generally slightly better on very large, highly prefix-shared vocabularies at some cost in update-friendliness. Both are batch-built, which is not a limitation in a segment architecture — you rebuild the dictionary once per new immutable segment and never mutate one in place, exactly as Lucene does.

Maintenance signal on fst

fst 0.4.7 was last released 2021-06-06 upstream — no releases in about five years, though it is stable, feature-complete, and depended on by ripgrep's ecosystem, so bit-rot risk is low. Licence is Unlicense OR MIT. Plan to be ready to patch it yourself rather than expecting upstream responsiveness; its scope (ordered set/map FST) is narrow and stable enough that this is a low risk.

At the scale in question — vocabularies in the low millions of terms at most — FST traversal will not be the bottleneck. Use fst for per-segment dictionaries, keep a small term-id to postings-offset side table if you want term-ids decoupled from FST outputs, and reach for ART or a hash map only if a profiler says otherwise.

Inside nextGEQ on a plain sorted array, galloping (probe at offsets 1, 2, 4, 8…, then binary-search the bracket) beats a linear scan whenever the lists have very different lengths — a rare term ANDed with a common one. That is precisely what skip lists and Elias-Fano's nextGEQ are built to make cheap. For AND-NOT, wrap an iterator to skip ids in the excluded set; cheapest when that set is a Roaring bitmap.

Phrases: positions versus re-scan — the biggest density lever on this page

R6 ranks this above every codec choice, and the reasoning is arithmetic rather than taste. Positions cost 3–10× the docs-only postings tier (2–4× whole-index by the textbook rule). Eliminating them removes that multiplier rather than compressing it better, which no codec can do.

The one condition attached

Re-scan reads the file's current content, which may have changed since indexing. Keep the file's inode, mtime and a generation counter in doc values so a since-modified file fails the phrase check safely rather than returning a match against stale content. That is one doc-value field, and it is what makes the whole trade legitimate rather than merely cheap.

Proximity and NEAR use the same machinery generalised: after docID intersection, sweep both sorted position lists in O(p₁ + p₂) rather than O(p₁ × p₂) to find the minimum distance. Under the re-scan design, that sweep happens over the re-tokenised candidate file instead of over stored positions.

Dynamic pruning: WAND, block-max WAND, MaxScore

All four are the same idea — skip documents that provably cannot enter the current top-k, using precomputed upper bounds. WAND (Broder et al., CIKM 2003) keeps one global max-score per term and finds a pivot: the first term in docID order whose cumulative max-score prefix exceeds the current threshold θ. Block-Max WAND (Ding & Suel, SIGIR 2011 4) is the refinement that matters: store a max score per block, aligned with the postings' physical block layout, so the pivot check uses a locally accurate bound.

This is why codec choice and pruning algorithm are coupled. Block-max scores must be computed at index build time at the same granularity the codec already uses — if the block size is 128, that is one quantised max-score per 128-doc block per term.

MaxScore (Turtle & Flood, IPM 1995 — older than WAND) partitions differently: essential terms that cannot be skipped, non-essential terms looked up opportunistically only for docs the essential ones already produced. Often competitive, sometimes faster when few terms dominate the score budget. Block-Max MaxScore applies the block-max augmentation to it. Recent work on superblock and adaptive-block pruning reports further reductions in scored postings paper — but scoped to learned-sparse scoring, not classical BM25, so it is not a drop-in number here. For BM25 on a desktop corpus, fixed-block BMW is the proven, simplest choice.

Static pruning runs backwards for this build

Dropping postings below a score threshold at build time trades size for lost recall, not size for latency. A desktop tool's users expect exhaustive recall — "did I definitely search my whole disk". It is not on the speed/density axis at all; reject it outright rather than filing it under the tradeoff. Tiering (a small high-quality tier 0 queried first, full postings as fallback) preserves exhaustive recall at the cost of maintaining two postings copies per term, which is a density cost, not a saving.

The thing to act on

Path-sort docIDs on the first build; it costs a sort and shrinks everything downstream. Then implement leapfrog AND over Elias-Fano nextGEQ, and only add block-max scores once ranked retrieval over large result sets is actually the bottleneck — on the measured corpus, exhaustive Boolean intersection over 73k documents rarely is.

Substring and regex: trigrams, suffix structures, and the run-length family

Prior art: Glimpse got here in 1993

Candidate-generation-then-verify is not a Google Code Search invention; it is the organising idea of Manber and Wu's Glimpse, written up as Arizona TR 93-34 in October 1993 and presented at the 1994 Winter USENIX 29. Every recommendation on this page that trades precision for size is a descendant of it, and the paper states the density argument in the terms this project uses.

The 1993 numbers, from the paper itself

Glimpse's index is 2–4% of the size of the text in most cases paper, against a full inverted index which the paper puts at 50–300% of the text (citing Faloutsos 1985) paper and signature files at 10–30%. That is a 12× to 100× gap, argued in 1993, and it is the same gap this page measures between a positional inverted index and a filter-plus-scan design.

The mechanism is worth stating precisely, because two details of it are better than what most modern descriptions of “n-gram index then verify” carry:

  • Block addressing, capped at 256 blocks. The corpus is divided into roughly equal blocks and the index maps a word to the blocks that contain it, not the files and not the offsets. The cap is chosen so that a block address is exactly one byte paper. That single decision is where the 2–4% comes from: the posting is a byte, and there is no positional data anywhere in the structure.
  • The index is searched with the same engine as the text. The words in the index are stored as ASCII specifically so that agrep can run over them; a pattern is first matched against the index's word list, and then agrep runs again over the candidate blocks paper. This is the distinction drawn in §7.2 below — regex over the term dictionary versus regex over content — implemented as literally the same tool called twice, thirty years before anyone framed it that way.

What Glimpse does not give is what the rest of this section is about: a word index cannot answer /foo.*bar/ where the match crosses a token boundary, and block granularity means the verify stage rescans a whole block rather than a file. Cox's contribution is not the two-stage shape but compiling an arbitrary regex into a sound boolean query over n-grams. The lineage is worth keeping in view: plocate is Glimpse's idea applied to filenames with a modern codec, and the tiered design recommended on the architecture page is Glimpse's idea applied to a corpus that also contains PDFs.

n-gram indexes

A trigram index keys postings by every contiguous 3-byte or 3-character substring. A literal of length ≥3 is looked up by ANDing its constituent trigrams' lists; a regex is compiled into a boolean expression over trigram existence and evaluated the same way. Every candidate is then verified with a real regex engine, because the trigram query is a necessary but not sufficient condition. This is Russ Cox's Google Code Search design 6.

The common-trigram pathology

Trigram frequency in code and prose is savagely skewed — " th", "ing", " = ", "()." occur in nearly every document and contribute no selectivity. Two mitigations, both used in practice: cap or elide postings lists above a document-frequency threshold (a dropped trigram is treated as "matches everything" for planning, so correctness is unaffected), and plan on the rarest trigrams rather than ANDing all of them — dropping a redundant AND term can only enlarge the candidate set, never lose a true positive.

Case folding controls the same pathology from the other side, and it is a genuine two-way trade: folding collapses roughly 96 useful ASCII characters to about 63, halving distinct trigrams (a smaller index) while lengthening every posting list and losing case-sensitive matching. Production tools keep a case-sensitive index and handle (?i) by trying case variants of each query trigram — which multiplies the boolean query by up to 2³ variants per trigram, worse for non-ASCII.

zoekt's successor lists

zoekt does not store a flat trigram-to-doclist map. Because it already keeps per-occurrence offsets, a literal of length L decomposes into L−2 overlapping trigrams whose positions must be consecutive. The executor picks the rarest trigram's posting list as the driver and, for each candidate position, checks the neighbouring trigrams directly at offset±1 without a second index lookup upstream. Verification cost becomes O(occurrences of the rarest trigram) rather than O(file size) per candidate document. That is the whole reason positional trigrams beat doc-only for longer literals.

On encoding: byte-level trigrams are simplest and are correct for ASCII-dominated text, but shred multi-byte codepoints into meaningless fragments. zoekt n-grams over runes and keeps a rune-to-byte offset table sampled every 100 runes upstream to translate between n-gramming space and file-slicing space. For CJK, prefer bigrams — this is why pg_bigm exists alongside pg_trgm. Going to 4-grams roughly quarters posting-list length at the cost of proportionally more distinct keys and worse recall for 3-character search terms.

Composition rules
NodeRule
Concatenation AB If both children are exact, the parent's exact is the cross product, capped at a small constant, beyond which it degrades to prefix/suffix tracking only — this bounds blow-up from things like (a|b|c|d)(a|b|c|d)(a|b|c|d)…. Alternation A|B Union of exact sets if both are exact and small; otherwise query(A) OR query(B). The single biggest source of query degradation — ORing two uncertain subqueries is rarely more selective than match-all
Repetition A*, A+, A{n,} Unbounded repetition destroys exact (infinite language) and generally destroys usable prefix/suffix beyond one iteration of A

The raw derived query can be arbitrarily large from combinatorial cross products, so Cox's implementation simplifies — folding duplicate leaves, distributing AND over OR to detect always-true subtrees, capping exact-set sizes — to a bounded-size boolean query before it reaches the posting-list executor.

Its update cost is equally disqualifying: an SA is a global sort order, so one file's change perturbs it non-locally. livegrep's answer is to rebuild per repository and hold everything resident in RAM, sharded across machines — a reasonable architecture at repo scale, a poor fit for an always-on personal index that should reflect edits within seconds. FM-index and BWT

The BWT of the text is the sequence of characters preceding each suffix in suffix-sorted order, computable from the SA as BWT[i] = text[SA[i]-1] and invertible. The FM-index adds three things on top of the BWT string L: a rank/select structure (typically a wavelet tree, or per-character bitvectors for small alphabets); the C-array, counting characters lexicographically smaller than each character; and a sampled suffix array, every k-th SA value, to recover text offsets.

count(P) falls straight out as hi - lo in O(m) rank operations, with no locate needed. locate(P) additionally walks each position back to a sampled entry via the LF-mapping (LF(i) = C[L[i]] + rank(L, L[i], i)), costing up to O(sample_interval) extra steps per occurrence. That is the classic tradeoff: count is cheap, locate is proportional to sampling density, and sampling density is exactly the index-size knob.

The first-order objection is update cost. The mitigation is the one the segment architecture already provides — build one FM-index per cold segment, keep recently-changed files in a small cheaply-mutable structure, and merge-and-rebuild in the background. A changed file costs an update to a small live segment rather than a global BWT rebuild, at the price of querying N segments instead of one.

Update cost is the disqualifier, not density

r-index and move-r are no better than a plain FM-index for updates, and arguably worse. Their entire value comes from exploiting global run-structure — r is a property of the whole text — so a local edit can split existing runs and increase r in ways not confined to the edited region. Every published r-index and move-r result targets static, build-once collections (pangenomes, versioned reference corpora); none of the papers reviewed describe an incremental or dynamic construction algorithm unknown. These are cold-segment-only structures: the background indexer folds files below a "hasn't changed in N days" watermark into an r-index segment while recently-touched files stay in a cheaply-mutable trigram segment until they age into the next merge.

True regex over an FM-index

Yes, via automaton search: generalise backward search from one fixed pattern to the current SA range for every active DFA state.

Cost is bounded by DFA states × active SA-range splits, which is why it pays off only for patterns whose DFA stays small. Note the symmetry: a regex that degrades badly under Cox's derivation tends to degrade badly here too, because both are bottlenecked by how much the pattern actually constrains the search space. The selling point is that there is no verify pass at all — the match is exact by construction, no false positives. The cost is interactive automaton simulation over compressed rank structures instead of a handful of cheap posting-list ANDs, and a substantially heavier engineering lift.

No Rust path exists

There is no maintained, production-grade Rust-native r-index or move-r unknown. The reference implementations (nicolaprezza/r-index, move-r) are GPL-3.0 research code — port the algorithm from the paper, do not vendor the code into a permissively-licensed build. The honest baseline

An index cannot beat disk bandwidth on a genuinely cold read of the whole corpus. It can only help by reading less of it. R7's single-threaded warm-cache ripgrep figures on a synthetic 1.6 GB file measured: ~7.3 GB/s for a literal that never matches (memmem fast path skips most of the buffer), ~1.3 GB/s for a literal present on every line, ~0.95 GB/s for a small char-class regex present on every line. The match-everywhere cases pay for materialising 20 million match records — a realistic worst case, not typical sparse-match search.

M1's figures on the real corpus are stronger still and supersede the extrapolations: 0.05 s for both a literal and a hard regex over the gitignore-pruned tree at ~1000% CPU, and 217–234 s at 0.65–0.71 GB/s for rg -uuu over the full unpruned 153.2 GB measured — I/O-bound at one core's worth of CPU, meaning the bottleneck is reading bytes nobody wants indexed anyway.

The index's job, restated: not to make regex matching faster, but to avoid touching most of the corpus's bytes at all on a cold cache. That is what the filter cascade in the next section is for.

The thing to act on

Build the Cox derivation over a doc-only trigram index and make brute-force scanning a first-class, well-optimised fallback rather than an apology. Then, if the density mandate still bites after exclusion policy has done its work, fold cold segments into move-r — R7 names it the most underrated option here, precisely because it is invisible to anyone reading only the 2010s suffix-array/FM-index literature.

ugrep-indexer: the production instance of this idea

ugrep-indexer, now folded into ugrep ≥ 6.0 as ug --index, builds a Bloom-like structure per indexed file over that file's n-grams — bigrams and trigrams in a shared hash table, but with separate bit tiers per n-gram length so 2-grams and 3-grams never share bits and cannot cross-contaminate each other's false-positive rate upstream. Its stated goal is a >10× search speedup upstream, and its framing is the right one: the win matters most on large, cold, not-page-cache-warm filesystems — the target is avoiding a disk read at all, not avoiding a CPU-bound scan.

One correctness-relevant design choice worth copying: it uses N² hash functions rather than N, because short patterns have too few distinct n-grams to get a low false-positive rate from a standard single-hash-per-position scheme upstream.

Filters do not apply to every query class

ugrep's indexed search is documented as incompatible with -v/--invert-match, --filter, -P/--perl-regexp and -Z/--fuzzy upstream. The general lesson: a pre-index filter only helps where "do the pattern's n-grams occur in this file" is a valid necessary condition. Inverted and fuzzy matches do not have that property — a fuzzy match can occur with no exact n-gram from the pattern present. Treat "can this query even be filter-accelerated" as a first-class check on the query, not an assumption.

The selectivity condition that decides whether the index is worth consulting at all:

An index that narrows 200 GB to 2 GB of candidates is an easy win. One that degrades to match-all, or narrows only to 150 GB, is pure overhead on top of the brute-force scan it did not avoid — which is why the fallback threshold in the regex planner is load-bearing rather than a nicety.

The thing to act on

Build the per-file binary fuse filter first, before any posting list. At ~9 bits per element it is far under 0.1× the text for realistic trigram cardinalities, it is the only layer that stops a cold file being opened, and xorf means it is a dependency rather than a project.

Where the crossover actually lands

The bloom trade is a clean win when the unit of "found it" is coarse — a whole log line, a whole block, a whole file — and a bad one when you need to locate the match cheaply. VictoriaLogs' index is an order of magnitude smaller than Lucene's because it throws away all intra-block addressing, not merely positions. A tool answering "which files contain X" can tolerate block-then-scan. A tool expected to jump to line N inside a 50,000-line file cannot, without at least an in-block offset table — much smaller than full positions, but not free.

The scan-first argument, and where it breaks

At ~1.3 GB/s single-core zstd decompression, scanning a fully decompressed 10 GB hot set costs ~7.7 s single-threaded estimate, trivially parallel to sub-second on a modern desktop. If the selective working set after cheap block and zone-map pruning is single-digit GB, brute-force decompress-and-scan is competitive with maintaining a term index, and categorically simpler. On the measured corpus the figure is stronger again: 5.73 GB of real signal after exclusions measured, and 50 ms for a hard regex over it.

A log line is already the natural unit of a hit, so block granularity is fine A 50,000-line source file is not. You want line and offset level results, which pushes back toward wanting some per-occurrence structure
Regex is a rare ad-hoc investigation, latency-tolerant Regex-over-content is a stated hard requirement here — and it is precisely the query type none of these systems accelerate
Recency skew justifies hot/cold tiering A five-year-old PDF is queried as often, in expectation, as yesterday's. This technique transfers weakly
A contradiction inside this lineage

VictoriaMetrics positions "not an inverted index" as categorically superior. But ClickHouse's 2025–2026 trajectory runs the other way: it dropped its bloom-filter-only tokenbf_v1/ngrambf_v1 approach in favour of a real native inverted index, re-implemented from scratch from Feb 2025, beta Dec 2025, GA around March 2026, reporting a 10–50× query-latency win over the bloom approach and 7–10× on cold queries vendor. That is direct evidence from a comparable system that bloom-over-columnar-blocks has a real ceiling once latency is prioritised. Notably ClickHouse's new index is explicitly not a relevance engine — no BM25, no TF-IDF, built for filter-and-aggregate. The field is bifurcating, not converging.

The thing to act on

Borrow the layering, not the philosophy. R10's own conclusion is that the transferable pattern is Splunk's, not VictoriaLogs': a cheap flat-cost bloom at file or block granularity purely to skip whole files, sitting in front of a real (non-positional) per-file structure — not as a substitute for it. Add VictoriaLogs' columnar-dictionary-then-zstd encoding for every metadata column (path, size, mtime, extension, mime type), where there is no argument for anything heavier.

RaBitQ-style binary quantisation plus rerank-on-candidates. Learned sparse: SPLADE and the "reuse your inverted index" promise

The architectural appeal is real and it is the most actionable idea in R9 for a from-scratch Ferret-shaped index: SPLADE produces a sparse weighted term vector that lives in the posting lists you already have — no separate ANN structure, no GB of dense floats. But it is not free density, and R9 quantifies the bloat rather than waving at it.

The mechanism is term expansion: SPLADE assigns weight to related vocabulary the document never contains — that is the paraphrase tolerance — and each synthetic term becomes a posting. The paper's own L1-style FLOPS regularisation exists to cap this, because unconstrained sparsity both bloats the index and lengthens posting-list traversal.

Two cautions R9 states explicitly

Do not adopt BM42 on the strength of its launch post — Qdrant's own SPLADE-adjacent claim was contested within months. SPLADE itself has real, less-contested evidence. And check the licence per checkpoint: NAVER's original SPLADE releases have historically been closer to research / non-commercial than a clean Apache or MIT grant. Verify the specific checkpoint's licence file before any redistribution rather than assuming.

Embeddable stores, and a hard ceiling

sqlite-vec is brute-force, with no ANN index as of its v0.1.0 stable release, and is documented as struggling above ~1M high-dimensional vectors benchmark — which caps it out of contention for the tens-of-millions-of-chunks end of this corpus unless paired with a pre-filter. DuckDB VSS was reported to "nearly OOM a development machine" at 500K vectors × 512d benchmark; DuckDB is built to consume all available RAM, a bad fit for a background daemon. LanceDB (Rust core, IVF-PQ) and Qdrant (Rust, HNSW, embedded mode) are the credible candidates, but R9 found no independently-verified demonstration of either at this scale on a desktop unknown.

Where R9 lands

Semantic search over the full corpus is possible but not an "index it overnight" feature: CPU-only first-embed of a 200 GB mixed corpus is 13–40 days estimate, and the boundary between "runs overnight" and "runs for weeks" sits somewhere in the 20–50 GB band, not at 200 GB. The answer R9 lands on is opt-in, per-collection, over a curated 1–10 GB slice — a project's docs, a PDF archive, a mail folder — where the vector store drops to low single-digit GB even at fp32 and HNSW's RAM residency stops mattering at all.

The thing to act on

If you build a vector tier, build it as a per-collection opt-in with 384-dim binary quantisation and an fp32 rerank — that is the only cell in the storage table that is denser than the lexical index it complements. Treat SPLADE as the more interesting long-run option precisely because it needs no new structure, but measure its expansion on the real corpus before believing the "barely bigger than lexical" framing.

R5's reading of this across every format it surveyed: every engine that documents a density knob does it the same way — drop positions, keep doc-membership or freq — and the price is always phrase support. FTS5's mistake is making it a table-wide setting. What the matrix says as one sentence

Filters first, then a doc-only trigram index with the Cox derivation and an honest brute-force fallback, then docs+freq postings under Elias-Fano with phrase resolved by re-scan; positional structures only if measurement shows verify latency is the real bottleneck; move-r as a cold-segment second phase for the repetitive fraction; and vectors as a per-collection opt-in at 384-dim binary. Every one of those choices leads with bytes, and each has a named point at which measurement would overturn it.
