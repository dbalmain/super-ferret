Matching with a trigram index

The matcher you built still opens every file. Index overlapping 3-character slices, compile the regexp into a boolean of trigrams that every match must contain, intersect posting lists, recheck survivors with search.

Read

Regular Expression Matching with a Trigram Index (Cox, 2012). First half before you implement; the transformation rules when you reach lesson 6. Production: google/codesearch index/regexp.go after your toy works.

Recheck with your part-3 search, not the language’s regex. That is the point of having done the first three parts.

Why a word index is not enough

Pencil, no code. 40,000 files, query hello world: why is running even a linear matcher on every file unattractive? Why can a word inverted index not answer /foo.*bar/, /handleRequest/ (if you split camelCase), or a twelve-character hexadecimal identifier? (The course syntax deliberately omits counted repetition.)

Matches do not sit on word boundaries. The index of n-grams names substrings that must appear. Files that lack them cannot match. Files that have them still might not. Necessary condition, then recheck. Over-accept; never drop a hit.

Posting lists

(1) Google Code Search (2) Google Code Project Hosting (3) Google Web Search Code {1,2} Google {1,2,3} Hosting {2} Project {2} Search {1,3} Web {3}

AND = intersection of sorted id lists. OR = union. Pencil: Code AND Search = {1}; Code OR Search = {1,2,3}; Google AND NOT Web = {1,2}.

We store presence, not positions. Recheck handles phrases. No tests.

Why n = 3

Read Cox through the first trigram example. 2-grams: too few keys, lists become “all files.” 4-grams: too many keys, index ≈ corpus. 3 is the stable point (Cox: Linux 3.1.3 sources, 420 MB → a 77 MB index, 18%).

Pencil. Document banana: trigrams ban ana nan (ana twice, posting list still {1}). Query Goo oog Sea ear arc rch on the three docs: {1,3}.

Index a directory

Map trigram → set of file ids. For each file, overlapping windows of 3 characters. Treat a NUL in the first 8 KB as a binary-file signal and skip that file. Skip files shorter than 3 characters. ASCII is enough; pick characters or bytes and stick to one.

Five facts

Read Cox from “Indexed Regular Expression Search” through the transformation rules. A regexp is not “pull out the literals.” For every subexpression compute:

FactMeaning
emptyablematches the empty string?
exactthe finite set of matching strings, or unknown
prefix / suffixif exact unknown: possible match prefixes/suffixes
matchboolean query over trigrams: ALL, NONE, AND, OR. Necessary, not sufficient.

trigrams(s) = ALL if len<3, else AND of overlapping 3-grams. trigrams(set) = OR of those. A short string in the set poisons it to ALL.

Rules (copy onto paper):

  • '': emptyable, exact {''}, match ALL
  • c: exact {c}, match ALL
  • . / unknown char: prefix {''}, suffix {''}, match ALL
  • e?: exactly e|''. Run the alternation rule against the empty-string node — exact becomes exact(e) ∪ {''}, and match is ALL because the empty string is in there. Do not shortcut this to “emptyable, so throw the subtree away”: that is the * rule, and applying it here costs you the whole index. ab?cdef under the alternation rule yields ("acd" AND "cde" AND "def") OR ("abc" AND "bcd" AND "cde" AND "def"); under the shortcut it yields ALL.
  • e*: emptyable, exact unknown, prefix and suffix {''}, match ALL — genuinely throw everything away, because e need never appear
  • e+: emptyable(e); match of e; exact unknown, and if exact(e) was known it becomes both prefix and suffix
  • e1|e2: union; match = OR
  • e1e2: cartesian exact if both known; match = AND; if not exact, also AND trigrams(suffix(e1)×prefix(e2)) when those strings are long enough to span the boundary

Dump trigrams(exact) into match at the root when you finish. Saving into match before shrinking sets is lesson 9.

Worked examples

Do these on paper, then as unit prints.

  • Sea → query "Sea"
  • Google.*Search → AND of grams of Google and of Search. .* adds nothing.
  • ab[cd]e → ("abc" AND "bce") OR ("abd" AND "bde"). Weaker ("abc" OR "abd") AND ("bce" OR "bde") is valid, less precise.
  • a* → ALL. Every file is a candidate. Recheck is grep. Honest.
  • (foo|bar)baz → OR of the two 6-letter paths’ grams (you may factor "baz").
  • ab* → ALL. a alone matches, and one character cannot name a trigram.
  • ab?cdef → ("acd" AND "cde" AND "def") OR ("abc" AND "bcd" AND "cde" AND "def"). Two exact strings, not a discarded subtree. If you get ALL here, you applied the * rule to ?.

Implement analyze

AST: Empty, Char, Dot, Class, Concat, Alt, Quest, Star, Plus. Build it from the parser you already have. Query: ALL / NONE / And / Or of trigrams and subqueries.

Invariant: if search(pattern, file) is true, that file’s id is in the candidate set. Test this yourself on the corpus before the harness. If it fails, a rule is wrong.

Simplification

Sets explode ([Aa][Bb][Cc] is 8 exact strings). Cox’s Go code, in order:

  1. AND trigrams(set) into match before shrinking. Information-saving transformations first, information-discarding second; do it the other way round and you throw away grams you could have kept.
  2. Exact too big — Cox’s maxExact is 7, and he also dumps when the shortest string is ≥ 4 — then: extract its trigrams into match, replace each string by its first two and last two characters (strings shorter than 3 go into prefix and suffix whole), and clear exact.
  3. Prefix or suffix too big — maxSet is 20 — then chop the last (prefix) or first (suffix) character off the longest strings until the set is small, and drop any string that already has a shorter one as its prefix or suffix.
  4. Boolean: ALL AND q = q, NONE OR q = q, ALL OR q = ALL, NONE AND q = NONE.

The constants are engineering, not theory; every step here trades precision for a bounded set, and every one stays sound. [a-z][a-z][a-z] should degrade toward ALL, not enumerate 17,576 exact strings.

Hook it up

index-search --corpus DIR PATTERN:

  1. Index every file in DIR (basenames in the output).
  2. q = analyze(pattern).match
  3. Evaluate q on the posting lists: ALL = every id, NONE = empty, AND = intersect, OR = union, trigram = list or empty.
  4. Recheck each candidate with search.
  5. Print JSON candidates and hits.

Read a failure by which field is wrong.

  • Hits wrong. Your search or your parser is wrong, not your index. Go back to part 3.
  • A true hit missing from candidates. analyze dropped a necessary trigram. The invariant in lesson 8 has failed, and this is the only kind of wrong that is not merely slow — it silently loses results.
  • Candidates for Search missing d.txt. You are reporting the survivors of the recheck, not the output of the trigram query. Print the query’s result before you recheck it.
  • Candidates for banana not empty. Your query degenerated to ALL somewhere, or you never intersected. No file holds ban, so the intersection is empty before recheck ever runs — this is the case that proves the index prunes at all.

After it passes, read index/regexp.go. You have earned it.
