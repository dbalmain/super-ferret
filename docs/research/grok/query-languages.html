Side investigation · D62 and D67

Query languages, read for ferret search

How other search tools spell a field, a boolean, a phrase and a regex, and which of those spellings an agent will type without looking the grammar up. Written so D62’s text: plus whole-argument OR/NOT, and D67’s grep:, stay a choice rather than an accident.

Research date 2026-10-08. Every syntax claim is cited to the vendor’s current documentation. A detail that could not be checked is marked unverified. “What an agent types” is analysis of those docs and of training-corpus habit, not a vendor claim.

Reading this against D62 / D67

Dave agreed with D62 A (text: for content; OR, NOT, ( and ) as whole arguments) and asked for this survey. D67 recommends grep:REGEX for a content regex, case-insensitive and multi-line, with re: left as a name regex. The recommendations at the end may disagree with either. They are recommendations with a tradeoff, not a change to the decisions.

Ferret today

The live grammar is crates/ferret-query/src/lib.rs and the help in crates/ferret/src/cli.rs. Query::from_args takes one atom per shell argument. OR, NOT, ( and ) are operators only as a whole argument. Adjacent atoms AND. AND binds tighter than OR; NOT is tightest. a b OR c is (a b) OR c. A quoted argument with spaces is one atom, so ferret search "text:foo OR text:bar" is a single text: phrase, not a boolean.

A bare word is a substring of the file name. A word containing /, and path:, are substrings of the path. name: forces the name reading, which is how a file named OR is spelled (name:OR, or case:OR). text: is content: one token is a term (a whole word or an identifier part), several tokens are a phrase in order. ext: is a name ending in .EXT. A glob (*, ?, [) matches the whole name, or the path’s trailing components when it contains /, or the whole path when it starts with /. * and ? stop at /; ** spans components. re: is an unanchored name regex (the regex crate). size: and mtime: and type: are metadata. case: makes the next atom exact. Otherwise words, globs and ext: fold ASCII case, re: folds Unicode case, and text: folds as the content index does. There is no smart-case rule.

An atom that starts with - is an unknown flag unless it follows -- (crates/ferret/src/args.rs). A row with no document (a directory, a binary, a file over the size cap) never holds a text: atom, so NOT text:x is true there. D67, still open, recommends grep:REGEX for a content regex: case-insensitive, ^ and $ at line boundaries, (?-m) for whole-document anchors, . not matching \n. DESIGN.md § Query still sketches /regex/, which D67 rejects because /usr/ is already a path substring.

What an agent types

Before it reads a help page, an agent reaches for one of about six shapes. Which one depends on the last tool in its training mix, and code-search and log-search outweigh desktop search.

  • field:value with a space meaning AND, from GitHub, Sourcegraph, Kibana, Datadog, Recoll, Everything. The field name it will guess for content is content:, then text:.
  • A bare word meaning the body, or the body and the path. GitHub does both. Sourcegraph keyword, Recoll, KQL, Splunk, Datadog free text, and a Lucene default field all search text. Everything, fd, and ferret search names.
  • /regex/ for a content pattern, from GitHub and Sourcegraph. Zoekt omits the slashes and treats the bare pattern as a Go regexp. Lucene uses the slashes and anchors to the whole term.
  • Uppercase AND/OR/NOT from Lucene, Splunk, GitHub’s examples, Recoll’s OR, and Windows AQS. Lowercase and/or/not from KQL, Sourcegraph, JQL clauses, and Kusto. Zoekt accepts only lowercase or, and and is not an operator there.
  • -term or !term for negation, from Lucene, Google, Datadog, Everything, Recoll, Zoekt, and Sourcegraph filters. Parentheses for grouping, except Everything, which uses < >.
  • The whole query in one pair of shell quotes. Every tool above except ferret, rg, and fd is a single string. Ferret’s operators are separate arguments.

Precedence is the quiet disagreement. Sourcegraph, JQL, and Kusto bind and tighter than or, which is also ferret and ordinary programming. Lucene’s AND/OR do not follow that rule, and the manual tells you to parenthesize. Splunk’s search command and Recoll bind OR tighter. LogQL label filters and Windows AQS bind left to right, so a OR b AND c is (a OR b) AND c. GitHub and the current Kibana KQL page show parentheses and do not state a binding. An agent that parenthesizes is safe everywhere. An agent that writes a b OR c and expects “a, plus either b or c” is reading Recoll, Splunk, and Everything’s likely habit, and it is wrong in ferret.

Lucene, Elasticsearch, OpenSearch

Lucene classic and Elasticsearch’s query_string are the same idea with two defaults that matter. OpenSearch’s query_string is that family; this section cites the Lucene 9.12 classic package summary and the current Elasticsearch pages, and does not re-read OpenSearch for deltas.

A field is status:active, and it applies only to the term it precedes. title:The Right Way searches title for The and the default field for Right and Way. Group with title:(quick OR brown). Elasticsearch’s default_field defaults to *, every eligible field. The default operator is OR, so capital of Hungary is three optional terms. AND, OR and NOT must be all capitals (Lucene), and Elasticsearch also accepts &&, || and !. Elasticsearch says those words do not honor the usual precedence, so parentheses are required. The preferred operators are + (must) and - (must not); other terms are optional and only affect score. A query that is only NOT "jakarta apache" returns no results.

Quotes are a phrase. "fox quick"~5 is proximity. Reserved characters include + - = && || > < ! ( ) { } [ ] ^ " ~ * ? : \ /. < and > cannot be escaped at all in query_string. Whitespace is not an operator.

Wildcards are ? and * inside a single term, not inside a phrase. Lucene classic rejects a leading * or ?. Elasticsearch allows it, and allow_leading_wildcard defaults to true. A regex is wrapped in slashes, name:/joh?n(ath[oa]n)/. The engine is Lucene’s, not PCRE. It has no ^ or $: the expression must match the entire string. The regexp query’s flags default to ALL, which turns on complement ~, interval <>, intersection &, any-string @ and empty #. allow_leading_wildcard does not apply to regexes, so /.*n/ walks every term. Case follows the field’s analyzer; wildcard terms are only normalized (lowercasing, ASCII folding) unless analyze_wildcard is set.

An agent types +required -excluded, uppercase AND, and /regex/, and it parenthesizes if it has been burned. It will also type lowercase and, which Lucene parses as a term.

Sources: Lucene 9.12 classic query parser, Elasticsearch query_string, Elasticsearch regular expression syntax.

Kibana KQL

KQL is Kibana’s filter language. It is not Lucene, and the current reference says so. A bare term searches every field. A field is http.request.method: GET. On keyword, numeric, date and boolean fields the value must match exactly, including case. On a text field the terms are analyzed and order does not matter, so null pointer also matches pointer null. Quotes restore order. Escape \():<>"*, or quote the value.

and, or and not are not case-sensitive. The current page’s boolean examples all use an explicit operator, and it says to use parentheses to set precedence. It does not say whether and binds tighter than or, and it does not show two bare terms side by side as an implicit AND or OR. not http.request.method: GET is a complete query. The only wildcard is *, and a leading * is allowed unless query:allowLeadingWildcards is off. That setting is unavailable on Elastic Cloud Serverless. There is no ? and no regex. Regex is why people switch the Kibana language picker to Lucene.

An agent that has used Discover types field:value and other:value in whatever case, with * and no slashes. When it says “KQL” without Kibana in the sentence, it often means Kusto, below.

Source: Kibana KQL.

Kusto (Azure Data Explorer, Log Analytics)

Included because an agent that says “KQL” in a logs conversation means this language, used by Azure Data Explorer, Log Analytics, Microsoft Sentinel and Fabric. It is a pipe language. There is no field:value.

A filter is where Column has "term" or Column == "term". has matches a term and is case-insensitive; has_cs is the sensitive form. contains is a case-insensitive subsequence. == is case-sensitive; =~ is not. The operator pages’ performance notes prefer a case-sensitive operator when one exists (hasprefix_cs is the page re-checked). matches regex is case-sensitive. Its example, State matches regex "K.*S", returns KANSAS, ARKANSAS and LAKE SUPERIOR, which only works as a containment match. The page does not say “unanchored” in words. hasprefix says the term index covers terms of three or more characters; a shorter term scans.

and has higher precedence than or. Both keywords are written in lowercase on the logical-operators page. Negation of a string test is !has, !contains, !=. A where that is only a negation is an ordinary predicate. There is no glob; hasprefix and hassuffix are the prefix and suffix operators.

An agent types Field has "error" and Field !has "timeout", or Field matches regex "foo.*bar", inside a | where. It does not type field:value once it has decided this is Kusto. Before it decides, it types Kibana.

Sources: Kusto string operators, matches regex, logical operators.

Splunk SPL

The search command is the part an agent pastes. It is not the whole of SPL. Terms and expressions have an implied AND: web error is web AND error. Field constraints are comparisons, clientip=192.0.2.255, with != < <= > >=. When a command’s syntax includes a logical operator, the operator is written in uppercase.

Evaluation order for search is parentheses, then NOT, then OR, then AND. eval and where evaluate AND before OR. The search reference says this outright, and the predicate-expressions page repeats it. A=1 AND B=2 OR C=3 is processed as the search command’s order, which is OR before AND. NOT applies to the term or expression immediately following it. The manual points at a separate page for the difference between NOT and !=; that page was not re-read, so the missing-field behaviour is not stated here. Wildcards are * in values and inside IN.

Searches are case-insensitive. Error matches error and ERROR. CASE(error) matches that case only, and CASE() can hold a wildcard. TERM() matches the parenthesized text as one indexed term, including minor breakers such as periods. The search command page does not document an inline regex. A regex pipeline command exists; its engine, flags and anchoring were not re-read for this report.

An agent types index=main sourcetype=app error NOT debug status=500, with uppercase OR when it wants a union, and it does not expect OR to bind tighter than AND unless it has hit this specific footgun. The footgun is real, and it is the opposite of eval.

Sources: search command, predicate expressions, SPL syntax (uppercase operators), CASE() and TERM() (English body served under a /ja-jp/ path).

Jira JQL

JQL has two layers, and mixing them up is the usual bug. The outer layer is clauses: project = FOO and status = Open. The keyword reference writes and, or and not in lowercase. There is no juxtaposition of two clauses; each pair needs an operator. Precedence, from strongest to weakest, is parentheses, then comparison (= != ~ IN IS and the rest), then NOT, then AND, then OR. So AND binds tighter than OR, as in ferret.

Contains is ~. text ~ "some words" searches summary, description, environment, comments and text custom fields. The value on the right of ~ is a second language, and that page is Lucene’s: AND, OR, NOT, + and - must be all capitals, OR is the default between terms, || works, and the page shows parentheses to force bugs AND (atlassian OR jira). Phrases are quoted. Wildcards are summary ~ "win*" and issueKey ~ "*WIN-1*". A leading or very broad wildcard can fail because it expands to too many terms. No regex dialect is documented on the operators page or the text-search page. summary ~ win also stems: the example says it matches derivatives such as wins.

An agent types the outer layer in lowercase (project = X and text ~ "foo bar") and, if it has used Lucene, puts capitals inside the quotes. A pure NOT inside the quoted value is the Lucene “matches nothing” trap. A JQL not on a clause is ordinary negation.

Sources: JQL operators, JQL keywords, order of operations, text-field search syntax.

Datadog log search

A term is a word, or a quoted sequence ("hello dolly"). The boolean operators on the syntax table are case-sensitive: AND (the default when nothing is written), OR, and - for exclusion. The table’s example is authentication AND -password. A later CIDR example uses NOT(CIDR(...)), so NOT occurs, but it is not in the operator table. The page does not state whether AND or OR binds tighter. Parentheses appear in the examples.

Reserved attributes are bare: service:web-app, status:error, host:.... Other attributes take @: @url:www.datadoghq.com. *:hello searches every attribute, including the message. A bare hello searches the message and a few error attributes, not every attribute. Attribute search is case-sensitive. The page says to use full-text search to get case-insensitive results; the same page also describes *:hello as an exact string, and it does not spell out how those two sentences interact. Wildcards are *, and only outside quotes: "*test*" is the literal characters. ? matches one special character or a space inside an attribute value (@my_attribute:hello?world). Escape - ! && || > < the brackets, quotes, * ? : \ # and spaces. / is not special. @ cannot appear as a search character in the explorer; it introduces an attribute.

There is no regex operator on this page. Grok regex is an ingest parser, and calculated-field regexp_like is a different surface. Do not teach an agent that /foo/ works in the log search bar. -@http.status_code:* is a documented query with no positive term. A bare -password alone is not shown.

An agent types service:web @http.status_code:500 -healthcheck, uppercase AND if it writes the operator, and * for a wildcard. It reaches for /regex/ and gets a literal or a syntax error.

Source: Log search syntax.

Dynatrace DQL

DQL is a pipe of commands: fetch logs | filter … | search …. The logs app documents the filter form an agent actually writes. Successive filter statements are connected with AND, so status = ERROR followed by status = WARN matches nothing. filterOut removes rows that match.

A phrase across every field is * ~ "failed to charge card", which the page says is the search command. The same phrase restricted to the body is content ~ "failed to charge card", equivalent to matchesPhrase. A wildcard value is content = "*card*", equivalent to matchesValue. matchesPhrase, on the matcher page, is case-insensitive for ASCII, treats * as one term rather than a mid-string wildcard, and checks word boundaries unless the phrase itself starts or ends with *. Field names outside [A-Za-z0-9_.] need backticks; that detail is from the DQL language reference and was not on the logs page re-read here, so treat the backtick rule as unverified against the current commands page. Boolean and / or / not appear in DQL filters. The logs page does not state their precedence, and this pass did not re-read a logical-operators page, so precedence is unverified. A regex spelling was not on the logs filter page. Leave it unverified rather than inventing matchesPattern syntax.

An agent types fetch logs | filter loglevel == "ERROR" | search "timeout", or the shorter content ~ "timeout". It does not type loglevel:ERROR once it knows this is DQL. The == and the pipe are the habit.

Sources: Query and filter logs, DQL commands, DQL matcher (matchesPhrase).

Grafana Loki LogQL

Included because it is the log query an agent meets next to Datadog and Splunk, and its anchoring rules are the ones people get wrong. Every query starts with a stream selector, {app="api", env="prod"}, then an optional pipeline of | stages. There is no field:value. Label matchers are = and != for exact strings, =~ and !~ for regex. A selector regex is fully anchored: it must match the entire label value, newlines included, and . does not match a newline unless the pattern uses (?s) or [\S\s].

Line filters are a distributed grep and are case-sensitive. |= "error" means the line contains the string, != "timeout" means it does not, |~ and !~ are the regex forms. A line-filter regex is not anchored, and . does match newlines. The engine is RE2. (?i) at the start of the pattern is the case fold. Chained filters are sequential AND: |= "error" != "timeout". Backticks quote a string so that backslashes stay literal. After a parser stage (json, logfmt, regexp), label filters reuse = != =~ !~ and combine with and, or, or with a comma, a space or a pipe meaning AND. Those predicates bind left to right, not AND-tighter: duration >= 20ms or method="GET" and size <= 20KB is ((duration >= 20ms or method="GET") and size <= 20KB). Parentheses force AND first.

An agent types {namespace="prod"} |= "error" != "timeout" or |~ "(?i)error.*timeout". A pure-negative line filter still needs a selector. The two anchoring rules (selector versus line) are the detail it will get backwards.

Source: LogQL log queries. The anchoring and precedence sentences above were checked against that page in this research; the page tail past the label-filter section was truncated in the fetch.

GitHub code search

This is the syntax an agent has typed most often. A bare term matches file content or the path. Whitespace means both terms, and the page says that is the same as AND. OR and NOT are written in uppercase in the examples. The page does not say whether AND binds tighter than OR. It does show parentheses: (language:ruby OR language:python) AND NOT path:"/tests/". Qualifiers, operators, quotes and regexes must be separated by spaces, or that piece of the query falls back to a literal search. printf("hello world\n"); is searched as that exact text.

Qualifiers include repo:, org:, user:, language:, path:, symbol:, content: and is:. content: restricts a term to file content, because the bare term also hits paths. Quotes are an exact string, whitespace included. Outside a regex the only escapes are \" and \\. A regex is /sparse.*index/, and a slash inside it is escaped. The engine is described as most common features, without lookaround, plus \n, \t and \x{hhhh}. The page does not say whether /regex/ is unanchored; path:/(^|\/)README\.md$/ shows the user adding anchors when they want them. Default search is case-insensitive. Case-sensitive is /(?-i)True/, a regex flag, not a query-wide switch.

path: accepts a small glob. * does not match /, ** does, ? is one character, a leading / anchors at the start of the path, and quotes turn the glob off so path:"file?" is literal. repo: is not a regex and not a partial match; the owner and name must be complete.

An agent types repo:org/name path:*.rs foo OR bar, quotes a phrase, and reaches for /regex/ and content:. It writes -path:tests less often than NOT path:tests, because that is the operator the page teaches. It will be surprised that ferret’s bare word ignores content, and that re: is a name.

Source: Understanding GitHub code search syntax.

Sourcegraph

Keyword search is the default. A space means both terms anywhere in the document. "foo bar" is that string, quotes not included. /foo.*bar/ is RE2. foo OR bar is either term. repo: and file: values are regexes and are not anchored; ^ and $ anchor them, and two repo: filters intersect unless you write repo:foo|bar or or. content:"..." is how you search for a reserved word such as OR. case:yes turns on case sensitivity; without it every match is case-insensitive. patternType:keyword and patternType:regexp select the mode. In regexp mode a space between patterns becomes .*?.

The boolean section accepts and and AND, or and OR, not and NOT. and binds tighter than or, so a and b or c and d is (a and b) or (c and d). NOT can stand where - stands on a filter. On a pattern, NOT excludes documents that contain the following term. Without parentheses, operators split the query into groups: file:main.c char c or (int i and int j) is read as (file:main.c char c) or (int i and int j).

An agent types file:\.go$ foo OR bar case:yes and /regex/. content: is the field name it will try on ferret. case:yes is the case switch it will try, and ferret’s case: does not take yes.

Source: Sourcegraph query reference.

Zoekt

Zoekt is the engine under Sourcegraph’s older regexp path, and its own query language is stricter and easier to misread. A bare pattern is a Go regular expression. There are no slash delimiters; a slash is a literal character. A pattern with no regexp operators is optimized to a substring search. Space is AND. The only boolean word is lowercase or. The word and is a search term. Negation is -. Parentheses group, and parentheses around a field keep the field: (sym:MyFunction) is not a content search for the text sym:MyFunction.

Fields take a regex value: content: (c:), regex:, file: (f:), repo: (r:), lang:, sym:. Double quotes group spaces. A backslash escapes the next character, and a regex backslash is two of them. case:yes, case:no, and case:auto. Auto is the default: an uppercase letter makes the pattern sensitive. file:README\.md$ uses the regexp’s own anchors.

An agent that knows Zoekt types file:.*\.rs$ foo or bar with a lowercase or, a leading -, and no slashes. It will type and and search for the word. Ferret’s uppercase OR and its refusal of -term both miss this habit. Ferret’s fold-by-default is case:no, not case:auto.

Source: Zoekt query syntax.

ripgrep and fd

Neither is a query language. They are the shell baseline, and Dave has already separated them from this grammar: ferret grep is a ripgrep-shaped verb, tracked on its own. The search grammar should not grow -i and -g to look like them.

ripgrep’s pattern is a Rust regex, unanchored within a line, so ^ and $ are line anchors. -U / --multiline lets a match span lines. -F is a fixed string. -i ignores case. -S / --smart-case ignores case until the pattern contains an uppercase letter, and the guide says that flag is usually put in an alias or a config file. The bare command does not fold. -g is a gitignore-style glob, with ! as a blacklist. -t and -T are file types. There is no AND of two patterns; the boolean is the regexp or a second invocation. A pattern that starts with - is a flag unless it follows -e or --. The common-options list re-read here does not include an invert flag; do not cite one from memory.

fd takes one pattern. The default is a Rust regex (docs.rs/regex), matched as an unanchored substring of the file name: fd netfl finds a name containing netfl, and fd '^x.*rc$' is how you anchor. Smart case is the default: insensitive until the pattern contains an uppercase letter. -s forces sensitive, -i forces ignore. -g switches to globs. -e is an extension, repeatable in the examples (-e h -e cpp). -t is a type. Hidden files and gitignore matches are skipped unless -H, -I or -u. There is no second pattern and no content search. The -h summary re-read here has no -F; literal mode is unverified against the current man page.

An agent reaches for rg -i -g '*.rs' pattern and fd -e rs pattern. Those belong to ferret grep and to ferret’s name atoms (ext:rs, a glob), not to a boolean inside text:.

Sources: ripgrep GUIDE, fd README.

Google

The current Search Help page is narrower than the cheat sheets agents have memorized. It documents quotes for an exact word or phrase, site:, - to exclude a word, before:, after:, and filetype:. There must be no space between the operator and the term: site:nytimes.com works, site: nytimes.com does not. The same rule is stated for the minus. The page does not document OR, |, AND, *, intitle: or ext:. Those spellings are not cited here. Implicit AND of bare words is how the product behaves in ordinary use; the operators page does not list an AND keyword, so this report does not claim one.

An agent still types site:, quotes, and -word with no space. The - habit is the one that hits ferret’s flag parser.

Source: Refine Google searches.

Everything (voidtools)

Everything is the desktop filename search agents have actually used, on Windows. A bare word is a substring of the file name. A backslash searches the path: \downloads. A trailing backslash means a folder. Space is AND. | is OR, and spaces around the bar are ignored. ! is NOT. < and > group. Quotes make operator characters literal, and they quote a path that contains a space: without them, C:\Program Files is the path C:\Program AND the name Files. The Searching page does not state whether | binds tighter than space. Do not copy a precedence claim from a forum post.

Wildcards are * and ?, which do not match \, and **, which does. Using a wildcard matches the whole filename, so *.pdf is every PDF, not a name containing that string. regex: enables PCRE for that term. ^ and $ are the start and end of the filename. Turning regular expressions on for the whole query disables operators, wildcards, macros, modifiers and functions. case: is a modifier that matches case, stacked in front of the term (case:README, case:regex:content:^FOO). Match Case is also a menu option. Content is a function, content:invoice, and it is not indexed: the page says it can be extremely slow and should be narrowed with an extension, a path or a date. ext:cpp;h;cs, size:>100mb and dm:today are the other functions an agent will try. Semicolons in ext: are a list; ferret’s ext: is one extension.

An agent types *.rs \src content:foo !draft. The bare word, the glob, ext: and size: all rhyme with ferret. content:, !, | and < > do not. regex: on a name is ferret’s re:; regex:content: is the content-regex spelling Everything uses, which is D67’s grep: in two prefixes.

Sources: Searching in Everything, search syntax, search modifiers.

Spotlight and mdfind

Apple’s archived File Metadata Query Expression Syntax is the page that still describes the predicate language mdfind evaluates. A clause is attribute == value. Operators are == != < > <= >=, plus InRange(attribute, min, max). Modifiers sit in brackets immediately after the operator: c case-insensitive, d diacritic-insensitive. kMDItemAuthors ==[c] "Steve" and kMDItemTextContent ==[c] "*Paris*" are the documented forms. Without [c], == is case-sensitive: == "Paris" does not match paris. Wildcards are * (many) and ? (one) inside the value. An exact value with no wildcard matches the whole attribute. Booleans are && and ||, with parentheses. Escape " and ' with a backslash. Dates are seconds since 2001-01-01, or $time.now, $time.today, $time.this_week(-1), $time.iso(...). The page has no regex.

One example on that page is malformed: kMDItemAuthors[c] == "Steve" puts [c] on the attribute. The same page shows the correct ==[c] form. The page does not document Finder’s keyword shorthand (kind:pdf, mdfind -name, a | OR, a -string NOT). That shorthand is what an agent who has used the Finder will type. It is unverified against an Apple-hosted page in this pass. Third-party reports that ==[c] fails on current macOS, and that a suffix form '*foo*'cd works, are also unverified here. Cite the bracket form as what Apple’s page shows.

An agent types either kMDItemDisplayName == '*report*'c or kind:pdf. Neither is ferret. The predicate shape is the same family as Kusto and DQL (field == value), not field:value.

Source: File Metadata Query Expression Syntax (archived, updated 2011-09-28).

Windows Advanced Query Syntax

AQS is the third desktop grammar, the one Windows Search and Explorer use. A restriction is prop:value, or a bare word that searches every property. Juxtaposition is AND. AND, OR and NOT must be uppercase; the rest of the language is not case-sensitive. Mixed AND and OR bind left to right no matter which operator it is: apple AND pear OR plum is (apple AND pear) OR plum, and apple OR pear AND plum is (apple OR pear) AND plum. The page recommends parentheses. The default string operator is word-starts-with; other types default to equal.

Quotes are phrases. A quote inside a phrase is doubled. Comparison operators include =, < > <= >=, and a family of ~ operators: ~< starts with, ~> ends with, ~= contains, ~! does not contain, and ~ alone is DOS wildcards (? one character, * many), as in System.FileName:~"Mic?osoft W*d". $< is word-starts-with and $= is word-equals. A range is 5kb..10kb. Empty [] means no value. There is no regex on the syntax page. For programmatic queries on Windows 7 and later the page requires canonical property names (System.Size:>1kb). The short keywords follow the Windows UI language, so they are the wrong spelling to put in a script. A double NOT on the same property is described, on the same page, as not cancelling (System.Kind:--picture stays “not a picture”). That sentence was read off the page earlier in this research and did not come back in a later search, so treat the double-negation example as checked once, not twice.

An agent on Windows types System.FileName:report AND ext:pdf or the localized keyword, uppercase AND, and a * glob. Left-to-right binding means a OR b AND c is not ferret’s reading and not JQL’s.

Source: Advanced Query Syntax.

Recoll

Recoll is the Linux desktop tool with a real query language, and it is the one ferret is closest to. The manual’s general syntax is Xesam-descended. field:value means contains. A bare word searches the document. Elements combine with an implicit AND. OR must be capitals, and it has priority over AND: word1 word2 OR word3 means word1 AND (word2 OR word3), not (word1 AND word2) OR word3. That is the opposite of ferret, of Sourcegraph, of JQL and of Kusto. Parentheses group. A - in front of an element excludes it. The sample query is author:"john doe" Beatles OR Lennon Live OR Unplugged -potatoes.

Quotes are a phrase, and order matters: title:"prejudice pride" is not title:prejudice title:pride. Words inside quotes, and capitalized words, are not stem-expanded. Wildcards are *, ? and [], anywhere in a term, including the left side. A left wildcard scans the term list and can be truncated if the expansion is too large. Stemming is preferred to a trailing * for natural-language terms, and any wildcard in a term turns stemming off. With a field prefix, author:john,lennon is AND and author:john/ringo is OR, with no spaces. Without a field prefix, a comma or a slash produces a phrase. text: is the explicit name of the main body, so text:napoleon/bonaparte is an OR in the body. Default fields include title, author, filename (alias fn), ext. The general syntax page does not document a regex operator or a case: modifier. Case control on that page is the stemming rule: capitalize a word to keep it literal. Modifiers such as "two one"po10 are a proximity syntax, not a case switch.

An agent that has used Recoll types ext:pdf filename:invoice "exact phrase" OR other -draft, and it reads a b OR c as a AND (b OR c). That reading is also Splunk’s search command. It is wrong in ferret. text: as the body field is the one spelling ferret already shares, which is why text: is less alien than it looks from the code-search side, where the word is content:.

Sources: Recoll general syntax, wildcards.

Implications for ferret

D62 A is the right grammar: content is prefixed, operators are whole arguments, AND is juxtaposition. D67 A is the right content-regex spelling: grep:, with re: left on names. The survey does not overturn either. It does say where an agent will be silently wrong, and which two small changes would catch the most of that without giving up what the grammar buys.

Least predictable

Ordered by how often the agent gets a wrong answer rather than an error.

  1. A bare word is a name. GitHub’s bare term is content or path. Sourcegraph keyword, Recoll, KQL, Splunk, Datadog free text and a Lucene default field all search text. Everything, fd and ferret search names. ferret search serde returns files whose names contain serde and says nothing about the miss on content. That is the expensive failure, because the exit status is success.
  2. The query is one string. Every tool in this report except rg and fd takes the query as one string. Agents quote it. ferret search "text:foo OR text:bar" is one text: atom whose tokens are foo, or, text, bar, a phrase, and it can succeed. The separate-argument form ferret search text:foo OR text:bar is the boolean.
  3. re: is a name, and the content regex is not /…/. GitHub and Sourcegraph spell a content regex as /regex/. Zoekt treats the bare pattern as a Go regexp. Lucene’s /regex/ matches the whole term and has no ^ $. An agent types ferret search /fn.*handler/ and gets a path substring, which is exactly why D67 rejected bare slashes. It types re:fn.*handler and searches names. grep: is the right spelling once the agent has read the help. It will not guess it.
  4. Operators are the exact bytes OR and NOT, and and is a name. Lucene, Splunk, GitHub’s examples, Recoll’s OR and Windows AQS want capitals, so the exact-case match is half the habit. KQL, Sourcegraph, JQL clauses, Kusto and Zoekt’s or want lowercase. ferret search text:foo or text:bar searches for a file named something with or in it, AND both text atoms. and is the same kind of miss. -term is a different miss: Google, Datadog, Lucene, Everything, Recoll, Zoekt and Sourcegraph negate that way, and ferret reports an unknown flag. The error is recoverable. The lowercase-or success is not.
  5. content: and case:yes. GitHub, Sourcegraph and Everything call the body content:. Recoll and ferret call it text:. Sourcegraph and Zoekt write case:yes. Ferret’s case: consumes the next atom, so case:yes is a case-sensitive search for the name yes.

AND-tighter-than-OR is predictable to anyone who parenthesizes, and it matches Sourcegraph, JQL, Kusto and the way the help already glosses a b OR c. It does not match Recoll or Splunk’s search command, both of which bind OR tighter, or Windows AQS and LogQL label filters, which bind left to right. GitHub and the current KQL page never say. This is a real disagreement. It is not one of the silent failures above, because the agent who writes a b OR c without parentheses is already wrong in Lucene, and the agent who has read ferret’s help has been told the binding in the first boolean line.

Change 1. Accept and / or / not in any case, as the operators.

AND is explicit juxtaposition. OR and NOT stay the operators they are, matched case-insensitively. A file named or, and or not is spelled name:or, which is already how a file named OR is spelled.

Buys. The lowercase habit from KQL, Sourcegraph, JQL, Kusto and Zoekt, and the uppercase habit ferret already accepts, become one rule. text:foo or text:bar stops returning a successful name search.

Costs. Three bare words stop being name substrings. They are common English words and uncommon filenames. The grammar comment and the help line change. No existing query that used uppercase OR or NOT changes meaning.

Not this. Do not also accept - or | or !. - is a flag, which args.rs already rejects, and D62 recorded why. | and ! need shell quoting and collide with globs and history. The error on -term is the right behaviour; the help already has a place to say “negation is NOT, and a name that starts with - goes after --”.

Change 2. Alias content: to text:. Keep text: as the documented spelling.

Buys. GitHub, Sourcegraph and Everything’s field name works. content:"request handler" is the phrase agents already know how to quote.

Costs. Two names for one atom. Help text has to say text: first and mention the alias once, or agents will document both and the grammar grows a third synonym later. A file whose name is the literal string content:foo is already unreachable as a bare word, because of the prefix scan; name:content:foo remains the escape, as it is for text:.

Not this. Do not rename text: to content:. D62 has shipped the shorter spelling, Recoll uses text: for the body, and a rename breaks every S2 query and the help. Do not make a bare word search content. That is D62 B, and it changes every S1 query. The fact that would change it is still the query log, not this survey. The survey says the failure is silent; the mitigation that does not rewrite history is the first line of the help and of the agent skill: a bare word is a name, text: is content.

A third, smaller, parse change is worth doing in the same patch if the two above land. If a single argument contains OR or NOT or AND as a separated word, reject it and print the unquoted form. Today that argument is a phrase or a name, and it succeeds. The cost is that a filename containing the letters “ OR ” has to be name:. That name is rare. This is the quoted-whole-query habit, and an error beats a wrong hit list.

Keep, including where it is unusual

Whole-argument operators, and AND by juxtaposition.

This is find’s shape and it is shell-safe. One atom per argument means a path with spaces is one atom and a parenthesis is one atom, quoted for the shell as the help already says. The cost is change 1’s leftover: agents quote the whole query. The parse error above is the patch. Switching to a single query string would match every other tool in this report and would give the shell’s quoting rules to the user twice. D62 already declined that.

AND tighter than OR.

Keep it. It matches Sourcegraph, JQL, Kusto, programming languages, and the reading the help states: a b OR c is (a AND b) OR c. Recoll and Splunk search bind OR tighter. Lucene refuses to choose and tells you to parenthesize. Windows AQS and LogQL label filters go left to right, so their second example is OR-then-AND. Following Recoll would make ferret’s help line a lie and would surprise every agent that writes code. The tradeoff is that a Recoll user, and a Splunk user who has learned that one footgun, misreads an unparenthesized mix. Parentheses already work. State the binding in the help, which it does, and do not switch.

grep: for a content regex. re: stays a name. No /regex/.

Agree with D67 A, and with the rejection of bare slashes. /usr/ is a path substring today. text:/usr/ is a content term today. Overloading either is a silent change of the kind D62 refused. grep: is one more prefix, and agents know the word from ripgrep. They will not invent the prefix; change 1 and change 2 do not fix that. The help line is the fix, next to re:: re: is the name, grep: is the content. D67’s own escape hatch is right: if S4’s traces show agents sending /…/ or re: for content, alias the winner. Do not alias it now, before those traces, because a slash alias reintroduces the /usr/ collision unless the rule is fiddly (slashes plus a metacharacter), and a fiddly rule is a second grammar.

The semantics D67 already picked also match the tools agents compare against. Case-insensitive by default matches GitHub, Sourcegraph, ferret’s text:, and Recoll’s fold-and-stem world. ^ and $ at line boundaries match ripgrep and LogQL’s line filter, and they do not match Lucene, which has no anchors and matches the whole term. (?-m) is the escape for the whole-document reading. . not matching \n is the regex crate’s default and ripgrep’s default without -U. Keep that set. The pure-NOT cost is a planner problem, which D67 (b) already answers by refusing when the Maybe bound exceeds a quarter of live documents. Do not copy Lucene’s “NOT alone matches nothing”. In ferret a directory has no document, so NOT text:x is true there, and that result is load-bearing.

Fold by default, case: on the next atom, no smart-case.

Keep it. GitHub folds and uses (?-i) inside a regex. Sourcegraph folds unless case:yes. Datadog’s attribute search is sensitive and its full text is the insensitive path. ripgrep is sensitive until -i, and smart-case is an opt-in the guide expects you to alias. fd and Zoekt case:auto flip to sensitive when the pattern contains an uppercase letter. An agent capitalises identifiers. Under smart-case, Request and request are different queries, and the agent does not know which one it typed. Ferret’s rule, already in the grammar comment, is that a query means the same whatever letters it is typed in. case:text:Foo and, once D67 lands, case:grep: are the explicit sensitive forms. The tradeoff is that case:yes does not work, which is item 5 above. Document case: as a prefix in the same breath as text:. Do not add case:yes as a query-wide toggle: two case mechanisms is how Zoekt’s case: and ferret’s case: get confused with each other. ferret grep should stay ripgrep-shaped, sensitive by default, with -i and -S. The two verbs should not converge.

ext:, the glob, and the leading / anchor.

Keep them. ext: is Recoll’s field and Everything’s function. The glob matches GitHub’s path: rules closely enough that an agent who writes src/**/*.rs or /home/*/x gets the same shape: * does not cross /, ** does, a leading / anchors. Everything’s wildcard matches the whole filename once a wildcard is present, which ferret’s no-slash glob also does (*.rs is the whole name). The difference to teach is Everything’s ext:cpp;h;cs list, which ferret does not have; ext:rs OR ext:toml is the spelling.
