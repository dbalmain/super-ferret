# S3 — Regex

M0 design, 2026-10-07. Code baseline: `e5f1283` on `wt/s2` (S2 closed after its
four Astra rounds). This is a design for review, not yet a build specification.
The new questions are D67–D69 in [§ Open questions](#open-questions), drafted
here for Dave to land in DECISIONS.md; each section names the brief it depends
on.

The shape in one paragraph. A regex atom (`grep:REGEX`, D67) is parsed once by
`regex-syntax`, and `ferret-query` folds its HIR into a Cox **trigram query**:
an AND/OR tree of 3-byte keys that every match must satisfy. The keys come from
a new structure, **trigram postings**, which is S2's segment format reused
unchanged with 3-byte ASCII-folded keys instead of tokens. Each follow pass
writes a trigram file beside each term segment, over the same DocId range, named
by the same manifest entry, merged by the same policy. On the seam this is one
new `Source` variant and two `match` arms; trigram lists come back as S2's own
`Candidates::Postings`, so no new cursor exists. A regex candidate is always
Maybe, and the `regex` crate verifies it (D17 A). The sprint opens with the
experiment D65 asked for: whether S2's singleton terms can leave the term
dictionary once trigrams exist. That experiment gains a second arm that needs no
trigrams at all.

**Where S3 should start.** With the measurement every later choice depends on,
as S2 did with its census. Trigram postings cost an unmeasured number of bytes:
the estimate below spans 2.9% to 25% of text, and its centre is 8.3%. That is
about as large as the whole S2 index, so it decides D65, D68 and D69 before any
planner code exists. M1 builds trigram segments offline with S2's writer and
measures them. M2 runs D65's experiment on them. Only then does the regex
surface get built.

## Regex to trigram query

### The derivation on `regex-syntax` HIR

The query compiler parses the pattern with `regex_syntax::ParserBuilder`, using
exactly the flags the verifier's `regex` will use (D67: case-insensitive by
default, multi-line). It then folds Cox's five facts bottom-up over the
resulting `Hir`. The two parses agree because `regex` uses the same
`regex-syntax` internally; `Cargo.lock` unifies both at 0.8.11. A property test,
not that argument, is what holds them together
([§ Tests for the derivation](#tests-for-the-derivation)).

Per node, the fold computes Cox's facts. The rules are the course's
([part 4](research/grok/cox-trigrams/part4.html)), from Cox's 2012 article:

| Fact        | Meaning                                                                                   |
| ----------- | ----------------------------------------------------------------------------------------- |
| `emptyable` | the node matches the empty string                                                         |
| `exact`     | the finite set of byte strings it matches, or unknown                                     |
| `prefix`    | when `exact` is unknown: a set every match starts with one of                             |
| `suffix`    | likewise for how a match ends                                                             |
| `match`     | a boolean over trigrams, `All` / `None` / `And` / `Or` / key; necessary, never sufficient |

The facts work over **bytes**, the UTF-8 the documents hold, and every literal
is ASCII-folded before it becomes a key
([§ Case and Unicode](#case-and-unicode)). `regex-syntax` 0.8's HIR has seven
kinds of node, and each maps to Cox's rules:

| `HirKind`                    | Rule                                                                                                                                                                                                                                                                                                                                                                                  |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Empty`                      | `exact {""}`, `match All`                                                                                                                                                                                                                                                                                                                                                             |
| `Literal(bytes)`             | `exact {fold(bytes)}`. A literal is already UTF-8 bytes in the HIR.                                                                                                                                                                                                                                                                                                                   |
| `Class` (Unicode or bytes)   | Its members are first folded and deduplicated, so `[Aa]` becomes `{a}`. With at most **4** distinct encodings left, `exact` is their UTF-8 set. With more, the class is an unknown character, so `prefix {""}`, `suffix {""}` and `match All`. That is sound because it only loses constraints. Code uses `[A-Z_]`-style classes often, so the cap is checked against M3's query set. |
| `Look` (`^`, `$`, `\b`, …)   | `exact {""}`, `match All`. An assertion consumes no bytes; the verifier checks it.                                                                                                                                                                                                                                                                                                    |
| `Repetition {min, max, sub}` | `min = 0` and `max = 1` is `sub \| ""` by the alternation rule; the course warns that the `*` shortcut there "costs you the whole index". `min = 0` otherwise gives `match All`, with everything unknown. `min ≥ 1` keeps `sub`'s `match`, and `sub`'s exact set becomes the prefix and suffix. Exact counts (`a{3}`) unroll as concatenation while the result stays under the caps.  |
| `Capture`                    | transparent: the child's facts                                                                                                                                                                                                                                                                                                                                                        |
| `Concat`                     | Cartesian product of the exact sets while both are known. Otherwise `And`, plus the trigrams of `suffix(e1) × prefix(e2)` that span the boundary, which neither child owns: Cox's subtle rule, and the one the course's `ab?cef` fixture pins.                                                                                                                                        |
| `Alternation`                | Union of the exact sets; `match` is `Or`.                                                                                                                                                                                                                                                                                                                                             |

Simplification follows Cox's order: **save before you discard**. Before an exact
set is shrunk, its trigrams are ANDed into `match`. The limits:

- an exact set of more than **7** strings, or whose shortest string is longer
  than 4 bytes, is dumped into `match`;
- a prefix or suffix set of more than **20** strings is shortened character by
  character until it fits;
- `All AND q = q`, `None OR q = q`, `All OR q = All`, `None AND q = None`;
- a finished query with more than **64** distinct keys keeps the 64 that are
  cheapest to drop, which means dropping whole `Or` branches (each becomes
  `All`). Dropping a constraint is always sound.

The first two limits are Cox's own (`maxExact` 7, `maxSet` 20). The others are
starting points that M3 measures.

The result is the plain tree below, independent of any index:

```rust
/// What every match of a regex must contain: necessary, never sufficient.
pub enum Trigrams {
    All,                       // no constraint: every document is a candidate
    None,                      // no document can match (e.g. `[^\x00-\u{10FFFF}]`)
    Key([u8; 3]),              // ASCII-folded
    And(Vec<Trigrams>),
    Or(Vec<Trigrams>),
}
```

It lives in `ferret-query` (new module `regex.rs`), because deriving a trigram
query is planning. The key function itself (fold, then three bytes) lives in
`ferret-index`, which also uses it to index documents. One function on both
sides means the folding rule cannot drift.

#### Tests for the derivation

- **Soundness, by property.** For random patterns drawn from a grammar
  (literals, classes, `.`, `?`/`*`/`+`/`{m,n}`, alternation, anchors, `(?i)`)
  and random haystacks built to contain matches, every haystack the `regex`
  crate matches must satisfy the derived query, evaluated against the haystack's
  own folded trigram set. This is the course's "never drop a hit" invariant,
  checked against the real verifier rather than a re-implementation of it
  (agent-playbook: a test that re-implements the rule is not a test).
- **Precision, pinned.** The course's `index.json` cases become unit tests, with
  their exact expected queries: `Search`, `Google.*Search`, `ab[cd]e`, `a*`,
  `ab?cef` (`"ace" OR ("abc" AND "bce")`, the discriminating case for the `?`
  rule), and `banana` against a corpus that lacks it. Add `(?i)k` (it must keep
  the Kelvin sign's bytes) and `[A-Z_]+Error` (the class cap).
- **Folding agreement.** For every byte string, the key the query side produces
  equals the one the index side produces.

### Case and Unicode

**The index folds ASCII case in its keys, and only ASCII.** A key is three raw
document bytes with `A–Z` mapped to `a–z`. Bytes at or above 0x80 are kept as
they are, so a key never needs decoding and invalid UTF-8 costs nothing.

The derivation is then sound for both of D67's case modes:

- **Case-insensitive (the default).** `regex-syntax` under `(?i)` already
  expands each letter to its case class using Unicode simple case folding: `k`
  becomes `[Kk\u{212A}]`, `s` becomes `[Ssſ]`, `é` becomes `[Éé]`. Folding the
  class's encodings collapses the ASCII members to one, and the non-ASCII
  members stay as separate strings in the exact set. So `(?i)kelvin` derives
  `"kel" AND …`, OR'd with the Kelvin sign's 3-byte sequence. That is exact to
  what `regex` will match, with no table of our own. This is why the derivation
  works on the HIR rather than on the pattern text.
- **Case-sensitive (`case:`).** The literal is folded before its keys are
  formed. The keys are weaker than case-exact ones would be, still sound, and
  the verifier checks exact case.

Folding is the fastest and the simplest choice for the default mode, which is
case-insensitive like `text:` and `re:`. Unfolded keys would expand every ASCII
letter of a query trigram into 2–8 keys, ORed. It is also the densest choice.
`Foo` and `foo` in one document share one posting, and the key space shrinks
from 95³ to 69³ printable-ASCII combinations, which is 328,509 against 857,375
(derived). The only loss is precision on `case:` queries, and verification
settles that anyway. This is settled without a brief.

**The tokenizer is not involved.** S2's `text:` meaning goes through
`ferret-text` (lowercasing with `str::to_lowercase`, and runs and parts). A
regex means what the `regex` crate says over the document's bytes. So
`grep:HttpRequest` and `text:HttpRequest` are different questions: the first is
a substring (`xHttpRequestx` matches, `http_request` does not), and the second
is a token or part sequence. The difference is deliberate. A regex user expects
grep semantics, and the D9 splitting rules have no regex spelling. Folding
differences such as `İ` follow from that and need no special case: `text:`
follows the tokenizer, `grep:` follows Unicode simple case folding.

### When a regex yields no usable trigrams

A pattern whose query is `All`, such as `grep:a.b`, `grep:\d+`, `grep:x*` or
anything under three bytes, gives no index narrowing. There are three choices:

- **Scan:** verify every live document. On `$HOME` that reads about 4.0 GB of
  text. M4b's page-cache read rate puts that near 0.4 s of reading plus a regex
  pass. Cold, D8 recorded a full-tree scan at 234 s.
- **Refuse:** a typed `RegexUnindexed { live }` error, unless the caller passes
  `--scan`. This is the precedent S2 set with `IndexIncomplete`.
- **Bound:** treat the atom as `Maybe` for every live document and let the rest
  of the query narrow it.

All three are needed, at different times. The atom compiles to `Maybe(live)`,
which is the Bound behaviour, and its estimate is `live`. If another conjunct
drives, for example `ext:rs grep:\d+` or `text:serde grep:v\d+`, the regex
simply filters that driver's candidates. The query is refused only when the
planner's chosen driver is such an atom, so that the whole query would verify
every live document. `--scan` overrides the refusal, and `IndexIncomplete`'s
`--scan-uncovered` becomes an alias of it.

A weak but not empty query, such as one common trigram, is not refused. It costs
what a broad phrase costs (§ Bench plan measures the class). This is settled
without a brief: it reuses S2's refusal shape, and the alternatives are either a
silent 4 GB read or refusing queries that other atoms make cheap.

## Candidate structures

### Trigram postings

**Layout: S2's segment format, unchanged, with 3-byte keys.** A trigram file is
a segment file in every respect: the head, front-coded dictionary blocks with
singletons inlined (dictionary codec 1), `pfor128skip` doc-id lists (postings
codec 1), the resident block index, and the 4 KiB chunk sums. The only
differences:

- a key is a folded trigram, not a token;
- the head's tokenizer-version field holds a **key-extractor id** of its own
  (`TRIGRAM_VERSION`, starting at `0x7472_0001`), so a change to the folding
  rule rebuilds through coverage, as a tokenizer change does.

Writing goes through the existing `segment::Writer`. Reading goes through the
existing `Segment::entry` / `read` and `postings::Term::read_until`. The
dictionary for 3-byte keys could be a dense 2²⁴ table, but front-coded blocks
already cost only a few bytes per key
([§ Bytes per content byte: estimate](#bytes-per-content-byte-estimate)). A
dense table is new code saving under 1% of text.

**One trigram file per term segment, same range, same manifest entry.**

```text
index/seg-<first>-<last>-<n>.seg    terms (S2)
index/seg-<first>-<last>-<n>.tri    trigrams (S3), same first/last/n
```

The follow pass reads each document once. It feeds S2's `Inverter` with tokens,
and a `TrigramInverter` with the document's distinct folded keys. Both are
drained into one manifest entry, so the structures always cover exactly the same
DocIds. One frontier, one unreadable set and one `uncovered` bitmap serve both,
and `Pinned` needs no per-source coverage. The `.tri` file is written and
fsynced before the manifest that names it, under S2's existing commit protocol.

`TrigramInverter` is the one new build-side type. A document's keys are
deduplicated through a 2²⁴-bit (2 MiB) seen-bitmap, cleared through a
touched-list after each document. Each new key appends the DocId to a
`HashMap<u32, Vec<u32>>`, keyed by the trigram as an integer. DocIds arrive in
ascending order, so there is no sort, as in S2. S2's `Inverter` would also work,
but it budgets about 64 B per distinct key for boxed byte strings, which would
make it flush on key count rather than on postings. That is why this one type is
new.

**Buffer.** A pass flushes both inverters when _either_ reaches its bound,
because they share a range. Trigram pairs outnumber term pairs, by about 5× in
the estimate below (444M against 89.7M). So the trigram bound is sized from M1's
measured pairs-per-content-byte so that S2's 64 MiB term buffer, not the trigram
buffer, sets segment size. Otherwise trigrams would shrink every segment, and a
higher h means more duplicated term dictionary entries, which was S2's main size
cost. Estimate: 444M pairs / 49 build segments ≈ 9M pairs per segment, about 40
MiB of `Vec<u32>` at ~4.5 B per pair.

**Merge.** The streaming merge in `merge.rs` already treats keys as opaque byte
strings, so a pair merges as two runs of that same function over the `.seg` and
`.tri` inputs. Liveness purge, range order, cancellation and the retry rules all
carry over. The policy's level uses the pair's combined file bytes. The
dead-fraction trigger uses the shared `docs` count.

**Build cost (estimate).** Extracting keys is a fold and a bitmap test per byte,
about 1–2 ns per byte. That is 4–8 CPU-s for 4.0 GB, an assumption. Appends cost
444M × ~5–10 ns = 2–4 CPU-s, also an assumption. Encoding costs 444M / 175 Mi/s ≈
2.4 CPU-s, using intpack's measured sorted-encode rate as S2's cost model does. So a first build adds roughly **9–15 CPU-s** to S2's measured 94.0 (M3),
which is +10–16%. Merging at M3's measured write amplification of 3.00 triples
the encode share. M1 measures all of it.

**Query.** The derived tree compiles to S2's existing `And` / `Or` cursors over
each key's `Candidates::Postings`, wrapped in `Maybe`. Before any list is read,
`Source::estimate` gives each key's document frequency from the dictionaries
alone. An `And` then reads only its **4 rarest** children. Every child of an AND
is necessary, so any subset is a sound, weaker filter, and the common keys would
cost the most to read for the least narrowing: an `ion` list at 10M documents
decodes millions of ids (estimate). The 4 is a starting point for M4.

### Per-document trigram filters

A **binary fuse filter** per document over its distinct folded keys (Graf and
Lemire, 2022). With 8-bit fingerprints it costs about 9 bits per key for large
sets, more for small ones, and has a 1/256 false-positive rate per probe. On the
seam it is `Source::DocFilter`, with `enumerable: false` and a
`Probe::DocFilter` arm. It never drives (S2.md § How S3 and the per-document
filters fit): a pure regex would drive from the live bitmap and probe every live
document.

**Its bytes are known without building it.** A filter's size is a function of
its key count, and its key count is exactly a trigram posting. So:

```text
filter bytes ≈ trigram pairs × 9 bits / 8   (more for small documents)
```

At the central estimate below, that is 444M × 9 / 8 ≈ **500 MB**, against
trigram postings of about **333 MB**. Filters come out _larger_ whenever
postings average under 9 bits per pair, and trigram lists are dense: S2's term
lists measured 8.32 (M2), and dense lists fall into pfor128's bitset blocks.

**D8's premise for filters is an arithmetic error.** The research size budget
([architecture § The size budget](research/claude/architecture.html)) priced
filters at "73,510 files × 3,000 keys × 9 bits = 248 Mbit = 31 MB". The product
is 1.98 Gbit, which is **248 MB**: the line divided by 8 twice. D8's "the
cold-cache win at 12% of the trigram tier's cost" rests on that line. At the
research's own inputs, filters cost about the same as its 221 MB of postings.

Per-document filters are also slow to query. A pure regex probes every live
document's filter, about three cache lines per probe. At 10M entries that is
8.13M documents (the fixture's count) × ~1.1 probes (a first No ends the
document) × 3 accesses. At 5–100 ns per access that comes to **0.13–2.7 s warm
per query**, an estimate, before cold reads of every filter's page. Postings
answer the same query with a few list reads.

So filters lose on bytes and on latency, and they are new code: a filter builder
and a probe arm. Their one advantage is that they never merge, only concatenate.
Whether to build them at all, given that ROADMAP lists them, is **D68**.

### Per-document term filters (D6)

The same arithmetic applies to S2's terms, and here the result is different. M1c
measured **89,749,389** (term, document) pairs. As fuse filters:

```text
89,749,389 × 9 bits / 8 = 101 MB     vs S2's merged index 392 MB (M3)
```

That is 3.9× smaller, because a filter stores no term strings, and S2's
dictionary is 74.5–87% of its index. But every `text:` atom would then probe
every live document. A rare term goes from M4b's measured **1.94 ms** warm
median to roughly 0.1–2.7 s at 10M (the estimate above). That is not the
"slightly slower" Dave's density preference allows, so the term filter is costed
in the bench and not built (D68). D65's experiment
([below](#experiment-d65-c-rare-terms-answered-by-trigrams)) chases the same
bytes, the dictionary's singletons, without paying that latency.

`fits` discards it. That costs one re-follow, about 99 s unpaced on `$HOME`
(M3). It is simpler than carrying two kinds of segment, and it is settled.

**Against S2.** The merged term index measured 392 MB (0.098 B/B, M3), so

this back. The proportions are the inverse of S2's. In the trigram file,
postings are about 95% and the dictionary about 5%, because a trigram index has
few distinct keys and long lists.

**Cross-check.** Cox's Linux figure is 18% of source. Ours should come out
lower, because more than half the bytes sit in large files whose keys saturate.
That expectation is an untested guess, and M1 tests it.

## Experiment: D65 C, rare terms answered by trigrams

D65 measured that the term dictionary is 74.5–87% of S2's index, and that
singleton entries (df = 1 in their segment) are 68–81% of the dictionary. They
cost 13.4 B each: long, unshared strings (M2). D65 C keeps them out of the
dictionary and answers them from trigrams. This experiment prices C now that
trigrams exist, and adds two arms that fix C's flaw.

**C's flaw, which the experiment must measure rather than assume away.** Once
singletons leave the dictionary, a term missing from a segment no longer means
"absent". It means "maybe a singleton here". So _every_ term lookup, common ones
included, must run the term's trigram AND over every segment whose dictionary
lacks it, and verify the documents that query proposes. For a short common term
that can be a lot of documents. `text:get` would propose every document holding
`get` as a substring (`target`, `budget`, `getter`) in each segment that lacks
the term itself. The arms:

| Arm         | Term dictionary                                                                                                                               | A term missing from segment s means                                        |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| **Control** | S2 as built, singletons inlined (dictionary codec 1)                                                                                          | No                                                                         |
| **C**       | singletons dropped (D65 C as written)                                                                                                         | Maybe, for s's documents matching the term's trigram AND; verified         |
| **C′**      | singletons dropped, plus per segment a binary fuse filter over the dropped terms' hashes (~9 bits each)                                       | No if the filter says No (255/256 of truly absent lookups); otherwise as C |
| **H**       | singletons moved to a section of `(32-bit fingerprint, DocId)` pairs, sorted by fingerprint and probed by binary search; no trigrams involved | a fingerprint match is Maybe for that one document, verified; a miss is No |

**H is new here.** It answers the same bytes with no coupling to S3. Its
estimate for the fully merged index (M3: 68.3% of 18,441,368 terms are
singletons, so 12.6M):

```text
H entry     ~2 B fingerprint delta (2³² / 12.6M ≈ 341 apart, vbyte)
            + ~3 B DocId offset (vbyte, < 2²¹)                        ≈ 5 B
saving      12.6M × (13.4 − 5) B                                      ≈ 106 MB
index       392 MB → ≈ 286 MB, 0.098 → ≈ 0.072 B/B                   (estimate)
collisions  12.6M / 2³² ≈ 0.3% of lookups verify one extra document
```

A fingerprint section merges as postings do: two inputs sharing a fingerprint
yield a short list, and dead documents drop out. C′'s filters cannot merge
without their keys, so a merged segment would carry its inputs' filters side by
side, one per original range. That is the complexity cost C′ pays and H does
not. H loses prefix ranges for singletons (a future `text:pars*`), which C and
C′ would answer through trigrams.

**Control and corpus.** The isolated `$HOME` catalog of S2 M1c–M4c, copied, and
the index built by M1's bench at `e5f1283` plus trigram files. The control is
S2's term index exactly as built, with trigram files beside it, so every arm's
total includes the trigram bytes that regex needs anyway. Each arm is measured
at **both** M3 states: steady (13 segments) and fully merged (1 segment).
Per-segment singletons differ between the two, and the steady state is what the
daemon lives in.

**Metrics.**

- **Bytes:** the term index plus the trigram files, per content byte, split by
  section.
- **Latency by term class**, warm and evicted, 50 seeded queries per class as in
  M4b, reporting the **median and p90**, with the control re-run in the same session:
  - df = 1;
  - df 2–100;
  - **absent**: real terms mutated by one character and checked absent in the
    control's dictionaries. This is the class C hurts most, and agents produce
    it (typos, a symbol that does not exist yet);
  - mid (df 1k–100k);
  - common (top 50 df).
- **Documents verified per query** and bytes read, per class.
- **Build CPU:** follow plus merge to steady state, and the forced full merge.

**Decision rule.** An arm beats the control if all of these hold:

1. total bytes fall by at least **15%**;
2. warm p90 for df = 1, df 2–100 and absent stays under **20 ms**;
3. warm median for mid and common stays within **1.5×** the control's;
4. build CPU stays within **1.2×**.

Of the arms that beat the control, the smallest wins, and D65 reopens with its
numbers. If none does, D65 A stands.

The thresholds are my judgement of "slightly slower", and Dave can move them.
The cheaper half of the result comes first. H needs no trigrams, so if H passes
on its own, D65 can close even if trigrams are later disabled.

## Experiment: D66 C, a chunk map for large files

D66 measured that phrase verification is dominated by **reading**: the median
query reads 1,254 MiB, and p90 2,273 MiB (M4c). Of that, 53% of the tree's bytes
are in files of 1 MiB or more. D66 C records, for each (term, large document),
which fixed-size **chunks** contain the term. Verification then reads only those
chunks, through `pread`, instead of the whole file.

**Soundness.** The design keeps M4c's windowed matcher as it is and changes only
where bytes come from:

1. A term is in chunk c when the byte span of a run emitting it overlaps c, so a
   run straddling a boundary marks both chunks.
2. Every phrase match contains its anchor unit's token, so it overlaps some
   chunk marked for the anchor. Only the anchor's chunks are read. Other units'
   chunk maps are **not** ANDed in: M4c's windows span any amount of separator,
   so a match's other units can lie any number of chunks away.
3. Within a read chunk, the matcher finds anchor occurrences and builds M4c's
   windows. A window that reaches a chunk edge fetches further bytes on demand
   until it reaches an ASCII separator or the document edge. M4c's points 2 and
   3 then hold unchanged, because the window's bytes are the document's own.

So a chunked answer equals M4c's whole-document answer. Fetching lazily makes
that true without bounding how far a window can reach. A property test holds the
two equal, as M4c's does.

**Layout.** This is a third file per segment pair, or a section of the term
segment: per (term, large document), a bitmap with one bit per chunk. That is at
most 8 MiB / chunk size bits, given the 8 MiB policy cap: 8 bits at 1 MiB
chunks, 128 bits at 64 KiB. The bitmaps are ordered as the term's postings, for
large documents only, so they can be found by rank in the list.

**Bytes (estimate, not measured).** Assume large documents hold 20–35M of M1c's
89.7M term pairs, a guess because `jsonl` alone has 6.3M distinct terms in 1,987
documents (M1c). Then:

| Chunk   | Per pair | Map bytes | vs 392 MB merged index |
| ------- | -------- | --------- | ---------------------- |
| 1 MiB   | 1 B      | 20–35 MB  | +5–9%                  |
| 256 KiB | ~1.5–4 B | 30–140 MB | +8–36%                 |
| 64 KiB  | ~2–16 B  | 40–560 MB | +10–140%               |

**The benefit can be measured without building anything.** For each of M4c's 50
phrase queries, a bench pass tokenizes each candidate large document in chunks
and counts the bytes the chunk map would have read: the anchor's chunks plus the
lazy extensions. The same pass counts the (term, document, chunk) pairs that
size the map. So M5's first step is a census, at all three chunk sizes, with the
same seeds as M4b and M4c.

**Control.** M4c's whole-file windowed verification: same catalog copy, same 50
phrases, same seeds, warm and evicted.

**Decision rule.** Build the chunk map at the cheapest chunk size, measured,
that cuts **p90 bytes read by at least 50%** for **at most 10%** more index
bytes. If no size does, close D66 C and leave D66 to A or B.

A trigram chunk map, the same idea keyed by trigram so that regex verification
could read chunks, would need far more pairs. A 64 KiB chunk holds thousands of
distinct trigrams, so the map would exceed the trigram postings (estimate). The
census counts it at 1 MiB only, as a single row. Regex does not need it the way
phrases do: the `regex` crate's literal prefilter scans at GB/s, so for regex
the cost is reading, and § Verification covers when windows are sound.

## Verification

**Where it sits.** `ferret-verify` gains `Grep`, beside `Text`. It holds the
pattern, the flags and a compiled `regex::bytes::Regex` behind the `Matcher`
trait, and `find` returns the first match's byte span for the JSON row's offset.
`plan.rs` evaluates every content atom of a Maybe row against one bracketed read
of current bytes, as it does for `text:`: the freshness contract, document-fact
caching, changed-path rules and the policy size cap all apply unchanged (S2.md §
Coverage). `MatchStats` gains regex counters: bytes scanned, and documents
rejected by the regex's own prefilter.

**D17's "regex crate until S3".** S3 keeps D17 A. The deciding number D17 named
is verification's share of end-to-end regex latency, and M4 measures it per
query class. The rule: if verification is more than half of p90 wall-clock _and_
the regex engine (not reading) is more than half of verification, an own engine
could win something and D17 reopens. Otherwise A stands with a number behind it.
M4c already suggests the outcome. Reading took 126 ms of 715 at the median, and
the two whole-document regex passes took the remaining ~400 ms over 1.25 GB
(S2 derived it, not split). That is the `regex` crate scanning about 6 GB/s per
pass (derived), which an own engine would have to beat.

The new direct dependencies are `ferret-query → regex-syntax` (the HIR for the
derivation) and `ferret-verify → regex-automata` (windows, below). Both crates
are already in `Cargo.lock` as `regex`'s own dependencies (0.8.11 and 0.4.18),
so the build gains no crate. DESIGN's graph block changes in the same commit.

**Windowed verification for regex: sound only for bounded matches, and only
worth it with a chunk map.**

A window search is sound for a regex R and anchor set A under four conditions:

1. The derived query's top level gives a set A of keys such that every match
   contains at least one of them. An `And` gives one such set per child, and the
   rarest is taken.
2. R's longest match is finite: `regex-syntax`'s `Properties::maximum_len()` is
   `Some(L)`.
3. Each anchor occurrence at byte p gets the window `[p − (L − 3), p + L)`,
   clipped to the document. Every match containing that occurrence lies inside
   it, because a match is at most L bytes and contains the anchor's 3 bytes.
4. Look-around sees the whole document. The search runs over the document with
   `regex_automata::Input::span(window)`. Its documentation says the span limits
   where a match may be while look-around may consult bytes outside it, so `^`,
   `$` and `\b` at a window edge answer as they would in the whole document.

Then the first match over the merged windows, taken in document order, is the
document's first match. Each match contains an anchor, so it lies in some
window, and no window holds a match that the document lacks.

Without condition 2, as for `foo.*bar` with `.*` crossing lines under `(?s)`, a
window has no bound, and the whole document is searched. M4c's phrase windows
had no such limit because a phrase's span is bounded by runs and separators that
the matcher walks; a regex's span is not.

The rule, settled:

- Without a chunk map, verify **whole documents**. The bytes are in memory
  anyway, and the `regex` crate's own prefilter already skips at memchr speed,
  so windows would save nothing measurable.
- With D66 C's chunk map (or a future trigram chunk map), windows decide which
  bytes to `pread`, and only regexes with `maximum_len ≤ chunk size` use them.
  Any other regex reads whole.

## Query surface (D67)

D67 below is the brief. Its recommendation, used throughout this document:

```text
atom   = ... (S1's and S2's atoms) | "grep:" REGEX | "case:grep:" REGEX
```

- `grep:REGEX` is a content atom. It is the `regex` crate's syntax, over the
  document's bytes, case-insensitive by default, with `^` and `$` matching at
  line boundaries (multi-line) and `.` not matching `\n`. `case:grep:` makes it
  case-sensitive, as `case:` does for every other atom.
- It composes like `text:`: adjacent atoms AND, and `OR`, `NOT` and parentheses
  work as D62 A spells them.
  - `ferret search ext:rs grep:'fn \w+_test'`: the name side drives, and the
    regex filters its documents.
  - `text:serde grep:'derive\(.*Serialize'`: term postings drive, and trigram
    postings narrow further.
  - `NOT grep:x`: the live bitmap drives.
- `re:` keeps its S1 meaning, a regex over **names**. Repurposing it would
  silently change every existing `re:` query, which is D62's argument against B,
  applied again.

**Certainty.** A `grep:` atom is never Yes from the index. A trigram query is
necessary, not sufficient (the course's `Seaearch`). So the index answers **No**
for a document outside the trigram query, and **Maybe** for one inside it, and
Maybe goes to the verifier. Under NOT, Kleene's table gives `NOT No = Yes`,
which needs no read, and `NOT Maybe = Maybe`, which does. A trigram query of
exactly one key could be exact for some ASCII literals, but Unicode folding
(`k`, `s`) makes the rule fiddly, and a 3-byte regex is rare. It is not
special-cased.

`explain()` prints the derived trigram query, the keys actually read (the 4
rarest), each key's df and the candidate count. The query log records them, so
M4's query set and S4's agent traces show which patterns degrade to `All`.

## Cost model at 10M

S2's convention holds. The content volume at 10M is unknown, so sizes are given
per row of indexed text. The 10M fixture has no text (S2 M3).

| Item                                | Estimate                                          | Arithmetic                                                |
| ----------------------------------- | ------------------------------------------------- | --------------------------------------------------------- |
| Trigram files on disk               | 8.7% of text (2.9–25%)                            | § Bytes per content byte                                  |
| At 10 / 30 / 100 GB of text         | 0.87 / 2.6 / 8.7 GB                               | × 0.087                                                   |
| Term index, measured ratio          | 9.8–11.1% of text                                 | S2 M3, full merge and steady state                        |
| Combined                            | ~19% of text before D65; ~16% if H's saving holds | 0.098 + 0.087; then − 0.026 (H, estimate)                 |
| Resident: trigram block indexes     | ~0.2–1 MB per segment                             | 1–4M keys / 32 per block × ~6 B                           |
| Resident: seen-bitmap during follow | 2 MiB                                             | 2²⁴ bits                                                  |
| Follow buffer, trigrams             | ~40 MiB                                           | 9M pairs per segment × ~4.5 B                             |
| Build CPU, trigrams                 | +10–16% over S2's                                 | 9–15 CPU-s per 4 GB; § Trigram postings                   |
| Rare-literal regex, warm            | low ms                                            | ≤ 4 keys × ~50 segments of block reads, as S2's rare term |

Trigrams scale with text more steeply than terms. The term dictionary grows
sublinearly (Heaps), while trigram keys are capped at 2²⁴, so beyond the first
few GB trigram bytes grow with pairs alone, roughly linearly in text. At 100 GB
the trigram files could be the larger half of the index. That is D69's
territory.

## Settled here without a brief (object if wrong)

- Trigram keys are raw document bytes, ASCII-folded and nothing else.
- The derivation works on `regex-syntax`'s HIR with the verifier's flags, with

## Rejected alternatives

| Alternative                                                      | Why not                                                                                                                                                                                           |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| An independent trigram index with its own manifest and follow    | It reads every document twice, and needs per-source coverage in `Pinned`. A pair under one entry gets the same answer with neither.                                                               |
| Trigram sections inside the term segment file                    | That needs a second dictionary in the reader and writer. A sibling file reuses both untouched, and the bench can drop it to get a control.                                                        |
| Unfolded (case-exact) keys                                       | Default queries are case-insensitive, so each letter would expand to 2–8 ORed keys per trigram, with more pairs on disk. Only `case:` precision is lost by folding, and the verifier restores it. |
| Rune (code-point) trigrams, as Zoekt's design describes          | They need decoding at index time and have no answer for invalid UTF-8. Byte trigrams are sound for UTF-8 regexes because the HIR is already bytes.                                                |
| Positional trigrams (Zoekt-style)                                | Positions were declined in D6/D7, and they would multiply the largest new structure.                                                                                                              |
| Pulling literals with `regex-syntax`'s `hir::literal::Extractor` | It extracts prefix and suffix literal sets, not a boolean over inner trigrams, so it loses Cox's AND across `.*`. Building the fold is also the point (build, not adopt).                         |
| Per-block filters over many documents (VictoriaLogs-style)       | They are a middle ground between per-document filters and postings, and a third structure. Revisit only if D68's numbers put filters within 2× of postings.                                       |
| `re:` meaning content                                            | It would change S1's name-regex queries silently (D67).                                                                                                                                           |

### D67 — How `ferret search` spells a content regex

**Status: open.** S3 M0, 2026-10-07; [design](S3.md#query-surface-d67).

**Question:** What prefix makes an argument a regex over file content, and what
line and case semantics does it have?

`re:` already means a regex over **names** (S1). D62 A gave content `text:`.
DESIGN's query section sketched `/regex/`. Agents call `ferret search` from
shells, so quoting cost matters.

| Option                                               | Costs                                                                                                                                                              | Buys                                                                                                                      |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| A. `grep:REGEX`                                      | One more prefix to learn.                                                                                                                                          | It reads as what it does, and agents know grep. `case:grep:` composes as `case:` does elsewhere. `re:` keeps its meaning. |
| B. `text:/REGEX/`                                    | It changes `text:`'s meaning for an argument that starts and ends with `/`, which today is a term (`text:/usr/` finds `usr`). A regex containing `/` needs a rule. | No new prefix: `text:` covers all content.                                                                                |
| C. Bare `/REGEX/`, as DESIGN sketched                | `/` already makes a bare word a path substring (S1), so `/usr/` changes meaning.                                                                                   | The shortest spelling.                                                                                                    |
| D. `re:` searches content as well as names (a union) | It changes every existing `re:` query's meaning and cost (D62's argument against its B).                                                                           | One regex prefix.                                                                                                         |

Semantics, under any option:

- **case-insensitive by default**, as `text:` and `re:` are, with `case:` for
  exact case;
- **multi-line**: `^` and `$` match at line boundaries, as grep users expect.
  `(?-m)` restores whole-document anchors;
- `.` does not match `\n` (the `regex` default).

The alternative is the `regex` defaults: whole-document `^`/`$`. Those are
surprising for content, though right for names.

**Recommendation: A, with multi-line on.** Fastest and simplest are indifferent;
this is interface taste and compatibility, as D62 was.

**Fact that would change it:** S4's agent traces showing agents reaching for
`/…/` or for `re:` on content. Then make B or D the spelling, with the old one
as an alias.

### D68 — Per-document filters: build them, or cost them on paper

**Status: open.** S3 M0, 2026-10-07;
[design](S3.md#per-document-trigram-filters).

**Question:** ROADMAP says S3 builds per-document trigram filters beside trigram
postings, and benches per-document term filters against postings (D6, D8).
Should both filters be built and benched, or priced from exact key counts and a
microbenchmark, with only postings built?

A binary fuse filter's size is determined by its key count, and each key is
exactly one posting. So filter bytes are `pairs × ~9 bits / 8`, plus overhead
for small documents. Figures are **estimates** unless marked:

- **Trigrams:** about 500 MB of filters against about 333 MB of postings at the
  central estimate. Filters are smaller only if postings average more than 9
  bits per pair; term lists measured 8.32 (M2), and trigram lists are denser.
- **Terms:** 89.7M pairs (**measured**, M1c) give 101 MB of filters against S2's
  392 MB merged index (**measured**, M3), so 3.9× smaller.
- **Latency:** either filter makes every query probe every live document. At 10M
  that is about 0.13–2.7 s warm, against a rare term's measured 1.94 ms warm
  median (M4b).
- **D8's premise** that filters cost 12% of postings is an arithmetic error in
  the research budget: 248 Mbit should have been 248 MB.

| Option                                                                                                                                           | Costs                                                                                                                                                 | Buys                                                                                     |
| ------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| A. Build both filters and bench them, as ROADMAP says                                                                                            | A filter builder, a `Probe::DocFilter` arm, filter merging, and their tests: about one slice of work for structures the arithmetic already rules out. | Measured rather than computed numbers; D6's experiment as written.                       |
| B. Compute filter bytes from M1's exact per-document key counts; microbench the probe over synthetic filters of those sizes; build postings only | The numbers are a calculation plus a microbenchmark, not a shipped structure, so the cold page-cache behaviour of real filter files is not measured.  | A slice saved. D6/D8 still get an answer with numbers: bytes exact, probe cost measured. |
| C. Build the term filter only, as a density option behind the opt-in                                                                             | A second term structure to keep correct, and rare-term queries 100–1000× slower when it is chosen.                                                    | The smallest term index by far, for users who value bytes over everything.               |

**Recommendation: B.** Fastest and simplest agree: postings are smaller or
equal, faster by orders of magnitude, and already built.

**Fact that would change it:** M1 measuring trigram postings above 9 bits per
pair (filters would then be smaller, so A for trigrams), or Dave wanting C's
density option, accepting second-scale term queries at 10M.

### D69 — Saturated large documents in trigram postings

**Status: open.** S3 M0, 2026-10-07;
[design](S3.md#bytes-per-content-byte-estimate).

**Question:** Large documents hold most of the bytes and nearly every common
trigram. Should their trigrams be indexed like any document's, or should a
document past a key-count line be marked "Maybe for every trigram" and skip
trigram postings?

Figures are **estimates** until M1. 53% of `$HOME`'s text is in files of 1 MiB
or more (**measured**, S2 M1), perhaps 800 files. At about 200k distinct keys
each, they contribute about 160M of an estimated 444M trigram pairs, roughly 120
MB of the trigram files. A selective regex likely excludes most of them, but a
common one includes them all.

| Option                                                                                                                       | Costs                                                                                                                                                                                                   | Buys                                               |
| ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| A. Index every document's trigrams                                                                                           | The full ~350 MB, about 36% of it from large documents. Bytes grow with text past a few GB, since keys saturate and pairs do not.                                                                       | Every regex narrows over every document. One rule. |
| B. Past a line (say 64k distinct keys), store the document in a per-segment "saturated" bitmap, Maybe for every trigram atom | Every regex query verifies every saturated document, about 800 files and 2.1 GB on `$HOME`. That is roughly the broad-phrase cost, 0.2–0.3 s of reading warm (M4c), on _every_ regex, and minutes cold. | Up to about a third of trigram bytes saved.        |
| C. A, plus D66 C's chunk map for regex as well, keyed by trigram at 1 MiB                                                    | The largest structure of the three (estimate: more pairs than the trigram postings themselves).                                                                                                         | Large documents both narrowed and partly read.     |

**Recommendation: A.** Fastest, and the simplest. B is denser but makes every
regex pay the cost the phrase work just removed, so the two disagree and this is
a brief. C is costed only by M5's single census row.

**Fact that would change it:** M1 measuring large-document pairs above about
half of all trigram pairs, _and_ M4 measuring verification of saturated
documents under 100 ms warm. Then B's cost is small enough to buy its bytes.
