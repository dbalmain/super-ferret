# S3 — Regex

M0 design, revision 3, 2026-10-08. Code baseline: `e5f1283` on `wt/s2`, the
point at which S2 closed after its four Astra rounds. This is a design for
review, not yet a build specification. Revisions 2 and 3 answer Astra's first
and second reviews (`.ai/s3-astra/note-01.md`, `note-02.md`);
[§ Revisions](#revisions-what-changed) lists what changed. The new questions are D67–D70, and an amendment to D65, all in
[§ Open questions](#open-questions). They are drafted here for Dave to land in
DECISIONS.md, and each section names the brief it depends on.

The shape in one paragraph:

- **Derivation.** A content-regex atom (`grep:REGEX`, D67) is parsed once by
  `regex-syntax` inside `ferret-verify`, with the same flags as the verifier.
  Its HIR is folded into a Cox **trigram query**: an AND/OR tree of 3-byte keys
  that every match must contain.
- **Storage.** The keys come from a new structure, **trigram postings**. It
  reuses S2's segment container and codecs, with 3-byte ASCII-folded keys in
  place of tokens.
- **Pairing.** Each follow pass and each merge writes a trigram file beside
  each term segment, over the same DocId range, and publishes the pair through
  one manifest entry. That pairing is new storage code, and
  [§ Paired segments](#paired-segments) specifies it.
- **Query.** On the seam, trigram lists come back as S2's own
  `Candidates::Postings`, so no new cursor exists.
- **Verification.** A regex candidate is always Maybe. The `regex` crate (D17 A)
  verifies it, reading the whole document.
- **Experiments.** D65's experiment runs as a new arm, H: hashed singletons,
  sound with or without trigrams. D66's chunk map is reduced to a measured
  census.

**Where S3 should start: the measurement every later choice depends on**, as S2
began with its census. The cost of trigram postings is unmeasured. The estimate
below has a central value of 8.8% of text and an envelope of 2.7% to 36.9%. At
the centre that is close to the whole merged S2 index, so it shapes D68, D69 and
D70 before any planner code exists. So M1a builds trigram segments offline and
measures them, beside the term index, under both of D70's memory policies. The
regex-driven screening (D68's workloads, D69's saturation sweep) is M1b, after
M3 supplies the derivation it needs. Only then is the regex surface built.

## Regex to trigram query

### Where the derivation lives

The derivation lives in **`ferret-verify`**, as a new module `trigram.rs`.
`ferret-verify` is already the one crate that knows regex syntax (DESIGN
§ Crates), and the derivation must parse with exactly the flags its verifier
compiles with. Keeping both in one crate lets one `Flags` value build both:

```rust
/// The one place a content regex's flags are set (D67).
pub struct GrepFlags {
    pub case_insensitive: bool, // default true; false under `case:`
}

impl GrepFlags {
    fn parser(&self) -> regex_syntax::ParserBuilder;    // for the derivation
    fn regex(&self, pattern: &str) -> regex::bytes::RegexBuilder; // for the verifier
}
```

Both builders get the same explicit settings:

| Setting                 | Value                 | Why                                                                                                                                                                  |
| ----------------------- | --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `utf8`                  | **false** (parser)    | `regex::bytes` permits patterns that match invalid UTF-8, such as `(?-u:\xFF)`. `ParserBuilder`'s default is UTF-8-only translation, which would reject such patterns, so the derivation must turn it off to accept every pattern the verifier accepts. |
| `unicode`               | true                  | the `regex` default; `(?-u)` inside a pattern still turns it off locally                                                                                             |
| `case_insensitive`      | per `GrepFlags`       | D67: insensitive by default                                                                                                                                          |
| `multi_line`            | true                  | D67: `^`/`$` at line boundaries                                                                                                                                      |
| `dot_matches_new_line`  | false                 | the `regex` default                                                                                                                                                  |
| `crlf`                  | false                 | the `regex` default                                                                                                                                                  |
| `swap_greed`, `ignore_whitespace`, `octal` | false | the `regex` defaults                                                                                                                                         |
| nest limit              | the `regex` default   | the verifier's and the derivation's parses must fail the same way                                                                                                    |

`regex` is built on `regex-syntax`, and `Cargo.lock` resolves both to one
`regex-syntax` 0.8.11, so the two parses see the same HIR: same syntax
defaults, nest limit 250, and `regex::bytes` already translating with
`utf8(false)`.

**Syntax and compilation are different gates.** Parsing accepts a pattern;
compiling it can still fail on resources. `RegexBuilder` caps the compiled
program (`size_limit`, 10 MiB by default), so a compact pattern such as
`a{100000000}` parses and then fails to compile. So the order at query time is:

1. Compile the verifier's `Regex` through `GrepFlags::regex`. A syntax error or
   a size-limit error is the user's answer (`RunError::Pattern`), and nothing
   else runs. The verifier alone decides whether a regex is executable.
2. Parse the same pattern with `GrepFlags::parser` and derive its trigrams.
   This must succeed for every pattern that compiled, since compilation
   includes this parse. A failure here is a bug, reported as such, never a
   silent `All`.

The tests check that implication, not equivalence: for every pattern in the
property grammar that the verifier compiles, the derivation parses it and the
soundness property holds. Patterns that parse but exceed the compile limit
are a pinned case (`a{100000000}`): refused at step 1, never derived.

The new edge is `ferret-verify → regex-syntax`. The crate is already in
`Cargo.lock` as a dependency of `regex`, so the build gains no crate. DESIGN's
graph line changes in the same commit. `ferret-query` gains no regex
dependency: it receives the finished `Trigrams` tree and compiles it into
cursors.

**The key function lives in `ferret-text`**, beside `TOKENIZER_VERSION`.
`ferret-text` is what decides "what a token is", and a trigram key is the
trigram index's token. Both `ferret-index` (indexing) and `ferret-verify`
(derivation) already depend on `ferret-text`, so one function serves both
sides and the folding rule cannot drift between them:

```rust
pub const TRIGRAM_VERSION: u32 = 0x7472_0001;
/// ASCII A–Z to a–z; every other byte unchanged.
pub fn trigram_key(bytes: [u8; 3]) -> [u8; 3];
```

### The derivation on `regex-syntax` HIR

Per node, the fold computes Cox's five facts, using the rules in the course
([part 4](research/grok/cox-trigrams/part4.html)), from Cox's 2012 article.
Every string in the facts is a **byte string**: a sequence of document bytes,
ASCII-folded by `trigram_key`'s rule before any key is formed.

| Fact        | Meaning                                                                                   |
| ----------- | ----------------------------------------------------------------------------------------- |
| `emptyable` | the node matches the empty string                                                         |
| `exact`     | the finite set of byte strings it matches, or unknown                                     |
| `prefix`    | when `exact` is unknown, a set such that every match starts with one of its members        |
| `suffix`    | likewise, for how every match ends                                                        |
| `match`     | a boolean over trigrams: `All`, `None`, `And`, `Or` or a key. Necessary, never sufficient |

`regex-syntax` 0.8's HIR has seven node kinds. The two class kinds are treated
separately, because they consume different units:

| `HirKind`                          | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Empty`                            | `exact {""}`, `match All`.                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `Literal(bytes)`                   | `exact {fold(bytes)}`. The bytes are used **as they are**. With `utf8(false)` a literal may hold bytes that are not valid UTF-8 (`(?-u:\xFF)`); it matches exactly those bytes, so they are never re-encoded.                                                                                                                                                                                                                                 |
| `Class(Class::Bytes(set))`         | Each member is **one raw byte**: `(?-u:[\x80-\x81])` matches the single byte 0x80 or 0x81, not their UTF-8 encodings. Members are folded and deduplicated. With at most **4** left, `exact` is that set of 1-byte strings. Otherwise the node is an unknown single byte: `exact` unknown, `prefix {""}`, `suffix {""}`, `match All`.                                                                                                          |
| `Class(Class::Unicode(set))`       | Each member is **one scalar value**, matched as its UTF-8 encoding of 1–4 bytes. Members are encoded, folded and deduplicated, so `[Aa]` becomes `{a}`. With at most **4** encodings left, `exact` is that set. Otherwise the node is an unknown character, handled as for bytes. Dropping to unknown is always sound because it only loses constraints. Code-like classes such as `[A-Z_]` fold to 27 members and fall to unknown; M3 measures how often that costs a query its keys. |
| `Look` (`^`, `$`, `\b`, …)         | `exact {""}`, `match All`. An assertion consumes no bytes; the verifier checks it.                                                                                                                                                                                                                                                                                                                                                           |
| `Repetition {min, max, sub}`       | With `min = 0, max = 1`, the node is `sub \| ""` by the alternation rule. The course warns that the `*` shortcut there "costs you the whole index". Any other `min = 0` gives `match All`, with every fact unknown and `emptyable` true. With `min ≥ 1` the node keeps `sub`'s `match`, and `sub`'s exact set becomes its prefix and suffix. Exact counts (`a{3}`) unroll as a concatenation while the result stays under the caps.             |
| `Capture`                          | transparent: the child's facts                                                                                                                                                                                                                                                                                                                                                                                                               |
| `Concat`                           | While both exact sets are known, their Cartesian product. Otherwise `And` of the children's matches, plus the trigrams of `suffix(e1) × prefix(e2)` that span the boundary, which neither child owns. This is Cox's subtle rule, and the one the course's `ab?cef` fixture pins.                                                                                                                                                              |
| `Alternation`                      | Union of the exact sets; `match` is `Or`.                                                                                                                                                                                                                                                                                                                                                                                                    |

**Empty matches.** A pattern that can match the empty string, or any string
shorter than three bytes, must derive `All` at the root. A document with fewer
than three bytes has no trigrams, so the index can never be allowed to exclude
it. The rules above produce `All` here without a special case: an exact set
containing a string under 3 bytes contributes no key when Cox's rule
converts it, so `match` stays `All`. A unit test pins this.

**Simplification** follows Cox's order: **save before you discard**. Before an
exact set is shrunk, its trigrams are ANDed into `match`. The limits:

- An exact set of more than **7** strings, or one whose shortest string is
  longer than 4 bytes, is dumped into `match`.
- A prefix or suffix set of more than **20** strings is shortened, one unit at
  a time, until it fits.
- The identities `All AND q = q`, `None OR q = q`, `All OR q = All` and
  `None AND q = None` apply.
- A finished query with more than **64** distinct keys drops whole `Or`
  branches, turning each into `All`, until it fits. Dropping a constraint is
  always sound.

The first two limits are Cox's own: `maxExact` 7 and `maxSet` 20. The class
cap of 4 and the query cap of 64 are starting points, and M3 measures them.

The result is a plain tree, independent of any index:

```rust
/// What every match of a regex contains: necessary, never sufficient.
pub enum Trigrams {
    All,          // no constraint: every document is a candidate
    None,         // no document can match
    Key([u8; 3]), // folded by ferret_text::trigram_key's rule
    And(Vec<Trigrams>),
    Or(Vec<Trigrams>),
}
```

#### Tests for the derivation

- **Soundness, by property.** Patterns are drawn at random from a grammar:
  literals, Unicode classes, `.`, `?`/`*`/`+`/`{m,n}`, alternation, anchors,
  `(?i)`, **`(?-u)` regions with raw-byte classes and `\xNN` literals ≥ 0x80**.
  Haystacks are built to contain matches, **including invalid UTF-8**. Every
  haystack the verifier's `Regex` matches must satisfy the derived query,
  evaluated against the haystack's own trigram set from `ferret_text::trigram_key`.
  This is the course's "never drop a hit" invariant, checked against the real
  verifier and the real key function, with no copy of either. The case Astra
  named is one of the pinned discriminating cases: `(?-u:[\x80-\x81])ab`
  against the bytes `80 61 62`.
- **Precision, pinned.** The course's `index.json` cases become unit tests with
  their exact expected queries: `Search`, `Google.*Search`, `ab[cd]e`, `a*`,
  `ab?cef`, and `banana` against a corpus that lacks it. `ab?cef` must give
  `"ace" OR ("abc" AND "bce")`; it is the discriminating case for the `?` rule.
  Two more are added:
  - `(?i)kelvin` must give an `Or` that includes the Kelvin sign's encoding
    `E2 84 AA` followed by `el` alongside the ASCII `kel`, and similarly for
    each key containing the letter.
  - `[A-Z_]+Error` must fall to the class cap and keep only `Error`'s keys.
- **Short patterns.** `(?i)k`, `a?`, `\b` and `""` must each give `All`. A
  matching document such as `k` has no trigrams.
- **Agreement.** For every byte triple, `trigram_key` is the only folding
  function used on both sides. This is checked by construction, since there is
  one function, and by a test that indexes a document and queries its own
  literal.

### Case and Unicode

**The index folds ASCII case in its keys, and only ASCII.** A key is three raw
document bytes with `A–Z` mapped to `a–z`. Bytes at or above 0x80 are kept
unchanged, so a key never needs decoding and invalid UTF-8 costs nothing.

The derivation is then sound for both of D67's case modes:

- **Case-insensitive, the default.** Under `(?i)`, `regex-syntax` expands each
  letter into its Unicode simple-case-folding class: `k` becomes `[Kk\u{212A}]`,
  `s` becomes `[Ssſ]`, and `é` becomes `[Éé]`. Encoding and folding that class
  collapses the ASCII members into one string, and keeps the non-ASCII members
  as further strings in the exact set. The derived keys are therefore exactly
  as broad as what `regex` will match, with no case table of our own. This is
  why the derivation works on the HIR rather than on the pattern text.
- **Case-sensitive (`case:`).** Literals are folded before their keys are
  formed. The keys are weaker than case-exact ones would be, but still sound,
  and the verifier checks exact case.

Folding is the fastest choice and the simplest for the default mode, which is
case-insensitive, as `text:` and `re:` are. Unfolded keys would turn every
ASCII letter of a query trigram into 2–8 ORed keys. Folding is also the densest
choice: `Foo` and `foo` in one document share a posting. The only loss is
precision on `case:` queries, which verification restores. This is settled
without a brief.

**The tokenizer is not involved.** S2's `text:` goes through `ferret-text`'s
tokenizer, which lowercases with `str::to_lowercase` and splits text into runs
and parts. A regex means what the `regex` crate says it means over the
document's bytes. So `grep:HttpRequest` and `text:HttpRequest` ask different
questions. The first is a substring search: `xHttpRequestx` matches, and
`http_request` does not. The second is a token or part sequence. The difference
is deliberate: a regex user expects grep semantics, and D9's splitting rules
have no regex spelling.

A trigram key and a token are different representations, so one cannot answer
a query posed in the other. A token such as `kelvin` can come from bytes with
no `kel` trigram, because the Kelvin sign lowercases to `k`. This is why the
D65 C fallback is unsound as written, and why
[§ Experiment: D65](#experiment-d65-rare-terms-without-dictionary-strings)
replaces it.

### When the planned query would read most of the tree

A regex whose query is `All`, such as `grep:a.b`, `grep:\d+`, `grep:x*` or any
pattern shorter than three bytes, gives no index narrowing by itself. Neither
does `NOT grep:x`. That expression is Yes, with no read, for documents outside
x's trigram query, but Maybe for every document inside it, and when x is `All`
that means every live document. The same holds for `grep:\d+ OR text:rare`:
the `OR`'s Maybe set includes the unrestricted branch. The question is not
which atom drives. It is **how many documents the whole planned expression
leaves Maybe**, because each of them becomes a document read.

**Two upper bounds per node.** Before any list is read, the planner computes
two figures for every node, in the **document** domain. Both come from
dictionary statistics only, through `Source::estimate`:

- P is an upper bound on the live documents where the node may hold, Yes or
  Maybe;
- M is an upper bound on the live documents where it is Maybe.

Dictionary frequencies count dead documents too. That only raises them, so
they stay upper bounds. Every figure is clamped to `live`. Clamping makes an
upper bound tighter; it never repairs a figure that was not an upper bound to
begin with, so nothing below subtracts.

**Leaves follow each atom's real cursor and certainty rules.** The rules
follow `content.rs`, where `TextAtom::estimate` already returns
`(docs + uncovered, certainty)`:

| Leaf                                                    | P                                                                     | M                                                          |
| ------------------------------------------------------- | --------------------------------------------------------------------- | ---------------------------------------------------------- |
| name atom                                               | an upper bound on documents with a matching name: the name index's exact count where it has one, else `live` | 0 (names are decided without reading) |
| `text:` atom, any form                                  | `TextAtom::estimate`'s docs + uncovered: whole-token df **plus** the least unit df when the argument has parts, so the whole-token `OR` branch is counted | P when the atom's certainty is Maybe; otherwise uncovered |
| …certainty, per `content.rs`                            |                                                                       | Yes only for a single token with no parts, not under `case:`, and `exact_under_cap`. Every other form (`case:text:`, capped terms, parts, phrases) is Maybe, so M = P |
| …under H (D65)                                          | add the fingerprint records matching fp(t) for each looked-up term      | add the same records: they are Maybe                       |
| `grep:` atom                                            | its trigram query's bound (below) + uncovered                          | P (a regex is never Yes)                                    |

A trigram query's bound comes from its keys. A key's bound is its df. An
`And` takes the least of its children's bounds, an `Or` takes the sum clamped
to `live`, `All` is `live`, and `None` is 0.

**Operators.**

| Node                | P                        | M                              |
| ------------------- | ------------------------ | ------------------------------ |
| `NOT e`             | `live`                   | M(e)                           |
| `e₁ AND … AND eₙ`   | min P(eᵢ)                | min(P(AND), Σ M(eᵢ))           |
| `e₁ OR … OR eₙ`     | min(live, Σ P(eᵢ))       | min(live, Σ M(eᵢ))             |

`NOT`'s P is `live`, conservatively. The first draft subtracted, P(NOT e) =
live − (P(e) − M(e)), and Astra showed that this is not an upper bound. P and
M are both upper bounds, and the difference of two upper bounds bounds
nothing. Astra's counterexample has four exact terms, each in 75 of 100
documents, missing from different quarters, so their conjunction is empty but
estimated at P = 75. A second problem is that names live in the row domain: a
document with both an `.rs` and a `.txt` name is reached by `NOT ext:rs` even
though it has an `.rs` name. A sound lower bound on Yes would need exact
co-occurrence counts, which the dictionaries do not hold.

`NOT`'s M is sound: `NOT` maps Maybe to Maybe and swaps Yes with No, so the
documents left Maybe are exactly e's.

**The rule.** The query is refused with `RunError::ScanRequired { maybe, live }`
when **M(root) > live / 4**, unless the caller passes the scan flag. Because M
is an upper bound, the rule errs toward refusing, never toward a silent full
read. S2's `IndexIncomplete` check for uncovered documents above
`UNCOVERED_BOUND` is unchanged.

**What the conservative `NOT` costs.** `NOT` itself never inflates M: `NOT
grep:rareliteral` has the literal's few candidates as M and runs. The cost is
in an `AND` whose only narrowing child is a `NOT`. In `NOT text:common
grep:'\d+'`, P(`NOT text:common`) is `live`, so the `AND` is not bounded by it,
and M(root) = live. That query is refused, even though few documents may lack
`common`. `NOT grep:x` for a broad x is also refused, but correctly: its Maybe
set really is x's broad candidate set. So the over-refusal is narrow, a regex
with no positive narrowing at all, and the scan flag answers it. D67 (b) puts
the tradeoff to Dave.

**The invariant test.** For random expressions over random corpora under
random coverage, the M5 oracle computes the actual snapshot-Maybe count: the
live documents whose root certainty, evaluated from the index alone without
verification, is Maybe. It asserts **M(root) ≥ that count**, and P(root) ≥ the
count of documents that are Yes or Maybe. It runs the real estimator and the
real cursors, with no copy of either.

The discriminating cases are pinned:

- Astra's four-quarters conjunction under `NOT`, `AND`-ed with `grep:\d+`;
- `case:text:Foo` under full coverage, where M must equal P and not 0;
- `text:HttpRequest` against documents holding only `httprequest`, which
  reach the whole-token branch;
- a capped term;
- a term with H fingerprint records;
- a document with both `.rs` and `.txt` names under `NOT ext:rs`.

The refusal table, each row run with M(root) printed by `explain()`:

| Query                               | Expected                                                             |
| ----------------------------------- | -------------------------------------------------------------------- |
| `grep:\d+`                          | refused                                                              |
| `NOT grep:\d+`                      | refused                                                              |
| `grep:\d+ OR text:rare`             | refused                                                              |
| `NOT text:common grep:\d+`          | refused (the conservative-`NOT` cost)                                |
| `NOT grep:rareliteral`              | runs: M is the literal's few candidates                              |
| `ext:rs grep:\d+`                   | runs when the name index counts ≤ live / 4 documents for `ext:rs`; refused otherwise |
| `text:serde grep:'v\d+'`            | runs: P(`text:serde`) bounds the `AND`                               |
| `case:text:Foo`                     | refused when Foo's df + uncovered > live / 4                         |
| `grep:the`                          | refused when `the`'s df > live / 4, as on `$HOME` it likely is       |

## Candidate structures

### Trigram postings

A trigram file is an S2 segment file in its container and codecs: the head,
front-coded dictionary blocks with singletons inlined (dictionary codec 1),
`pfor128skip` doc-id lists (postings codec 1), the resident block index, and
16-byte sums per 4 KiB chunk. It differs in two ways:

- A key is a folded trigram, not a token.
- The head's version field holds `TRIGRAM_VERSION`, not `TOKENIZER_VERSION`.
  A change to the folding rule therefore rebuilds the index, as a tokenizer
  change does.

**What changes in the segment code.** `segment::Writer::new` hard-codes
`ferret_text::TOKENIZER_VERSION` into the head (`segment/write.rs`), and
`Writer::spilling`, which every merge output uses, calls `Writer::new`. Both
paths need the version:

- `Writer::keyed(first, last, version)` is the in-memory constructor, and
  `new` delegates to it with `TOKENIZER_VERSION`.
- `Writer::spilling_keyed(first, last, version, out, postings)` is the
  spilling constructor, and `spilling` delegates to it the same way.
- A merge takes the version from its inputs' heads, refuses inputs whose
  versions differ, and writes that version into its output.

Tests check the `.tri` head's version after a first build, after an ordinary
merge and after a full merge, which is the spilling path.

The reader already exposes the head's version through `info()`, and
`SegmentEntry::matches` checks it against the version the caller names, which
was always the tokenizer's until now. Both functions change. The block reader,
`entry`, `read`, `postings::Term` and the merge stream's key handling are
untouched, because they treat keys as opaque byte strings.

A dense 2²⁴ dictionary table was considered and not used. Front-coded blocks
cost a few bytes per key
([§ Bytes per content byte](#bytes-per-content-byte-estimate)), and a dense
table would be new code saving under 1% of text.

**`TrigramInverter`, the one new build-side type.** It holds a pair buffer,
`Vec<u64>`, where each element is `key << 32 | doc`, and a 2²⁴-bit (2 MiB)
seen-bitmap.

- **Per document:** for each byte offset, fold the three bytes, test and set
  the bitmap bit, and on first sight push `(key, doc)`. When the document ends,
  walk the pairs it just pushed to clear their bits. No touched-list is needed.
- **At a flush:** an LSD radix sort on the 24 key bits, in three 8-bit passes,
  orders the buffer by key. Because the sort is stable and documents arrive in
  ascending DocId order, each key's documents stay ascending. The writer then
  takes the runs in order.

**Accounting is by capacity, and the buffer never grows silently.** The
buffer is allocated once at its bound's capacity (`Vec::with_capacity`), so its
allocated bytes are fixed and pages are touched only as pairs arrive. Before a
document is added, the follow pass checks that `len + (doc_bytes − 2)` fits
the capacity. A document has at most `doc_bytes − 2` distinct keys, so this
check never lets the buffer reallocate. If the document does not fit, the
segment is flushed first.

A single document larger than the whole capacity is the one exception: it
grows the buffer for itself, and is flushed alone. The policy size cap of
8 MiB bounds it at 8.4M pairs. At a flush, the radix scratch is allocated
at the buffer's length and freed afterwards. So the trigram side's accounted
memory is:

```text
trigram_accounted = 8 B × capacity + 8 B × len (during a flush only) + 2 MiB bitmap
```

There is no per-key overhead, and no capacity slack beyond the one oversized
document. This is why it is not S2's `Inverter`: that type keys a `HashMap<Box<[u8]>,
Vec<u32>>`, so its cost per distinct key would dominate for 3-byte keys. A
`HashMap<u32, Vec<u32>>` would cost a slot and a 24-byte `Vec` header per key,
plus up to 2× capacity slack per list, which is harder to bound.

**How large the buffer may grow is D70.** S2's `Inverter::memory()` is
already a capacity estimate: list capacities × 4 B, plus a fixed 64 B and the
key bytes per term. The two policies differ only in their flush condition,
checked before each document:

- **A, separate bounds.** Flush when `term.memory() ≥ 64 MiB` (S2's rule,
  unchanged), or when the next document might not fit the trigram buffer's
  capacity. That capacity is set from M1a so that the term rule fires first on
  `$HOME`.
- **B, one shared budget.** Flush when `term.memory() + 16 B × trigram
  capacity ≥ 64 MiB`. The 16 B counts the pair and its flush scratch, because
  both are live at once during a flush. The trigram capacity is whatever is
  left of the 64 MiB after the term side, re-checked before each document.

Both are budgets on accounted bytes. Peak RSS also holds the writers' encode
buffers and allocator overhead, so M1a measures RSS and does not infer it.

[§ Memory](#memory-live-structures-not-serialized-bytes) has the arithmetic.

**Merge.** S2's streaming merge treats keys as opaque, so merging a pair means
running that same stream once over the input `.seg` files and once over the
`.tri` files, then publishing both outputs as one pair. The policy's level
uses the pair's combined bytes, and the dead-fraction trigger uses the shared
`docs` count.

**Build cost (estimate).**

- Extracting keys is a fold, a bitmap test and a rare push per byte: about
  1–2 ns per byte (assumed), which is 4–8 CPU-s for 4.0 GB.
- The radix sort is three passes over 8 B per pair: at about 1 ns per pair per
  pass (assumed), 444M pairs cost about 1.3 CPU-s.
- Encoding 444M postings at 175 Mi/s, intpack's measured sorted-encode rate
  that S2's cost model uses, takes about 2.4 CPU-s.

So a first build adds roughly **8–12 CPU-s** to S2's measured 94.0 (M3), which
is +9–13%. Merging at M3's measured write amplification of 3.00 roughly triples
the encode share. M1 measures all of it.

**Query.** The derived tree compiles to S2's existing `And` and `Or` cursors
over each key's `Candidates::Postings`, wrapped in `Maybe`. Before any list is
read, `Source::estimate` gives each key's document frequency from the
dictionaries alone. An `And` then reads only its **4 rarest** children. Every
child of an `And` is necessary, so any subset of them is a sound, weaker
filter. The common keys would cost the most to read for the least narrowing.
The 4 is a starting point, measured in M5.

### Paired segments

A pair is one storage unit: one segment number, one DocId range, and two files
published by one manifest entry.

```text
index/seg-<first>-<last>-<n>.seg    terms     head version TOKENIZER_VERSION
index/seg-<first>-<last>-<n>.tri    trigrams  head version TRIGRAM_VERSION
```

**Manifest v3.** `SegmentEntry` keeps its terms fields: number, first, last,
docs, terms, pairs, bytes and digest. It gains the trigram file's own facts:
bytes, keys, pairs and head digest. This is about 40 bytes more per entry. The
manifest head records both versions.

**Write, `IndexWriter::write_pair`.** It replaces `write_segment` for follow
and merge outputs. The steps, in order:

1. Take one number from `manifest.next_number`.
2. Write `tmp-<n>.seg` and fsync it. Write `tmp-<n>.tri` and fsync it.
3. Open both files and check each head against what was meant: range, counts,
   and its own version.
4. Rename `.seg` into place, then rename `.tri` into place.
5. Fsync the directory.
6. The caller publishes a manifest naming the pair through S2's existing commit
   (`manifest.tmp`, fsync, rename, fsync the directory).
7. Only then are the inputs retired: both files of each, unlinked.

**Failure and cancellation.** Every failure path relies on two existing facts.
A manifest names only complete pairs. `remove_unnamed` deletes every `seg-*`
and `tmp-*` file the manifest does not name, and its prefix test already
matches `.tri` names.

- A crash at any point before step 6 leaves unnamed files, and the next open
  sweeps them away.
- A crash between steps 6 and 7 leaves the inputs unnamed, and they are swept
  the same way.
- Cancellation, or an error after the first file is written but **before the
  manifest publication starts**, unlinks whatever this call created before
  returning. The sweep covers anything that unlink misses.
- **Once publication has started, nothing is deleted eagerly.** A manifest
  rename can succeed and the directory fsync still report an error, so the
  caller cannot know which manifest a restart will read. On any error from
  step 6 the outputs are kept, the error is returned, and the index is
  reopened through the recovery path: open reads whichever manifest is on
  disk, and `remove_unnamed` then deletes the files that manifest does not
  name, inputs or outputs. `remove_unnamed`'s retained set includes both final
  names of every pair.

The crash-point tests gain these points:

- after `.seg` is synced, before `.tri` is written;
- after the first rename;
- after both renames, before the directory sync.

Each must reopen to the previous manifest, with no files left that it does not
name.

**Open.** `open_segments` becomes `open_pairs`. For each entry it opens both
files and checks **each head against its own facts and its own version**: the
`.seg` file against the terms fields and `TOKENIZER_VERSION`, the `.tri` file
against the trigram fields and `TRIGRAM_VERSION`. Any mismatch fails as
`ReadError::Head` does today. `fits` additionally requires the manifest's
recorded trigram version to equal `TRIGRAM_VERSION`.

**One coverage, one unreadable set.** A document's bytes are read once and fed
to both inverters. Both outputs are published by one manifest write, so a
DocId range is either covered by both structures or by neither. That is why
`Pinned` keeps one `uncovered` bitmap, and S2's unreadable set stays valid
unchanged.

**Compatibility: a pre-S3 index is rebuilt.** `Manifest::decode` today accepts
format 1 or 2 (`manifest.rs`). In v3 it accepts only 3, and returns `None` for
1 and 2. S2's existing path for that answer discards the index and rebuilds it
through coverage. That costs one re-follow, about 97 s of wall-clock on `$HOME`
going by the M4c run's `index-build`, and it happens once. The alternative was
a v2 index opening as "terms only" for a while, which needs per-structure
coverage in `Pinned` until a re-follow completes. That is more code for a
state that lasts one re-follow, so the rebuild is settled here.

**Resources.** `IndexView::resident_bytes` sums both files of each pair, and so
does the daemon's `status` figure. Merge selection sees the pair's combined
bytes.

### Per-document trigram filters

A **binary fuse filter** per document over its distinct folded keys (Graf and
Lemire, 2022). With 8-bit fingerprints it costs about 9 bits per key for large
sets and more for small ones, with a false-positive rate of 1/256 per probe.
On the seam it would be `Source::DocFilter`, with `enumerable: false` and a
`Probe` arm. A filter cannot be enumerated, so it never drives: a pure regex
would drive from the live bitmap and probe every live document.

**Its bytes are known without building it.** A filter's size is a function of
its key count, and its key count is exactly the document's number of trigram
postings. So:

```text
filter bytes ≈ Σ over documents of fuse_bytes(distinct keys)   (≈ 9 bits per key, more when small)
```

At the central estimate below, 444M × 9 / 8 ≈ **500 MB**. That compares with
about **350 MB** for complete trigram files: postings, dictionary and sums
together. Which layout is smaller depends on the posting width M1 measures, so
this is a screening input and not a verdict.

**D8's premise for filters is an arithmetic error.** The research size budget
([architecture § The size budget](research/claude/architecture.html)) prices
filters at "73,510 files × 3,000 keys × 9 bits = 248 Mbit = 31 MB". The product
is 1,984,770,000 bits, which is **248 MB**: the line divides by 8 twice. Astra
confirmed the arithmetic. D8's "the cold-cache win at 12% of the trigram tier's
cost" rests on that line.

**What a filter costs to query depends on the workload.** If nothing else
narrows the query, every live document is probed. At 10M entries that is
8.13M documents (the fixture's count) × about 1.1 probes, since a first No ends
the document, × 3 memory accesses. At 5–100 ns per access that is **0.13–2.7 s
warm per query** (estimate), before cold reads of the filter pages. But a
selective conjunct such as `ext:rs` or a rare `text:` term narrows the
documents first, and then a filter probe per candidate is cheap. So filters
are compared on matched workloads, including selective conjunctions. That
comparison is D68's screening stage, and it runs in M1.

### Per-document term filters (D6)

The same arithmetic applies to S2's terms. M1c measured **89,749,389** (term,
document) pairs. As fuse filters:

```text
89,749,389 × 9 bits / 8 = 101 MB     against S2's merged index, 392 MB (M3)
```

On bytes alone, term filters are **3.9× smaller**, because a filter stores no
term strings, and the dictionary is 74.5% of S2's merged index (M3). Their cost
is latency on unnarrowed queries: an unnarrowed rare `text:` term would go from
M4b's measured **1.94 ms** warm median to the probe-everything figure above.
Term filters are not dominated by postings. They are a density-for-latency
trade, which is why D68 screens them separately from trigram filters, against
matched workloads.

### Experiment: D65, rare terms without dictionary strings

D65 measured where the term index's bytes go. The term dictionary is 74.5–86.4%
of S2's index (M3), and singleton entries, those with df = 1 in their segment,
are 68–81% of the dictionary. At M2 they cost 13.4 B each, because they are
long, unshared strings. D65 C would take singletons out of the dictionary and
answer them from trigrams.

**C and C′ are withdrawn as unsound.** Astra's findings 1 and 2 were verified
against the code.

1. **The representations differ.** C answers a missing term with the AND of
   its trigrams over the document's ASCII-folded bytes. But a term is the
   tokenizer's `to_lowercase` output, not a substring of the bytes. A document
   holding `KELVIN` written with the Kelvin sign emits the term `kelvin` but has
   no `kel` trigram, and `CAFÉ` emits `café` but its bytes have no `fé`. So C
   rejects real matches.

   A sound version would derive, for each term, the byte strings that could
   lowercase to it under `to_lowercase` (not simple case folding: `İ`
   lowercases to two scalars), and fall back to `All` where it cannot. That is
   a second case model beside the regex crate's, and every term lookup would
   run it.
2. **Merging breaks "missing means fall back".** Suppose segment A drops
   singleton `foo` in document 1, and segment B keeps `foo → [2, 3]`. The
   merged dictionary holds `foo → [2, 3]`, and a fallback that runs only on a
   dictionary miss never finds document 1. Repairing that needs provenance
   recording which ranges dropped which terms, and those records outlive their
   segments.
3. **Every lookup pays.** Once singletons can be missing, a dictionary miss no
   longer means "absent". Even common terms pay the trigram fallback, and
   superstring false positives too: `get` in `target` or `budget`.

**H replaces them, and it needs no trigrams.** H keeps every term's
occurrences but stores a singleton as a 32-bit fingerprint of the term instead
of the term itself. It is simpler than a repaired C and sound by construction.
It is also independent of S3: its result holds whether or not trigrams ship.

**H's invariant.** For every term t and segment s:

```text
docs(t, s)  ⊆  dict_postings_s(t)  ∪  fingerprint_docs_s(fp(t))
```

- **Write.** When an inverter flushes, a term with df = 1 goes to the
  fingerprint section as `(fp(t), doc)`. Every other term goes to the
  dictionary. Each (term, document) pair lands in exactly one of the two.
- **Merge.** Each input's dictionary streams through as today. Each input's
  fingerprint records are merged in `(fp, doc)` order, with dead documents
  purged. A dictionary term whose merged live df is 1 moves to the fingerprint
  section, since its string is known. A fingerprint record never moves back,
  because its string is not stored.

  So one merged segment can hold `foo` both ways: A's document 1 as a
  fingerprint record, and B's documents 2 and 3 in the dictionary. Each output
  pair comes from an input pair, so the union over the inputs equals the union
  over the output, less dead documents. The invariant holds after any sequence
  of merges and purges.
- **Lookup.** Every term lookup, in every segment, consults **both** sections
  and unions them, **whether or not the dictionary hits**. Dictionary postings
  are Yes, as today. Fingerprint documents are Maybe and are verified: two
  terms can share a fingerprint, and every record in a matching run is kept.
- **Absent.** The answer is No only when both sections miss in every segment.
- **Hash.** `fp` is 32 bits of BLAKE3 over the term's bytes. BLAKE3 is already
  a dependency of `ferret-index` for checksums, and the choice is fixed by the
  segment format. The dictionary codec id changes, so an index built before H
  is rebuilt through coverage.

**Fingerprint records accumulate.** A record never returns to the dictionary,
so after merging, the fingerprint section holds every occurrence that was a
singleton in **any first-build segment**, not just the current segment's
singletons. If `foo` was a singleton in 49 first-build segments, a full merge
keeps 49 `foo` records. That has two consequences:

- **Lookup cost.** A term's fingerprint records, and so its extra Maybe
  documents, number up to the count of first-build segments in which it was a
  singleton: up to 49 on `$HOME`, more on a larger tree. Collisions add about
  `records / 2³²` per lookup, about 0.006 at the population below. M2 reports
  the distribution of records per looked-up term, per class.
- **Population.** The section's size is set by the first build, not by the
  merged index's singleton count.

**H's layout: restart blocks.** Records are sorted by `(fingerprint, doc)` and
grouped into blocks of 128.

- **First record of a block:** fingerprint as `u32` and doc offset from the
  segment's `first` as `u32`, both fixed width.
- **Each later record:** a vbyte fingerprint delta (0 inside a run of equal
  fingerprints) and a vbyte doc offset.
- **Resident block index:** each block's first fingerprint and its byte offset
  in the section, 8 B per block.
- **Checksums:** the section is covered by the file's 16-byte chunk sums, like
  every other section.

**H's lookup finds the whole run.** A run of records with fingerprint f can
begin anywhere: mid-block, or in an earlier block whose first fingerprint is
below f, and it can span several blocks. Purges and regrouping during merges
move the boundaries. So the lookup works like this:

1. Find i, the first block whose first fingerprint is **≥ f** (a lower-bound
   search over the resident index).
2. Start decoding at block i − 1, or at block 0 when i = 0. If i − 1 holds any
   f records, they are its last ones, and they begin the run.
3. Skip records below f, collect every record equal to f, and continue across
   block boundaries into i, i + 1, …, until a record above f or the end of the
   section.

A block whose first fingerprint equals f is never the start of the run unless
the block before it ends below f, and step 2 covers both cases. The first
draft's "last block whose first fingerprint ≤ f" lost every record of a run
before that block. Astra's example puts 129 records of f in two blocks and
finds only one of them.

Tests, all through the real lookup with a test-only hash injected through the
writer's constructor:

- a run that starts mid-block;
- a run that spans three or more blocks;
- a run that starts exactly at a block's first record, with the previous block
  ending in the same fingerprint;
- a run that shifts across a boundary after a purge removes records ahead of
  it in a merge;
- a target fingerprint below the first block's, and above the last block's.

**H's bytes, two estimates.** Per record on disk, at a population of about
26M:

- fingerprint delta: 2³² / 26M ≈ 160 apart, so 2 B vbyte;
- doc offset: 3 B vbyte on `$HOME` (fewer than 2²¹ docs), 4 B at 10M;
- restart header: 8 B per 128 records, 0.06 B;
- sums: 16 B per 4 KiB, 0.4%.

That totals about **5.1 B per record**. The two estimates differ in their
population.

*Lifecycle estimate.* This is the one the experiment tests. Records are the
first build's singletons, kept through merges. M3's first build had h = 1.81
over 18,441,368 terms, which is 33.4M entries (derived), and 78.8% were
singletons: **26.3M records** (derived). The control's singleton entries cost
13.4 B each (M2) and are counted per state from M3. H's dictionary drops at
least those entries, and keeps the rest of the control's bytes as an upper
bound:

```text
state          control (M3)   control singletons            H ≈ control − singletons + 26.3M × 5.1 B   change
first build    500.7 MB       26.3M  × 13.4 = 352 MB        500.7 − 352 + 134 = 283 MB                  −43%
steady (13)    442.3 MB       18.6M  × 13.4 = 250 MB        442.3 − 250 + 134 = 326 MB                  −26%
full merge     391.9 MB       12.6M  × 13.4 = 169 MB        391.9 − 169 + 134 = 357 MB                  − 9%
```

Steady state has 25,553,432 entries, 72.9% of them singletons. Full merge has
68.3% of 18,441,368 terms as singletons. These are estimates. The 13.4 B
figure was measured before merging, and removing entries changes how well the
remaining terms front-code.

**H erodes as merging proceeds.** Each merge removes the control's singletons,
but H's 134 MB of records stays. At full merge the estimated saving is under
the 15% line.

*Idealised conversion estimate.* This is not what H builds. Converting only
the fully merged index's 12.6M singletons to records would give 12.6M ×
(13.4 − 5.1) ≈ **105 MB**, or −27%. This was revision 2's figure. It assumes
a structure that has seen no merges, so it is kept only for comparison.

**Cost per lookup.** One extra resident lower-bound search, plus one or two
block reads per segment, plus one verification per fingerprint record (above).

**Arms.** The experiment has two:

- **Control:** S2's term index exactly as built.
- **H:** an index **built through H's own lifecycle**, with the real follow
  into 49 segments, then the real merges to steady state, then a forced full
  merge. It is never a conversion of the control's merged index.

Trigram files are left out of both. H is judged on the term index. The combined
index is reported for information.

**Corpus.** The isolated `$HOME` catalog copy that S2 M1c–M4c used. Each arm is
measured at all three of M3's states. The decision is taken at **steady state**,
which is where the daemon lives. First build and full merge are reported for
H's erosion.

**Metrics.**

- **Bytes:** term-index bytes per content byte, split by section, and the
  fingerprint record count at each state.
- **Latency by term class**, warm and evicted, as the median and p90 of 50
  seeded queries per class, with the control re-run in the same session. The
  classes:
  - df = 1;
  - df 2–100;
  - **absent:** real terms mutated by one character and checked absent in the
    control. Agents produce these (typos, a symbol that does not exist yet).
  - mid, df 1k–100k;
  - common, the top 50 by df.
- **Verification:** documents verified and bytes read per query, and
  fingerprint records per looked-up term, per class.
- **Build CPU:** follow, merges to steady state, and the forced full merge.
- **Correctness:** every query's verified rows must equal the control's.

**Decision rule.** H replaces dictionary codec 1 if, at steady state, all of
these hold:

1. term-index bytes fall by at least **15%**;
2. warm p90 for df = 1, df 2–100 and absent stays under **20 ms**;
3. warm median for mid and common stays within **1.5×** the control's;
4. build CPU stays within **1.2×**.

The full-merge saving is reported beside it. If H passes at steady state but
falls under 15% at full merge, as the lifecycle estimate predicts, the D65
amendment puts that erosion to Dave. If it fails at steady state, D65 A
stands. The thresholds are my reading of "slightly slower", and Dave can move
them in the D65 amendment.

**Tests.** S2's differential oracle runs on random corpora under random merge
sequences. It includes mixed occurrences, where a term is a singleton in some
inputs and has df ≥ 2 in others. It includes forced fingerprint collisions,
through the injected hash, so that the real lookup path runs. Every lookup,
verified, must equal brute force before and after every merge. The restart
block tests above are part of it.

### Memory: live structures, not serialized bytes

Astra's finding 11 was right: the first draft priced the resident and buffer
costs at their serialized sizes. This revision uses the allocated structures.
M1a measures `resident_bytes()` and peak RSS, with both inverters fed from each
document read, under both of D70's policies.

**Follow buffer.** The trigram side's accounted memory is 8 B per pair of
capacity, plus 8 B per buffered pair of radix scratch during a flush, plus the
2 MiB bitmap ([§ Trigram postings](#trigram-postings)). Sizing it to S2's
segment boundaries, which M3 measured as 49 segments at first build, gives
these pair counts per segment:

| Scenario | Pairs per segment             | Peak buffer (16 B/pair) |
| -------- | ----------------------------- | ----------------------- |
| low      | 201.7M / 49 = 4.1M            | 66 MB                   |
| central  | 443.5M / 49 = 9.1M            | 145 MB                  |
| high     | 1,379.4M / 49 = 28.2M         | 451 MB                  |

Under policy A this adds to S2's own measured build peak of **288,616 KiB**
RSS (M3), together with the trigram writer's encode buffers, which are not
estimated here. Under policy B, one 64 MiB budget covers both sides. At the
central estimate, an S2-sized segment needs about 64 MiB for terms plus
145 MB for trigrams, so a shared 64 MiB ends segments at about 31% of S2's
size: about 3.3× as many segments (estimate). The extra term-dictionary
duplication and merge work that follow are what M1a measures, by building both
structures under both policies. D70 is this choice.

**Resident per `.tri` segment.** The decoded `Block` is four 8-byte fields
(`segment/read.rs`), and each block also holds its first key's 3 bytes, so a
block costs about 35 B per 32 keys, or 1.1 B per distinct key per segment.
Chunk sums cost 16 B per 4 KiB, which is 0.39% of file bytes.

```text
keys per segment   0.5–2M (assumption)        → 0.55–2.2 MB per .tri
steady state (13)                             → 7–29 MB, + sums 349 MB × 0.0039 ≈ 1.4 MB
first build (49)                              → 27–108 MB until merging
```

These are estimates, and M1 measures `Segment::resident_bytes()` directly.
For scale: S2.md's cost model priced term blocks at 12 B, but the code's
`Block` takes 32 B plus the key. That is a disagreement in S2.md, listed in
[§ S2.md against the code](#s2md-against-the-code).

```text
small-file pairs     1.89e9 × 0.10 = 189M   1.89e9 × 0.15 = 283.5M  1.89e9 × 0.30 = 567M
large-file pairs     254 × 50k = 12.7M      800 × 200k = 160M       2,031 × 400k = 812.4M
pairs                201.7M                 443.5M                  1,379.4M
postings             × 4/8 = 100.9 MB       × 6/8 = 332.6 MB        × 8.32/8 = 1,434.6 MB
dictionary           1M × 1.39 × 6 = 8.3 MB 2M × … = 16.7 MB        4M × … = 33.4 MB
sums (0.39%)         0.4 MB                 1.3 MB                  5.7 MB
trigram files        ≈ 110 MB               ≈ 351 MB                ≈ 1,474 MB
per content byte     2.7%                   8.8%                    36.9%
```

**The envelope combines every bound independently**, and so it is wider than
the plausible range. The high corner pairs the largest N, meaning files that
average only about 1 MiB, with the largest K, meaning 400k distinct keys in
about 1 MB of text. That would be 38% of the file's byte offsets introducing a
new trigram, which is unlikely for text. A correlated high, N = 2,031 with
K = 200k, gives 406M large-file pairs, 973M in total, and about 1.05 GB, or
26%. The low corner is just as unlikely in the other direction. Astra's
2.5–35.9% is the posting-bytes part of this table, before the dictionary;
the arithmetic agrees.

**Against S2.** The merged term index measured 392 MB, 0.098 B/B (M3). At the
central estimate, trigrams nearly **double the index**, taking it to about
741 MB, or 0.186 B/B. Their proportions are the inverse of S2's: postings
are about 95% of a trigram file and the dictionary about 5%, because a trigram
index has few distinct keys and long lists.

**Cross-check.** Cox's Linux figure is 18% of source. Ours should come out
lower, because more than half our bytes sit in large files whose keys saturate.
That is an untested expectation, and M1 tests it.

## Experiment: D66 C, reduced to a census

D66 measured that phrase verification is dominated by **reading**. The median
query reads 1,254 MiB and the p90 2,273 MiB (M4c), and 53% of the tree's bytes
are in files of 1 MiB or more. D66 C would record, for each (term, large
document) pair, which fixed-size chunks contain the term, so that verification
reads only those chunks.

**The design is deferred, and this sprint only measures.** Astra's findings 5
and 6 show that a sound chunked reader needs more than the first draft said:

- **Separator stretches.** M4c's matcher walks a fixed number of
  run-containing segments in each direction, across separator stretches of any
  length. Stopping a lazy fetch at the first ASCII separator misses `alpha`,
  then several chunks of spaces, then `beta`.
- **Anchors that straddle a chunk edge.** A scan of either chunk alone does not
  see the whole anchor. Reads must join adjacent chunks, and must align to
  UTF-8 boundaries.
- **Unicode.** M4c's İ/Kelvin documents are tokenized whole, and a chunked
  reader must keep that fallback.
- **Changed versions.** The chunk map describes the catalogued version of a
  document. S2 verifies current bytes. If the file was rewritten so that the
  phrase moved from chunk 1 to chunk 4, an old map misses the match even though
  the read is correctly bracketed. A chunked read is therefore valid only after
  the opened file is established to be the catalogued version. Otherwise the
  whole document must be verified, every content atom re-evaluated, and S2's
  path-specific caching rules kept.

A specification of all four would be about as long as M4c's. It is worth
writing only if the chunk map would save enough, and this census answers that
before any design work.

**The census.** For each of M4c's 50 phrase queries, with the same seeds, and
for each candidate document of 1 MiB or more:

1. Run M4c's real `TextMatcher` over the whole document, with an observer
   argument that records the byte span of every anchor occurrence, every
   window, and every segment the widening walks. It is a hook on the real
   matcher, not a copy of the matcher.
2. At chunk sizes of 1 MiB, 256 KiB and 64 KiB, count the chunks covered by
   those spans. That is a **lower bound** on what any lazy reader following
   M4c's rules must fetch. An **upper bound** adds one neighbouring chunk for
   each anchor occurrence within a run's length of a chunk edge. Both are
   reported.
3. Count (term, document, chunk) triples over every document of 1 MiB or more,
   at each chunk size. That count sizes the map.
4. Count the candidates whose current stat differs from the catalogued version.
   Those would fall back to whole-document reads.

**Map bytes (estimate, to be replaced by step 3).** Assume large documents
hold 20–35M of M1c's 89.7M term pairs. That is a guess: `jsonl` alone has
6,298,674 distinct terms in 1,987 documents (M1c).

| Chunk   | Per pair   | Map bytes  | Against the 392 MB merged index |
| ------- | ---------- | ---------- | ------------------------------- |
| 1 MiB   | 1 B        | 20–35 MB   | +5–9%                           |
| 256 KiB | ~1.5–4 B   | 30–140 MB  | +8–36%                          |
| 64 KiB  | ~2–16 B    | 40–560 MB  | +10–140%                        |

**Decision rule.** If some chunk size cuts **p90 bytes read by at least 50%**
at its upper bound, for **at most 10%** more index bytes, D66 C becomes a
design task with its own brief in the next sprint, carrying the four
requirements above. Otherwise D66 C closes on the census table.

**Regex gets no chunk map.** A term map cannot locate regex matches.
`grep:foo` matches `xfooy`, whose only token is `xfooy`, so there is no `foo`
entry to consult. That needs a trigram-location map, which would be larger
than the trigram postings themselves (estimate). So regex verification reads
whole documents. See [§ Verification](#verification).

## Verification

**Where it sits.** `ferret-verify` gains `Grep`, beside `Text`. It holds a
`regex::bytes::Regex` built from `GrepFlags::regex`, behind the `Matcher`
trait. Its `find` returns the first match's byte span, which becomes the JSON
row's offset. `plan.rs` evaluates every content atom of a Maybe row against one
bracketed read of the current bytes, as it does for `text:`. S2's whole
coverage contract applies unchanged: the freshness rule, document-fact caching,
changed-path rules and the policy size cap (S2.md § Coverage). `MatchStats`
gains regex counters for bytes scanned and documents rejected.

**Whole documents, through M6.** Regex verification reads and searches the
whole current document. A bounded-window search was considered and deferred,
because two prerequisites are missing:

- **Locating match positions.** Windows need anchor positions, and the term
  chunk map cannot supply them for substrings (see above). Finding them in the
  loaded bytes needs the whole document anyway.
- **Real context at the edges.** `regex_automata::Input::span` limits where a
  match may lie while letting look-around consult bytes outside the span, but
  only bytes present in the haystack it was given. Searching a loaded slice can
  make `\Afoo` or `\bfoo` succeed where the full document rejects them.

A partial-read design would have to specify boundary context, true document
endpoints, offset translation and cross-chunk anchor discovery. None of it is
needed while reading is whole. The `regex` crate's own literal prefilter
already skips through loaded bytes at memchr speed. So `ferret-verify` gains no
`regex-automata` edge.

**D17, "the regex crate until S3".** S3 keeps D17 A. The deciding number D17
named is verification's share of end-to-end regex latency, and M5 measures it
per query class. The rule: if verification is more than half of p90
wall-clock, *and* the engine (not reading) is more than half of verification,
an own engine could win something, and D17 reopens. Otherwise A stands with a
number behind it.

M4c already suggests the outcome. Reading took 126 ms of the 715 ms median, and
S2 derived the remaining ~400 ms as the two whole-document regex passes over
1.25 GB (it did not split them). That is the `regex` crate scanning at about
6 GB/s per pass (derived), which an own engine would have to beat.

## Query surface (D67)

D67 below is the brief. Its recommendation is used throughout this document:

```text
atom   = ... (S1's and S2's atoms) | "grep:" REGEX | "case:grep:" REGEX
```

- `grep:REGEX` is a content atom. It uses the `regex` crate's syntax over the
  document's bytes, under `GrepFlags`: case-insensitive by default, `^` and `$`
  matching at line boundaries, `.` not matching `\n`. `case:grep:` makes it
  case-sensitive, as `case:` does for every other atom.
- It composes like `text:`: adjacent atoms AND, and `OR`, `NOT` and
  parentheses work as D62 A spells them.
- When the planned expression would verify more than a quarter of the live
  documents, the query is refused unless the scan flag is given. That is D67's
  question (b).
- `re:` keeps its S1 meaning, a regex over **names**.

**Certainty.** A `grep:` atom is never Yes from the index, because a trigram
query is necessary but not sufficient (the course's `Seaearch`). The index
answers **No** for a document outside the trigram query, and **Maybe** for a
document inside it, which goes to the verifier. Under `NOT`, Kleene's table
gives `NOT No = Yes`, with no read, and `NOT Maybe = Maybe`, with a read.

`explain()` prints, for the query:

- the derived trigram query;
- the keys actually read, the 4 rarest of each `And`;
- each key's df;
- the P and M estimates of every node;
- the candidate count.

The query log records the same, so M5's query set and S4's agent traces show
which patterns degrade to `All` or are refused.

## Bench plan

Everything runs in `ferret-bench`, against a **copy** of the isolated `$HOME`
catalog that S2 M1c–M4c used. The index under test is built into the copy, and
the copy is deleted afterwards. The rules S2 kept:

- **One measurement at a time on the machine.** Check `uptime` and the process
  table first, and record the load. Match process names exactly (`pgrep -x
  cargo`, `pgrep -x ferretd`) so the check cannot match itself.
- **Release builds**, at a named commit.
- **An isolated environment.** `HOME`, every `XDG_*` variable and the runtime
  directory point into scratch, and no real-home daemon runs. The real query
  log's size and mtime are recorded before and after, and must not change.
- **Warm and evicted.** Evicted means `posix_fadvise(DONTNEED)` on every index
  file before the query, while the catalog stays warm, as in M4b. **Cold** also
  evicts the candidate documents, using the bench's checked opener.
- **Seeded selection.** Queries come from the index's own dictionaries, or from
  documents chosen by hash, never from reading Dave's files into the report.
  Results report counts and timings, never paths or content.
- **Figures labelled.** Every number is marked measured, derived or estimate,
  together with the run that produced it.

Trigram bytes scale with text more steeply than term bytes. The term
dictionary grows sublinearly (Heaps' law), but trigram keys are capped at 2²⁴,
so beyond the first few GB trigram bytes grow with pairs alone, roughly in
proportion to text. At 100 GB the trigram files could be the larger half of the
index. That is D69's territory.

## Settled here without a brief (object if wrong)

- Trigram keys are raw document bytes, ASCII-folded and nothing else.
  `ferret_text::trigram_key` is the one folding function.
- The derivation lives in `ferret-verify` and parses with the verifier's own
  flags, set by one `GrepFlags`, with `utf8(false)` explicitly. The caps are
  Cox's (7 and 20) plus ours (4 per class, 64 keys per query). Raw-byte classes
  and literal bytes are never UTF-8-encoded.
- Trigram files reuse S2's container and codecs as one `.tri` per pair, under
  one manifest entry, with shared coverage. Pair writes follow
  [§ Paired segments](#paired-segments)' ordering.
- A pre-S3 manifest (v1 or v2) is rebuilt through coverage. It is never opened
  as terms-only.
- An `And` reads only its 4 rarest keys.
- Regex candidates are always Maybe.
- The planner's refusal is computed over the whole expression from the P and M
  estimates. The user-visible threshold and flag are D67's.
- Regex verification reads whole documents through M6.
- D17 A stays, pending M5's share measurement.
- D65 C and C′ are withdrawn as unsound. H replaces them.
- D66 C is reduced to a census this sprint.
- The edge `ferret-verify → regex-syntax` is added, and no others.

## Rejected alternatives

| Alternative                                                     | Why not                                                                                                                                                                                                  |
| --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| An independent trigram index with its own manifest and follow   | It reads every document twice, and needs per-source coverage in `Pinned`. A pair under one entry gives the same answers with neither.                                                                    |
| Trigram sections inside the term segment file                   | A second dictionary in one file's reader and writer. A sibling file reuses both, and the bench can drop it to get a control.                                                                            |
| A v2 index opening as terms-only until a re-follow              | Per-structure coverage in `Pinned`, for a state that lasts one re-follow.                                                                                                                                 |
| Unfolded (case-exact) keys                                      | Default queries are case-insensitive, so each letter would expand into 2–8 ORed keys per trigram, with more pairs on disk. Folding loses only `case:` precision, and the verifier restores it.            |
| Rune (code-point) trigrams, as Zoekt's design describes          | They need decoding at index time and have no answer for invalid UTF-8. Byte trigrams are sound for byte regexes because the HIR is already bytes.                                                         |
| Positional trigrams (Zoekt-style)                               | Positions were declined in D6 and D7, and they would multiply the largest new structure.                                                                                                                 |
| `regex-syntax`'s `hir::literal::Extractor`                      | It extracts prefix and suffix literal sets, not a boolean over inner trigrams, so it loses Cox's `AND` across `.*`. And the project builds rather than adopts.                                          |
| D65 C or C′, repaired                                           | It needs a `to_lowercase` inverse with a conservative fallback, plus omission provenance that survives merges. H gets about the same bytes with neither.                                                  |
| A `HashMap<u32, Vec<u32>>` trigram inverter                     | A slot and a `Vec` header per key, plus up to 2× capacity slack. The pair buffer costs exactly 16 B per pair at peak.                                                                                     |
| Windowed regex verification                                     | It needs a trigram-location map and true edge context, and it saves nothing while documents are read whole.                                                                                              |
| Per-block filters over many documents (VictoriaLogs-style)      | A middle ground between per-document filters and postings, and a third structure. Revisit only if D68's screening puts filters within 2× of postings on matched workloads.                               |
| `re:` meaning content                                           | It would silently change S1's name-regex queries (D67).                                                                                                                                                   |

## S2.md against the code

These were found while reading the code at `e5f1283`. S3 follows the code in
every case. Each is a candidate one-line fix to S2.md, made on main only if
Dave wants S2.md kept current.

1. S2.md says that estimating a source before reading it "does not exist". The
   code has `Source::estimate` and `estimate_until`, which read dictionaries
   only, and `TextAtom::estimate` uses them. S2's sketch puts `cursor` and
   `probe` on `Source`; the code has them on `Candidates`.
2. The sketch calls the `Or` cursor a min-heap. The code scans its children
   linearly, which S2.md concedes later.
3. S2.md defines "uncovered" as outside every segment range. The code uses the
   manifest frontier: live documents at or above it, plus the unreadable set.
4. `Or` materialises past `bound / 32`, where `bound` is `next_doc`, not the
   live count.
5. `ferret-verify`'s `lib.rs` doc says changed files are "reported stale, never
   matched". That contradicts S2's contract of verifying current bytes.
6. S2's cost model prices a resident block at 12 B per 32-term block. The
   decoded `Block` is four 8-byte fields plus the first term's bytes.
7. Not S2.md, but DESIGN: § Query sketches content regex as `/regex/`, while
   `re:` is already S1's name regex. D67 settles which spelling stands.

### D65 amendment — H replaces C as the singleton experiment

**For the existing D65 brief, to append.** S3 M0, revision 2, 2026-10-08;
[design](S3.md#experiment-d65-rare-terms-without-dictionary-strings).

**C as written is unsound, and so is C′.** Three problems, the first two from
Astra and confirmed against the code:

- **False negatives.** The trigram fallback checks a normalised term against
  the document's raw bytes. A document whose `Kelvin` is written with the
  Kelvin sign emits the term `kelvin`, but its bytes hold no `kel` trigram, so
  C misses it.
- **Merging loses documents.** Merging a dropped singleton into a segment that
  keeps the term means a dictionary hit no longer lists every document.
- **Every lookup pays.** A dictionary miss stops meaning absent, so every term
  lookup pays the trigram fallback.

**The replacement option, H.** Singletons move to a searchable section of
(32-bit fingerprint, DocId) records, and every lookup unions that section with
the dictionary. It is sound by construction, and it needs no trigrams.

- **Bytes (estimate):** about −105 MB at full merge, taking the term index
  from 392 MB (measured, M3) to about 287 MB, or 0.072 B/B.
- **Latency:** every fingerprint hit is Maybe, costing one verification read,
  plus one extra block read per segment per lookup.

**Proposed rule.** H replaces dictionary codec 1 if, at both merge states, all
of the following hold. Otherwise A stands.

- term-index bytes fall by at least 15%;
- warm p90 for df = 1, df 2–100 and absent terms stays under 20 ms;
- the mid and common medians stay within 1.5× the control's;
- build CPU stays within 1.2×.

**Fact that would change it:** M2 measuring H's marginal saving under 15%, for
example because front coding of the remaining terms worsens. Then D65 A stands
and no singleton work remains.

### D67 — How `ferret search` spells a content regex, and when it refuses

**Status: open.** S3 M0, revision 2, 2026-10-08;
[design](S3.md#query-surface-d67).

**Question (a):** What prefix makes an argument a regex over file content, and
with what line and case semantics?

**Question (b):** When the planned expression would verify most of the tree,
does the query refuse, at what threshold, and through which flag?

`re:` already means a regex over **names** (S1), and D62 A gave content the
`text:` prefix. DESIGN's query section sketched `/regex/`. Agents call
`ferret search` from shells, so quoting cost matters.

**(a) Spelling.**

| Option | Costs | Buys |
| --- | --- | --- |
| A. `grep:REGEX` | One more prefix to learn. | It reads as what it does, and agents know grep. `case:grep:` composes as `case:` does elsewhere. `re:` keeps its meaning. |
| B. `text:/REGEX/` | It changes `text:` for an argument that starts and ends with `/`, which today is a term (`text:/usr/` finds `usr`). A regex containing `/` needs a rule. | No new prefix: `text:` covers all content. |
| C. Bare `/REGEX/`, as DESIGN sketched | `/` already makes a bare word a path substring (S1), so `/usr/` would change meaning. | The shortest spelling. |
| D. `re:` searches content as well as names | It changes every existing `re:` query's meaning and cost, which is D62's argument against its B. | One regex prefix. |

Semantics under any option:

- **case-insensitive by default**, as `text:` and `re:` are, with `case:` for
  exact case;
- **multi-line:** `^` and `$` match at line boundaries, as grep users expect,
  and `(?-m)` restores whole-document anchors;
- `.` does not match `\n`, the `regex` default.

The alternative is the `regex` defaults, with whole-document `^` and `$`. Those
are right for names but surprising for content.

**(b) Refusal.** The planner estimates M, the documents the whole expression
leaves Maybe, from dictionaries alone, as an upper bound. It covers `NOT` and
`OR`: `NOT grep:\d+` and `grep:\d+ OR text:rare` both leave every document
Maybe. S2 already refuses when uncovered documents exceed 10,000, with the flag
`--scan-uncovered`.

| Option | Costs | Buys |
| --- | --- | --- |
| i. Refuse when M > live / 4 with `ScanRequired`; one flag `--scan` overrides both this and S2's uncovered refusal, with `--scan-uncovered` kept as an alias | Some broad but legitimate queries need the flag. `grep:the` likely does on `$HOME`. The estimate is an upper bound, so it occasionally refuses a query that would have been cheaper. | No accidental 4 GB read; one rule an agent can learn; one flag. |
| ii. Refuse only when M comes from an `All` trigram query | Broad non-empty queries (`grep:the`, `NOT grep:common`) read most of the tree silently. | Fewer refusals. |
| iii. Never refuse; report M in `explain()` and the JSON stats | Agents pay the full read before learning the cost. | Nothing to learn. |

**Recommendation: (a) A, with multi-line on; (b) i.** On (a), fastest and
simplest are indifferent: this is interface taste and compatibility, as D62
was. On (b), i is the simplest single rule, and it follows S2's precedent.

**Fact that would change it:** S4's agent traces. If agents reach for `/…/` or
for `re:` on content, make B or D the spelling, with the old one as an alias.
If agents hit `ScanRequired` on queries they meant, raise the fraction or take
ii.

### D68 — Per-document filters: a screening stage, terms and trigrams separately

**Status: open.** S3 M0, revision 2, 2026-10-08;
[design](S3.md#per-document-trigram-filters).

**Question:** ROADMAP says S3 builds per-document trigram filters beside
trigram postings, and benches per-document term filters against postings (D6,
D8). Should either filter go into the index, or is a screening measurement
enough to decide?

A binary fuse filter's size follows from its key count, and each key is one
posting, so its bytes can be computed exactly from the documents' key sets.
Figures are **estimates** unless marked:

- **Trigrams:** about 500 MB of filters against about 351 MB of complete
  trigram files at the central estimate. The comparison flips if postings
  average much above 9 bits per pair. Term lists measured 8.32 (M2), and
  trigram lists should be denser.
- **Terms:** 89.7M pairs (**measured**, M1c) give about 101 MB of filters,
  against S2's 392 MB merged index (**measured**, M3). That is 3.9× smaller,
  so term filters are a real density option.
- **Latency:** a filter is probed once per candidate document. Unnarrowed, that
  is every live document: 0.13–2.7 s warm at 10M, against a rare term's
  measured 1.94 ms warm median (M4b). Narrowed by a selective name atom or a
  rare term, the probe cost shrinks with the narrowing.
- **D8's premise** that filters cost 12% of postings is an arithmetic error in
  the research budget: 248 Mbit should have been 248 MB.

| Option | Costs | Buys |
| --- | --- | --- |
| A. Build both filters into the index and bench them, as ROADMAP says | A filter builder in follow and merge, a probe arm, coverage and tests: about one slice of work before knowing whether either survives. | Measured end-to-end numbers, including cold page-cache behaviour of real filter files. |
| B. Screen first, in M1: build real filters in the bench from exact key sets, terms and trigrams separately; compare complete layouts on matched workloads (unnarrowed; narrowed by 1%, 10%, 50% name atoms; narrowed by a rare term); integrate only a layout that survives | A layout that survives screening still needs the integration slice later. Screening does not measure follow or merge cost. | Each structure is decided on measured bytes and probe cost, before any index code. A surviving density/latency trade comes back here with its numbers. |
| C. Build term filters only, as a density opt-in, without screening | A second term structure to keep correct; unnarrowed rare-term queries 100–1000× slower when chosen. | The smallest term index, for users who value bytes over everything. |

**Recommendation: B.** Fastest and simplest agree on screening first: it costs a
bench command, and it can only remove work. I expect trigram filters to fail
screening, being larger and slower than postings. Term filters will likely
survive as a trade, and come back here as a question about the opt-in.

**Fact that would change it:** screening showing a filter layout within about
1.2× of postings on the narrowed workloads, and smaller on bytes. Then build it
(A), for that structure only.

### D69 — Saturated large documents in trigram postings

**Status: open.** S3 M0, revision 2, 2026-10-08;
[design](S3.md#bytes-per-content-byte-estimate).

**Question:** Large documents hold most of the bytes and many of the common
trigrams. Should every document's trigrams be indexed? Or should a document
above some distinct-key threshold be marked "Maybe for every trigram atom"
instead, and skip trigram postings?

Figures are **estimates** until M1. On `$HOME`, 53% of the text is in files of
1 MiB or more (**measured**, S2 M1), perhaps 800 files. At the central estimate
they contribute about 160M of 444M trigram pairs, about 120 MB. A selective
regex likely excludes most of them, but a broad one includes them all. A high
distinct-key count does not prove that a document holds the keys queries
actually use, so the threshold has to be measured, not guessed.

| Option | Costs | Buys |
| --- | --- | --- |
| A. Index every document's trigrams | The full trigram files: about 351 MB central, about 36% of it from large documents. Bytes grow with text past a few GB. | Every regex narrows over every document. One rule. |
| B. Above a threshold chosen from M1's sweep (16k–256k distinct keys), put the document in a per-segment "saturated" bitmap, Maybe for every trigram atom | Every regex verifies every saturated document: up to about 800 files and 2.1 GB on `$HOME` at a low threshold. Warm, that is a few hundred ms of reading (M4c) on every regex; cold, much more. | Up to about a third of trigram bytes, at the threshold the sweep picks. |
| C. A, plus a trigram chunk map | Likely larger than the trigram postings themselves (estimate). | Large documents both narrowed and partly read. Not costed further this sprint. |

**Recommendation: A**, the fastest and the simplest. B is denser but makes every
regex pay a cost that the phrase work just removed. Fast and dense disagree,
and that is why this is a brief.

**Fact that would change it:** M1's sweep finding a threshold where the
saturated documents hold more than about half of all trigram pairs, *and* the
cold and warm verification of those documents measures under 100 ms warm on the
M5 regex classes. B's cost is then small enough to buy its bytes.

### D70 — How large the trigram follow buffer may grow

**Status: open.** S3 M0, revision 2, 2026-10-08;
[design](S3.md#memory-live-structures-not-serialized-bytes).

**Question:** During a follow pass, should trigram pairs count against S2's
64 MiB flush budget, ending segments sooner? Or should they get their own
bound, so that segment size is still set by terms alone?

The trigram buffer costs exactly 16 B per pair at a flush: 8 B per pair, plus
8 B of radix scratch. Figures are **estimates** until M1. At S2's 49 build
segments (**measured**, M3), a segment holds about 9.1M trigram pairs
(central), with a range of 4.1–28.2M. S2's own build peak was **288,616 KiB**
RSS (**measured**, M3).

| Option | Costs | Buys |
| --- | --- | --- |
| A. Own bound, sized from M1 so terms set segment size | Follow peaks about 145 MB higher (central), and 66–451 MB across the envelope. The daemon's follow is paced, but the memory is held while it runs. | Segment count and term-dictionary duplication (h) unchanged from S2's measured figures. |
| B. Shared 64 MiB budget, so whichever buffer fills first ends the segment | About 2.2× as many segments at the central estimate, so more term-dictionary entries duplicated across segments. S2's dictionary is most of its index, so the term index grows, by an amount M1 measures. More merge work to get back to steady state. | Follow memory stays where S2 measured it. |
| C. Spill sorted trigram runs to a scratch file within a range, merged at flush | New code, and a scratch file in the index directory to clean up. | Both: S2's segment sizes and S2's memory. |

**Recommendation: A**, if M1 measures follow's peak RSS under 512 MiB on `$HOME`.
It is the fastest and the simplest. B is the most frugal with memory but costs
density, which outranks memory here. C is the most code.

**Fact that would change it:** M1 measuring A's peak above 512 MiB, or B's term
index growing by less than 3%. Then take B. If neither A's memory nor B's
density is acceptable, take C.
