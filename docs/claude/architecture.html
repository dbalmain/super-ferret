The measurement that reframes the project

Before any of the design below, the number that has to be absorbed: on the corpus this tool is being built for, ripgrep already answers the hardest query shape in 50 milliseconds. The premise that does not survive

"Build a trigram or n-gram content index so that regex search over my code is fast." Case B kills it. The query shape with no extractable literal — the one case where a literal-based scanner is supposed to degrade to a full scan — costs 50 ms, identical to the literal case, because .gitignore pruning has already reduced the input to 5.73 GB and 32 threads eat that at multiple GB/s. An index lookup, posting intersection, candidate-set materialisation and per-candidate verification pass cannot be made to happen in materially less than 50 ms on cold structures, and it will be slower the first time after boot. There is no latency win here, at this corpus size, ever.

Two second-order claims fall with it. "The index will save I/O" — case C shows the full-corpus scan is I/O-bound at one core's worth of CPU, reading bytes nobody wants indexed anyway; exclusion, not indexing, is what saves that I/O. And "153 GB is a big corpus" — it is 5.73 GB of corpus wearing a 147 GB costume.

The honest cold-cache caveat

The cold-cache argument is the weakest of the five and should not be leaned on. The cold number available is 0.65 GB/s over the full 153.2 GB measured — a mostly-sequential read of large binaries. A cold read of 73,565 small files is a different access pattern and no measurement of it exists unknown. On NVMe with high queue depth it may be far better than 8.8 s; on a fragmented tree it may be worse. This is the first experiment to run (see §10, stage 0): drop caches, scan the 5.73 GB tier, and get the number. If cold scan is under ~1 s the cold-cache argument dies too and the project narrows to documents, metadata and ranking.

What this does to the engineering priorities

M1's own conclusion, and I agree with it without reservation: at this scale the design problem is not posting-list compression, and it is not query planning either. Ranked by how much a wrong answer costs:

ConcernCost of getting it wrongWas it the plan?

That inversion is the finding. It does not mean the index is not worth writing — he is writing it to learn the algorithms, and that is a legitimate and sufficient reason on its own. It means the index must not be the thing the product's usefulness rests on, because on this corpus it demonstrably is not. Build the index because it is interesting and because the document tier genuinely needs it. Build the exclusion engine, the extractor pipeline and the politeness budget because those are what determine whether the tool is used.

Verdict

Build Super Ferret as a document-and-metadata search engine with a first-class scan fallback, not as a grep replacement. The inverted index earns its keep over extracted text (PDF, Office, email, OCR) and over metadata; over source code it is a convenience layer in front of a scanner that is already fast enough, and the query planner should be honest enough to route to the scanner when the scanner wins. That routing decision — §5 — is the most novel part of this design, and it exists only because the measurement was taken.

Where the no-unsafe posture bites

Four techniques in this design would force an exception. Each is avoidable, and I recommend avoiding all four in the core.

TechniqueWhy it needs unsafeRecommendation
mmap of index segmentsA memory-mapped file is not a sound &[u8] in Rust's model: another process can truncate or rewrite it under you, which is UB. Every mmap crate exposes this as unsafe.Confine it. One small leaf crate with unsafe_code = "allow", wrapping memmap2, with the soundness argument written down (index files are append-only and never truncated in place; a segment is unlinked only after every reader has dropped it). Everything else in the workspace stays forbid. This is the one exception I would actually take.
Raw syscalls: statx, fanotify, posix_fadvise, SCM_RIGHTSFFI into libc is unsafe by definition.Avoid the exception. rustix provides safe wrappers over all four, and on Linux it can use raw syscalls with no libc at all. Take the dependency; do not write the FFI.
Zero-copy posting decode via transmute / bytemuck::cast_sliceAlignment and validity invariants.Avoid. zerocopy proves the invariants at compile time with derives and no unsafe at the call site. Where alignment cannot be guaranteed, read unaligned via u32::from_le_bytes on a 4-byte slice — LLVM compiles that to the same load.
SIMD-accelerated decode (bitpacking, SIMD-BP128)Intrinsics are unsafe; runtime feature detection doubly so.Do not do this in v1. It is a density-neutral speed optimisation on a tier where speed is already demoted (N3, N4). If it ever matters, std::simd or a vendored leaf crate, same confinement pattern as mmap.
Posture recommendation

Workspace lints stay unsafe_code = "forbid". Exactly one crate — call it ferret-mmap — downgrades to deny with a per-item #[allow] and a doc comment stating the invariant it relies on. If a second crate ever needs the exception, that is a design smell worth a day of thought first.

The recommended architecture

Five layers, each with a hard boundary and an independently testable contract. The shape is conventional — segment-based index, immutable segments, manifest commit — because R1 found that every long-lived Linux desktop search tool in the survey is Xapian- or Lucene-family, and nothing in M1 argues for novelty in that layer. The novelty, such as it is, lives in three places: the exclusion engine sitting ahead of the crawler, the query planner that is willing to route around its own index, and the politeness controller nobody has built.

Process topology

Three processes, one systemd user slice. ferretd holds the watcher, the queue, the in-process extractors, the segment writer and the merge scheduler. ferret-extract-* are pooled, long-lived subprocess workers — spawned once per format family, not per file, because LibreOffice-headless startup is reported in the hundreds-of-ms-to-seconds range estimate and must be amortised. ferret is the CLI/query client, which opens the index read-only and does not talk to the daemon — so a query works while the daemon is stopped, crashed, or being upgraded. That last property is worth more than it sounds: it means the search tool is never down.

Tiered index design

Four tiers. Each is separately buildable, separately droppable, and answers a named set of queries. The point of the separation is that tier 2 is the one whose existence is genuinely in doubt after M1, and the design must let him build tiers 0 and 1, measure, and then decide — rather than discovering at the end that the trigram index is load-bearing for the whole thing.

A second exclusion axis the path rules miss

Before sizing anything: the 5.73 GB post-exclusion figure is still not the text corpus. M1's exclusion was purely path-based. Look at what survives it:

55 files hold 72% of the post-exclusion bytes. A per-file size cap and a mime check are therefore worth almost as much as the whole path denylist, and cost one statx field. Recommendation: cap full-text indexing at 8 MB per file; above it, index metadata plus the first 8 MB, flag the document as TRUNCATED, and let the scan path answer regex over the tail. A 62 MB CSV is not a document; it is a table, and a search engine that pretends otherwise produces a term dictionary full of one-off numeric tokens that inflate every structure downstream.

Caveat on that cap

This is a judgement, not a measurement: the 8 MB threshold has no empirical basis and should be a config value with the default chosen after looking at the actual size histogram. M1's distribution table says 527k of 578k files (91%) are under 256 KB measured, so almost any cap in the low megabytes captures essentially every real document; the cap exists to catch the tail, not to tune recall.

Tier verdict

That combination is ~89 MB on his corpus and every piece of it is justified independently of whether the trigram tier ever gets built.

Query planning and execution

This is the heart of the design and the part that is actually novel, because it exists only as a consequence of the measurement. Every other indexed search tool assumes its index is worth consulting. On this corpus that assumption is false often enough that the planner must be able to decline its own index, and must do so from a cost model rather than a heuristic bolted on later.

The 177× gap is the whole game

Warm and cold differ by roughly 177× estimate. Every argument for the trigram index lives in the cold regime and every argument against it lives in the warm one. Regex derivation: what the planner does with the HIR

Do not write a regex parser. Walk regex_syntax::hir::Hir and implement Cox's9 match/exact/prefix/suffix lattice as a fold over it. The crate is MIT/Apache, Unicode-correct, and gives you a clean recursive tree with Literal, Class, Repetition, Concat, Alternation and Look nodes. The genuinely novel work is the lattice and the boolean-query simplification, not the parsing.

Two correctness rules that are easy to get wrong

Rule 1 — regex matches original bytes, and the UI must say when it cannot

R8 calls this the real design trap and it is. Normalisation — encoding conversion, NFC, dehyphenation, whitespace collapse — is mandatory for usable full-text search and every step of it moves byte offsets. A user typing a regex expects it to match the bytes in the file.

The decision, made explicitly rather than by default: T1 is built over normalised text; T2 and every verify pass operate on original bytes. Two streams, deliberately. Regex results always carry a real byte offset into a real file, and are always re-verified against those bytes. Recoll and most FTS tools quietly reach the same place by degrading regex to "grep the original file at query time" — that is honest, and it is what R5 already is.

The exception has to be surfaced, not hidden: for an extracted document there are no original bytes. A regex over a PDF matches the extracted text, which is a normalised, dehyphenated, reading-order-approximate proxy of the document. Label those results in the output (a marker on the hit, not a footnote in the man page), because a user who opens the PDF and cannot find the bytes we reported will conclude the tool is broken, and will be right to.

Rule 2 — filters are only valid where the necessary condition holds

A trigram or fuse filter answers "can this file possibly match". That is a necessary condition for a positive match and for nothing else. ugrep-indexer documents exactly this limitation19: its indexed path is incompatible with -v/invert-match, --filter, PCRE mode and fuzzy matching upstream. Make "can this query be filter-accelerated at all" an explicit predicate on the query, checked before the planner reaches the cost model — not an assumption. Invert-match and fuzzy go straight to R5.

Extraction and the plugin interface

The plugin interface has to be settled before the first plugin is written or every plugin becomes a one-off integration. It is also, simultaneously, the sandboxing boundary and the licence boundary — which is the reason the answer is as clear as it is.

The licence ledger forces the shape

R8's survey6 is blunt: the best-in-class PDF and legacy-Office parsers are all copyleft or worse. poppler is GPLv2, MuPDF is AGPL-or-commercial, LibreOffice is MPL-2.0, calibre and notmuch are GPLv3, readpst/libpff is GPLv2. The permissive alternatives trade away either build complexity (pdfium: BSD-3 / Apache-2.0, but vendoring Google's prebuilt shared library is not a small dependency) or extraction fidelity (pure-Rust lopdf / pdf-extract lag noticeably on ligatures and CID fonts).

Static-linking GPL code into an MIT/Apache binary is the mistake to avoid. Invoking a GPL binary at arm's length as a subprocess — the way a shell script would — does not propagate the licence; this is the standard, widely-relied-on reading of the FSF's own distinction between linking and mere aggregation upstream21. So the subprocess boundary does triple duty: crash isolation, sandbox, and licence firewall. That is an unusually clean alignment of three separate concerns onto one mechanism, and it is why option 2 wins on its own merits rather than by elimination.

The extracted-text cache is not optional

Two reasons beyond avoiding re-extraction, and the second is the one that matters over the life of the project. Snippets: rendering a result needs the actual text, and without a cache every rendered PDF result re-opens and re-parses the source — exactly the expensive path the index existed to avoid. Queue overflow, and the reconciliation backstop

When the per-instance queue (16,384 events here measured) fills faster than userspace drains it — a git checkout across branches, a large rsync, a cargo build touching 260,695 object files measured — the kernel drops events and delivers one IN_Q_OVERFLOW16 pseudo-event with watch descriptor −1. You cannot know which files were affected. The only correct response is to re-crawl and diff, scoped to the affected subtree if you can bound it and to the whole tree if you cannot. An indexer that logs a warning and continues will silently drift out of sync forever.

Two structural facts make this worse than it sounds. First, Linux has no USN journal. NTFS maintains a persistent, queryable, append-only log of every metadata change, so Windows Search can catch up after being offline by reading the backlog. inotify and fanotify are purely event-streaming: anything that happens while the daemon is not running is gone. This is not a fixable-with-better-code gap; it is an absent primitive on ext4 and xfs. btrfs send --no-data and zfs diff are the closest Linux analogues and are available only on those filesystems. Second, no notification mechanism works at all on NFS, SMB, or most FUSE mounts — those need a periodic crawl, full stop.

Design consequence: reconciliation is always on

Because of both facts, a periodic metadata-only reconciliation crawl is not a fallback — it is a permanent, always-running backstop, and it is cheap enough to be one: 1.24 s for 578,200 files warm measured. Run it on daemon start unconditionally, then on a low-frequency timer, comparing (dev, ino, mtime, size) against doc values. Every wrong answer the watcher can give — the create race, the overflow, the network mount, the unclean shutdown — is caught by this one mechanism, and it costs a rounding error.

And then surface it. R8 identifies the compound risk as the biggest in the whole subsystem: change detection can silently miss events and extraction can silently produce garbage, neither crashes anything, neither logs anything anyone reads, and the result is an index quietly diverging from the filesystem for months in a way indistinguishable from working correctly — until a user searches for something they know exists, gets nothing, and files a bug with no reproduction. The mitigation is not a better watcher. It is ferret status reporting N files failed extraction, M pending, last full reconciliation T ago, K quarantined as a first-class user-visible answer.

Save-storm debouncing

Atomic-save-via-rename — write temp, rename over the original, which vim and most IDEs do — produces several inotify events per logical save: an IN_CREATE for the temp file, an IN_MOVED_FROM/IN_MOVED_TO pair, sometimes an intervening IN_CLOSE_WRITE. Naively re-extracting per raw event wastes work and can race: indexing the temp file's transient content under the final filename.

The other special cases that must be handled at this layer, all from R8: hardlinks and bind mounts need (st_dev, st_ino) dedup or the same content is indexed twice under two paths, polluting ranking with duplicate hits — index once, list both paths as aliases. Symlinks are not followed by default, matching fd and find; if followed, track the target's (dev, ino) against cycles. Huge single files are no different at the watch layer but must not trigger full re-extraction on every touch — that is the size cap from §4, and it belongs in the indexing layer, not here. The change-detection layer's only job is to report "this inode changed" correctly.

The activity-based backoff nobody has built

Genuine gap in the prior art

R1 read the source trees of Baloo, Tracker/LocalSearch and Recoll and found that none of the three implements input-idle detection or foreground-activity detection — no X11/Wayland idle time, no watching for foreground CPU spikes — that pauses or resumes indexing based on interactive activity, as opposed to battery state (Baloo only) or raw scheduling priority (all three) upstream. "Don't index while I'm compiling" is not a pattern to copy from anywhere. It is new design work.

R1 also names the uncomfortable possibility this has to answer: Baloo's complaints may not be a scheduling failure at all, but a total work volume problem — extracting a million files' content is simply a lot of CPU-seconds regardless of scheduling class — or an extractor correctness problem, where one file hanging inside a poppler call burns its low-priority slice forever. R1 could not distinguish those two explanations and calls it the most important open question it surfaced. Note that this design attacks both directly: exclusion cuts total work volume by 25×, and the poison-file quarantine plus per-file timeout bounds the hang. That is a claim worth testing, not asserting.

Two deliberate choices in that sketch. It never uses all cores, even fully idle — an indexer that pins 32 threads the moment you walk away is exactly the behaviour that gets a tool uninstalled, and the marginal wall-clock gain over half the cores is small next to the cost of being wrong about idleness. And it uses PSI (/proc/pressure/io) rather than load average or raw utilisation, because PSI measures stall time actually experienced rather than a proxy for it — it is the one signal that directly answers "is anything waiting on the disk right now", which is the question the controller is really asking.

Crash safety, atomic swap, and near-real-time flush

This part is solved. Copy Lucene's commit protocol12 close to verbatim rather than re-deriving it — R6 says so and it is right. What is not solved, and what this section actually has to work out, is how the merge scheduler behaves when it is deliberately throttled to lose every contention it enters.

The commit protocol

Step 4 is what makes the rename itself durable across a power loss on Linux; omitting it is the classic bug in this protocol and it is invisible in testing because it only manifests on an unclean shutdown. Recovery is then trivial: read the manifest, open exactly the segments it names, and garbage-collect every segment file no manifest generation references — those are either half-written or superseded-by-merge leftovers, and the two cases need not be distinguished.

PropertyHow it falls out

mmap, and why it is not the automatic answer

The default: mmap for read-only, already-fsynced segments; buffered reads for anything still being written or on storage that might vanish. The page-cache-sharing benefit is real when most segments are read rarely and the OS manages eviction for free. But mmap has two costs worth naming explicitly rather than accepting because Lucene does it. Page faults are synchronous and opaque: a query thread blocks on disk inside what looks like a memory read, with no timeout, no retry, no accounting — the core of the widely-cited 2022 argument for buffer-pool-managed I/O20 paper. And the failure mode that actually matters for a desktop tool: a USB drive yanked or a network mount dropped mid-mmap raises SIGBUS on the next page fault, which kills the process, where a read()-based design gets a catchable EIO. Wrap mmap access with SIGBUS handling, or simply do not mmap anything not proven to be on stable local storage. Use MADV_RANDOM on dictionary and term-index files (defeating readahead that would otherwise pull in irrelevant neighbours) and MADV_SEQUENTIAL during merges.

This is also the one place the unsafe exception is taken (§2): a single leaf crate wrapping memmap2, with the soundness argument written down — segment files are append-only, never truncated in place, and unlinked only after every reader has dropped them.

NRT under a throttle

The standard Lucene NRT model applies unchanged on the write path: a change event re-tokenizes one file, appends to the in-memory buffer, and the buffer is exposed as a searchable segment before it is flushed. That gives sub-second visibility of an edit without a commit. What changes here is the merge side, and it changes in one specific way: merge I/O now competes with the user's foreground disk activity, on purpose throttled to lose that contention — so merges must be rate-limited, not merely deferred.

The interaction that needs testing, not assuming

The merge scheduler and the backoff controller (§7) can deadlock each other in a soft but real way: the controller drops merge concurrency to zero whenever there is I/O pressure, and on a machine that is busy most of the day, segments accumulate without bound. Segment count degrades every query linearly. The fix is a floor, not a smarter controller: below some segment count — say 40 — merges are genuinely optional and the controller may starve them freely; above it, one merge thread runs at a hard-capped rate regardless of pressure, because an unmerged index eventually hurts the user more than a throttled merge does. Pick the floor by measuring query latency against segment count, which is a half-day experiment.

Verdict

Do not build this into the core, at any tier, in any form. Ship it as ferret semantic-index <path> — an explicitly opted-into subsystem scoped to a path or a content-type filter, entirely separate from the always-on lexical index. Default it to documents only: PDF, Office, email, notes. Never .rs, .c, .py by default, because semantic code search is a different and harder problem, and on code the lexical and structural paths are both cheaper and more precise.

At a curated 1–10 GB slice the entire feasibility picture inverts: first-embed drops from days to hours, the vector store drops to low single-digit GB even at fp32, and HNSW's RAM residency stops being a consideration at all. The lexical and semantic query paths meet only at a result-merging step (reciprocal rank fusion); neither has to be architecturally aware of the other.

Two supporting facts worth carrying. Incremental cost is not the problem — a normal day's file changes re-embed in seconds to minutes even CPU-only; it is exclusively the first full index, plus any wholesale re-embed forced by a model upgrade, which on a large corpus is effectively running the whole job again. And the desktop-embeddable vector stores that exist today are independently documented to struggle well below this scale: sqlite-vec above ~1M vectors, DuckDB VSS near-OOM at 500K anecdote — the direct opposite of the "billions of vectors on a laptop" marketing framing. LanceDB and usearch are the more plausible candidates on architectural grounds, but R9 found no independent at-scale verification of either unknown.

The one thing genuinely worth revisiting later: learned sparse retrieval (SPLADE, not BM42) reuses the inverted index this design already has instead of standing up a separate ANN subsystem, at the cost of a transformer pass per document comparable to dense embedding. That is the cheapest possible on-ramp to semantic behaviour for a project that has already built T1 — but its recall claims need verification against his own corpus before being trusted. ColBERT-style late interaction is a reranker over a small candidate set and never a primary index; its storage scales with token count and would run into terabytes here.

Ferret and Super Ferret: what carries over

He wrote Ferret — the Ruby port of Lucene 2 — and has said he would enjoy building it again in Rust while doubting it is the right engine for this job. That instinct is correct, and it is worth being precise about which part of it is correct, because the answer is not "throw it away." The distinction that matters

Every row marked replace is an encoding. Every row marked keep is a write model. Rewriting Ferret in Rust would produce a better Ferret and not this product, because it would carry the encodings forward and those are exactly the parts that have moved on twenty years. The reverse is also true and less obvious: the segment-and-merge mental model he already has is not a legacy constraint to escape, it is the thing that lets this design do near-real-time updates without a mutable posting format. The enjoyable part — implementing codecs, skip structures, segment merge — is entirely preserved. It is the file format that changes.

A staged build plan

The ordering principle: each stage ships something usable, and each stage tests the assumption that would invalidate the next one. That is not generic agile advice here — it is a direct consequence of M1. The riskiest assumption in this whole project is "a content index is worth building", and the plan is arranged so that assumption gets tested by stages 0 and 1, before a single posting list is written.

Why stage 1 is the smallest genuinely useful thing

Because it is a complete search tool. Filename and metadata search is instant and free at this scale — a full crawl is 1.24 s measured — and content search routed to a well-optimised scanner answers in 50 ms warm measured. Neither plocate nor updatedb is installed on this machine measured, so stage 1 fills a real gap on day one rather than duplicating something. And it makes the strongest possible test of the project's premise: if a month of using stage 1 does not produce a concrete query he wished had been indexed, stages 3 and 5 are being built for the pleasure of building them — which is a fine reason, and worth knowing is the reason.

Commit discipline

Stages 3 and 5 are each long enough that their first green boundary is weeks away. Write the design notes and the size measurements into the repository as they are produced, not at the end — the analysis is the expensive half and the least recoverable. A design can be re-derived only from scratch; code can be rewritten from a design.
