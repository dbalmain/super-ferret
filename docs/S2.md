# S2 — Content index

M0 design, 2026-10-06. Code baseline: `f722d1f` on `wt/s1b` (S1b through its
end-of-sprint review). This is a design for review, not yet a build
specification. ROADMAP gates every structure on a review of the
`CandidateSource` seam, so nothing below is built until Dave has read
[§ The candidate seam](#the-candidate-seam). The new questions are D60–D64 in
[DECISIONS.md](DECISIONS.md), and each section names the brief it depends on.

The shape in one paragraph. `ferret-text` gets a fast, allocation-free tokenizer
whose output is identical to today's reference one. `ferret-index` gets
immutable segments over disjoint DocId ranges: a front-coded term dictionary,
doc-id postings in intpack's `pfor128skip`, and no positions (D6). The index
**follows** the catalog. After each catalog publication the writer tokenizes the
live documents the index does not yet cover, in DocId order, and commits a
segment through an index manifest of its own. Queries pin a catalog view and an
index manifest together. Every content atom becomes a tree of cursors over
DocIds, and each element carries a certainty, yes or maybe. That lets exact
postings, inexact filters, S3's trigram structures and not-yet-indexed documents
all compose under one AND / OR / NOT algebra. Maybe-documents are verified
against their bytes once per document. Rows still come out per path (D15).

**Where S2 should start.** The brief asks whether S2 starts at the trait. It
starts there for _review_, as ROADMAP says. The first _build_ slice, though, is
the tokenizer plus a content census of the real tree (M1). There are two
reasons. The trait has no second caller until postings exist, and the house
style forbids building the abstraction first. More importantly, one unmeasured
input dominates every other in the cost model: how many bytes of text the
catalog actually holds. Nobody has measured it (the
[DECISIONS preamble](DECISIONS.md#status) records that stage 0 was never run).
The census is a pass over columns the catalog already stores.

## Baseline constraints and binding decisions

[GOALS.md](GOALS.md) asks for a minimal index, niceness to the CPU, and regex
for code, and says "CPU indexing impact and index size take priority over
performance". [DESIGN.md](DESIGN.md) says to build the structures rather than
adopt them. It also says `ferret-index` knows doc ids and byte strings and never
files, that the planner never sees a format, and that the crate graph is
enforced by `crates/ferret/tests/layering.rs`. The licence is
`MIT OR Apache-2.0` (D12), which intpack shares.

These answered decisions bind S2. This design cites them and does not reopen
them:

## The candidate seam

This is the section ROADMAP gates on.

### What a candidate is

A candidate is a **`DocId` with a certainty**. `Yes` means the atom certainly
holds for this document's content. `Maybe` means it may, and the verifier
decides. Absence from the stream means `No`.

A candidate is not a document plus offsets. D6 rules out positions, so no
structure can produce offsets; the verifier produces them as a by-product when
it runs. Nor is it a bitmap. A bitmap is one _implementation_ of a cursor, used
for liveness, uncovered documents and large materialised unions. Fixing the
bitmap as the interface would force every common term to be materialised, at
1.25 MB per atom at 10M docs. It would also throw away the skip tables that
intpack already built.

DESIGN gave each source an `exact` flag. Why certainty per element instead? A
source-level flag cannot say "this source is exact for most documents but has
not seen these ones". That case is real from day one, because the existing
catalog has 8M documents and no index, and it recurs whenever the tokenizer
changes. With a certainty on each element, "not yet indexed" is just one more
source: a `Maybe` bitmap of uncovered live documents, unioned under every
content atom. The same mechanism carries S3's inexact filters. Negation also
gets a correct three-valued meaning, which a per-source flag gets wrong (see the
table below).

### The Rust shape

The style guide asks for an `enum` with one arm per structure, not trait
objects, and DESIGN already expected this ("the likely shape is an enum of the
known structures"). So the "trait" is two enums and their `match` arms, in
`ferret-index`. `ferret-query` depends on these types and on nothing else in the
crate, which is what DESIGN's graph comment already says.

```rust
/// One content atom at the index level: byte strings, never paths.
/// Query-level atoms (a phrase, a regex) compile into trees of these.
pub enum Atom<'q> {
    /// One ferret-text token, already normalised.
    Term(&'q [u8]),
    /// Three raw bytes. No S2 source answers it; S3's do.
    Trigram([u8; 3]),
}

pub enum Certainty { Maybe, Yes }

/// What a source can do for an atom, and roughly what it costs.
pub struct Estimate {
    /// Upper bound on documents the cursor yields (Lucene's `cost()`).
    pub docs: u64,
    /// Whether every yielded document is `Yes`.
    pub exact: bool,
    /// Whether the source can enumerate its documents. A per-document
    /// filter cannot; it can only be probed.
    pub enumerable: bool,
    /// Bytes the cursor is expected to read, for ordering sources.
    pub bytes: u64,
}

/// One structure registered for a pinned index view.
pub enum Source<'v> {
    /// S2: term postings over one manifest's segments.
    Postings(postings::View<'v>),
    // S3: TrigramPostings(trigram::View<'v>),
    // S3: DocFilter(docfilter::View<'v>),  per-document trigram/term filters
}

impl<'v> Source<'v> {
    /// None: this source does not answer this atom.
    pub fn estimate(&self, atom: &Atom) -> Option<Estimate>;
    /// Ascending DocIds. Only for an enumerable estimate.
    pub fn cursor(&self, atom: &Atom) -> Cursor<'v>;
    /// Membership by id, for a source that is not the driver.
    pub fn probe(&self, atom: &Atom) -> Probe<'v>;
}

/// intpack's `next_geq` semantics (Lucene's `advance`): the cursor stays on
/// the returned element, and targets never decrease.
pub enum Cursor<'v> {
    Postings(postings::Cursor<'v>),   // concatenated across segments
    Bits(bits::Cursor<'v>),           // liveness, uncovered docs, wide unions
    And(Box<[Cursor<'v>]>),           // leapfrog
    Or(Box<[Cursor<'v>]>),            // min-heap, or bits when wide
    AndNot(Box<(Cursor<'v>, Probe<'v>)>),
    Filter(Box<(Cursor<'v>, Probe<'v>)>),
    Empty,
}

impl Cursor<'_> {
    pub fn next_geq(&mut self, target: DocId) -> Option<(DocId, Certainty)>;
}

/// Answers "is doc d in this atom?" with No, Maybe or Yes, for increasing d.
pub enum Probe<'v> {
    Cursor(Cursor<'v>),       // a postings list, probed by next_geq
    // S3: DocFilter(docfilter::Probe<'v>),
}
```

`Cursor::next_geq` returns the certainty with the id. A postings cursor always
says `Yes`. A bitmap cursor says whatever it was built with. The composite arms
combine certainties under Kleene's three-valued logic:

| Arm            | Yields `d` when                             | Certainty of `d`                                |
| -------------- | ------------------------------------------- | ----------------------------------------------- |
| `And`          | every child yields `d`                      | `Yes` if all are `Yes`, else `Maybe`            |
| `Or`           | some child yields `d`                       | `Yes` if any is `Yes`, else `Maybe`             |
| `AndNot(a, b)` | `a` yields `d` and `b`'s probe is not `Yes` | `a`'s if `b` says No; `Maybe` if `b` says Maybe |
| `Filter(a, p)` | `a` yields `d` and `p` is not No            | as `And`                                        |

`AndNot` is the only negation inside the index, so a NOT is always relative to
something enumerable. Some queries have a content part that is a bare negation,
such as `ferret search NOT text:foo ext:rs`. Their positive side is a `Bits`
cursor over the live documents. That is correct, and it costs one bitmap of 1.0
MB at 10M (an estimate: 8.13M documents in the fixture / 8). The bitmap is
already resident for liveness.

### Liveness, coverage and the cursor tree a query sees

Postings name every DocId a segment ever indexed. Two bitmaps turn them into the
query's answer, both over `[0, next_doc)` of the pinned catalog view:

- **live** is built once per pinned catalog generation from `Catalog::docs()`
  (the base sequence column plus the overlay). Each overlay generation patches
  it copy-on-write, as `NameIndex::adopt` does for names. It is estimated at 1.0
  MB and 10–20 ms to build at 10M: one decode of the DocId sequence column,
  about 8M values. This has not been measured.
- **uncovered** is the set of live documents the pinned index manifest has not
  tokenized: live documents outside every segment range, plus the manifest's
  unreadable set ([§ Coverage](#coverage)). It is usually empty, and holds 8M
  documents during the first build.

Every content atom compiles to:

```text
Or( source-tree(atom), Bits(uncovered, Maybe) )
```

The query's whole content tree is then wrapped in `Filter(tree, live)` once, at
the top, rather than per atom. When `uncovered` is empty, the `Or` arm is
dropped at plan time.

### How S3 and the per-document filters fit, unchanged

- **Trigram postings (D8 C).** S3 derives a Cox trigram query from a regex,
  which is an AND/OR tree of trigrams. The planner compiles that tree into
  `And`/`Or` cursors over `Atom::Trigram`. A new `Source::TrigramPostings` arm
  answers each one with `exact: false`. The regex itself is the residual the
  verifier runs on `Maybe` documents. Nothing in the seam changes: S3 adds one
  `Source` variant, its `estimate`/`cursor`/`probe` arms, and its cursor
  variant.
- **Per-document trigram filters (D8 B) and term filters (D6).** A binary fuse
  filter per document answers "might doc d contain trigram t", but it cannot
  enumerate. It registers with `enumerable: false` and supplies a `Probe` arm.
  The planner never drives from it. Some enumerable source drives instead: a
  postings atom elsewhere in the conjunction, or failing that the live bitmap.
  The filter then rejects documents from the driver's stream through `Filter`. A
  pure regex with only per-document filters drives from `live` and probes every
  live document, which is exactly D8 B's cost model.
- **Positions, if an experiment earns them.** Positions would make a phrase
  exact. They would fit as a source answering a future `Atom::Phrase(&[&[u8]])`
  and yielding `Yes`. Without that source, the planner compiles a phrase to an
  `And` of terms with certainty `Maybe`. The atom variant is the only change,
  and it is additive.

One thing would _not_ fit without a change: a structure that answers by scoring,
such as top-k with block-max WAND. Scoring needs a score, not a certainty.
Ranking is not in S2's scope, and D61 decides whether term frequencies are
stored at all.

### Composition with S1's name and metadata predicates

Content atoms live in DocId space. S1's atoms (`word`, glob, `re:`, `path:`,
`ext:`, `name-term:`, `size:`, `mtime:`, `type:`) live in name and inode space.
A row is `(NameId, InoId, DocId?)`. D4's recommendation stands: a content atom
is evaluated on the row's document. A row with no document makes every content
atom false, so `NOT text:foo` holds for it. Rows with no document are
directories, symlinks, binary or over-cap files, and content faults.

The planner splits the boolean expression into content subtrees and name
subtrees. It then picks a **driver side** for each top-level conjunction:

1. **Content drives** when its estimate is small. The content tree yields
   `(DocId, Certainty)` pairs, and `DocId → [InoId]` (D30's lazy inverse) maps
   them to inodes. The existing evaluator applies the name and metadata atoms
   per name, using S1's `InodeScan` machinery entered at known inodes instead of
   all of them. The cost is `docs × (inodes per doc) × names per inode`.
2. **Names drive** when a name atom is selective. D54's counted name postings
   give the count for free, and `HeapScan` gives a literal. The name side yields
   rows. Their DocIds are collected, sorted and deduplicated (at most one `u32`
   per hit), then leapfrogged against the content cursor with `next_geq`. This
   is the plan for `ferret search Cargo.toml text:serde`.

The comparison is between two estimates. The content side's is the driver's
`Estimate::docs` times 1.2 inodes per document, the 10M fixture's ratio (9.96M /
8.13M). The name side's is D54's, which already exists.

A top-level `OR` across sides (`text:foo OR ext:rs`) runs each disjunct's plan
and deduplicates rows by `NameId`, in a bitmap over the epoch's names (10M bits,
1.25 MB). No other cross-side shape is needed, because a `NOT` across sides is a
per-row test once the rows exist.

**Verification** comes last, and it happens per document, not per path. Each
`Maybe` document that survived the name side is verified once:

1. Open one of its live paths, the row's own first.
2. Check the D55 carry-over key against the catalog row.
3. Read the file, tokenize it once, and evaluate the whole content expression on
   it. Evaluating the whole expression rather than only the `Maybe` atoms is
   simpler, and it is required for uncovered documents, where every atom is
   unknown.
4. Record yes or no for every row that shares the document.

A key mismatch means the file has changed since the catalog saw it. The row is
dropped, never reported from stale data, and the path is queued for the writer
(DESIGN § Query, step 4). Documents are verified in DocId order, which is close
to path order for a first crawl (D4). Foreground queries read unpaced.

## Tokenizer

`ferret-text` already has the D9 tokenizer at version 1, which D54's name terms
use. Its contract stays. Its implementation is replaced for content-scale
throughput, and the old implementation becomes the test oracle.

### Contract

- **Runs.** A run is a maximal sequence of Unicode alphanumerics and `_`. Every
  other character separates runs. Bytes that are not UTF-8 separate runs too:
  today's `from_utf8_lossy` turns them into U+FFFD, which is not alphanumeric. A
  Latin-1 `café` therefore yields `caf`. That is accepted, since a UTF-8 query
  could not match the raw byte anyway, and a file that is mostly not UTF-8 then
  yields few tokens rather than junk.
- **Parts.** Parts are split at `_`, at lower → upper, at UPPER → Upper-lower
  (the acronym rule: `HTTPRequest` → `http`, `request`) and at letter ↔ digit.
  The whole run is emitted first, then each part that differs from it. This is
  unchanged from today and from D9's example (`parseHTTPRequest2` →
  `parsehttprequest2`, `parse`, `http`, `request`, `2`).
- **Normalisation.** Lowercase with std's `str::to_lowercase`. That is
  `char::to_lowercase` per character except for `Σ`, which becomes `ς` at the
  end of a word (Unicode's Final_Sigma condition) and `σ` elsewhere. Each part
  is lowercased on its own, so a part is not always a slice of the lowercased
  whole: `ΑΣΒc` gives `ασβc`, then the part `ας`. There is no Unicode
  normalisation (NFC/NFKC) and no full case folding, so `ß` stays `ß`. Both
  would need tables std does not have, and the payoff is small for a corpus of
  code and notes. The ASCII path lowers letters with `| 0x20`.
- **Length cap.** A term is at most **64 bytes**, the same bound
  intpack-bench's extractor used for its corpus. A longer token is indexed as
  its first 64 bytes, cut at a character boundary, and its parts are emitted
  normally, each capped the same way. The cap is `ferret_text::cap`, which the
  content indexer applies to each token; `tokenize` itself does not cap,
  because D54's name terms match whole runs of any length through `has_token`,
  and capping there would silently break name search for longer names. A query token longer than 64 bytes is cut
  the same way and becomes `Maybe`, so the verifier checks the full token. This
  keeps postings exact for every token up to the cap, and correct beyond it.
  Truncating rather than dropping matters: a dropped token would make a long
  identifier findable only by a full scan.
- **No minimum length, no stop words, no cap on parts.** Single-character parts
  (`2`, `x`) are emitted. Their posting lists are long and dense, and pfor128
  stores those as bitset blocks when that is smaller, so the cost is bounded. M1
  measures whether hash-like runs (hex digests, base64, UUIDs) bloat the
  dictionary rather than assuming it. If they do, the fix would be a version-2
  tokenizer that indexes such a run whole and marks queries for its parts
  `Maybe`, decided on that number.
- **Versioning.** `TOKENIZER_VERSION` stays 1 if the new implementation is
  byte-identical to the old one, which is the plan. Segments record the version.
  A manifest whose version differs from the binary's is discarded and rebuilt
  through the ordinary coverage path ([§ Coverage](#coverage)).

### Interface

```rust
/// Streams tokens without allocating. `emit` gets each token's bytes, the
/// byte range of its run in `bytes`, and whether it is a whole run or a part.
pub fn tokenize(bytes: &[u8], scratch: &mut Scratch, emit: impl FnMut(Token<'_>));

pub struct Token<'a> { pub bytes: &'a [u8], pub run: Range<usize>, pub kind: Kind }
pub enum Kind { Whole, Part }
```

The phrase verifier needs the run range. It walks the part stream and reports
the byte span of a match, which is the offset a JSON result row carries.
`tokens()` and `has_token()` stay as thin wrappers for D54.

The fast path handles ASCII runs byte by byte. It classifies each byte through a
256-entry table, lowercases into a scratch buffer and finds part boundaries in
the same pass. A run that contains a byte ≥ 0x80 falls back to the per-`char`
path. The **target**, not a measurement, is 300 MB/s per core on ASCII source.
Today's implementation is estimated at 50–100 MB/s, since it allocates a
`String` per run and per token. M1 measures both.

### Tests

- **Oracle property test.** Today's implementation moves into the test module
  unchanged, as the specification. The new one must produce the identical token
  sequence on four kinds of input:

  - random bytes, from the house xorshift generator, as in `ferret-verify`'s
    tests;
  - random identifiers from a grammar of case runs, digits, underscores and
    separators;
  - random valid UTF-8 drawn from a table of multi-byte letters, digits and case
    pairs whose lowercase changes length (`İ`, `Σ`);
  - every truncation of each input at a random point, which cuts UTF-8
    mid-character.

  The test names its discriminating cases: an ASCII run with one non-ASCII
  letter in the middle, an acronym boundary, `__a__b`, a digit-to-letter
  boundary ending a run, a lone invalid byte between runs, and a part whose `Σ`
  is final in the part but not in the whole. `cap` has its own: 64, 65 and 200
  ASCII bytes, and a multi-byte character straddling byte 64.

- **Invariants on the same inputs.** Every emitted token is lowercase,
  non-empty and valid UTF-8, and lowercasing its run's input bytes yields it. Every part is a substring of the
  lowercased run. Tokenizing a token yields that token first.
- **Agreement between query and index.** For any document and any token it
  emits, `normalize_token(token)` is that token. For any substring of a document
  that is a whole run, the query compiler's plan for it finds the document.
- **A corpus from the real tree.** About 2,000 text documents are sampled by
  hash from Dave's catalog, the same sampling idea as intpack-bench's extractor.
  They go into the private corpus repository beside `~/w/find-compat`, each with
  its expected token stream as a golden file. The corpus catches what random
  input does not: minified JavaScript, lock files, Markdown tables and Nix
  hashes. It stays private, because the files are Dave's.
- **Throughput.** A `ferret-bench tokenize` command runs over the corpus. It
  reports MB/s for old and new, on ASCII and mixed input. It also reports
  tokens, parts and distinct terms per content byte, which the cost model below
  needs.

## Postings layout on intpack

`ferret-index` takes the dependency `ferret-index → intpack`, and DESIGN's crate
graph changes in the same commit to `ferret-index → ferret-text, intpack`. D59's
"facts" note said DESIGN once listed this edge although nothing used it. The
edge is within D11 and D59 A.

### What a posting holds

- **Doc ids**, as `pfor128skip` sorted lists, relative to the segment's first
  DocId. On intpack-bench's corpus this was measured at **9.61 bits/int**
  including the skip table, against Lucene's 10.36
  ([intpack results](intpack/results.html), `words.docs`). The estimates
  below use the earlier figure, 9.69, which is 0.8% higher; that difference
  changes no recommendation.
- **Frequencies are open: D61.** If kept, they are a parallel `pfor128` unsorted
  stream, measured at **4.33 bits/int** (`words.freqs`), which adds 45% to the
  doc stream. They buy nothing in S2, where the index is a candidate filter;
  they are ranking's input. The recommendation is to leave them out.
- **No positions** (D6). A phrase is an `And` of terms, `Maybe`, verified.
- **Singletons inline.** A term with document frequency 1 stores its DocId in
  its dictionary entry and has no postings bytes. Lucene did the same with its
  pulsing codec, and later with singleton inlining in its block-tree terms
  dictionary. On a code corpus most distinct terms are hapaxes, so this decides
  much of the dictionary's cost. M2 measures the fraction.

`next_geq` comes from intpack's `Cursor` trait as it is. The skip table is one
`(last_value, offset)` pair per full 128-block. A cursor finds the target block
by galloping from the current block, or by binary search from a fresh cursor.
Lucene's multi-level skip list is not needed: the table sits in place in the
list's bytes and costs 0.5 bits/int, already counted in the 9.69.

### Term dictionary

The dictionary is sorted, **front-coded blocks** of 32 terms. Each block holds
its first term whole and the rest as `(shared prefix length, suffix)`. Each
entry carries its document frequency (vbyte) and either the inlined singleton
DocId or the postings offset, delta-coded within the block. A **block index** of
every block's first term and byte offset is read into memory when the segment
opens. At an estimated 12 B per block, that is 0.4 B per term. A lookup
binary-searches the block index, then decodes at most 32 entries linearly.

This is the shape of Tantivy's `sstable` dictionary. It is also the house
precedent: D54's name terms are a sorted `PackedStrings` searched by binary
search, not an FST. ROADMAP lists the dictionary structure as an S2 decision. M2
measures the dictionary's share of the index, and the decision rule is this: an
FST is an experiment row only if the dictionary exceeds a quarter of index
bytes. That is the point at which an FST's suffix sharing could save more than
its considerable code costs. Under "build, not adopt", the FST would be ours.

Front-coded blocks also give prefix ranges for free, so a later `text:pars*`
atom needs no format change.

### Segment file

There is one file per segment, `index/seg-<first>-<last>-<n>.seg`:

```text
head      magic, format version, tokenizer version, codec ids,
          DocId range [first, last], term count, posting count,
          section table (offset, length, BLAKE3-128 per section)
blocks    the front-coded dictionary blocks
index     block index: first term and offset per block
postings  pfor128skip lists, concatenated, in term order
```

Section checksums follow the catalog's `checkpoint_checksum` convention. A torn
or corrupt segment is therefore an error from the section that reads it, never a
panic, which matches the catalog's reader contract (DESIGN § The catalog).

### Segments are disjoint DocId ranges

Every new DocId is above every existing one, because D36 B's counter never
decreases, and the index follows the catalog in DocId order. So every segment
covers a contiguous `[first, last]` range, and no two ranges overlap. This has
four consequences:

- A term's cursor across segments is a **concatenation**, not a merge. It walks
  segments in range order and offsets each list by its segment's `first`.
  `next_geq` skips whole segments by their ranges.
- Merging is concatenation plus purge: decode each input list, drop dead DocIds,
  re-encode. There is no doc-id remapping and no sort. DESIGN § Content already
  says that "merging segments concatenates ranges".
- The merge policy is **adjacent tiers**. That is the shape of Lucene's
  `LogMergePolicy`, not its `TieredMergePolicy`, which merges non-adjacent
  segments and would break range order. Tiers go by factors of 10 of posting
  bytes. When ten adjacent segments sit in one tier, they merge. Any segment
  whose dead fraction exceeds 25% is merged on its own. A query then sees
  roughly `10 × log10(postings bytes / smallest segment)` segments: about 40–60
  at 10M documents (estimate: 2 GB / 64 KB ≈ 3×10⁴, and log10 of that is about
  4.5). Both thresholds are starting points, measured in M3.
- A merge reads **liveness from the catalog view it pins**, and drops the
  postings of documents that are dead in that view. The merged segment's range
  still covers the dropped ids, since a dead DocId is never reused.

### Manifest and commit

`index/manifest` holds the format and tokenizer versions, the catalog
incarnation the index belongs to, the catalog `next_doc` it was built against,
the segment list (file, range, counts, checksum) and an **unreadable** set
([§ Coverage](#coverage)). It is replaced by write, fsync, rename and directory
fsync, the same protocol the catalog uses. A reader opens the manifest and every
segment it names, and keeps their descriptors. A merge can therefore unlink its
inputs while an old reader still uses them (D32).

The index has its own commit point, independent of the catalog's. One invariant
makes that safe: **a segment only contains DocIds below the `next_doc` of the
catalog view it was built from, and only documents live in that view.** A DocId
is never reassigned, so a committed segment is never wrong about a document. At
worst it holds a dead one, which liveness hides.

- A crash between the catalog's commit and the index's leaves documents
  uncovered, and the next follow pass covers them.
- A crash in the middle of a segment write leaves a temporary file, which the
  next writer deletes.

The invariant leans on one catalog property: a published DocId is never
un-published. `follow` only reads views the catalog has published, and S1+'s
sync order makes publication durable
([S1PLUS § Sync order and recovery](S1PLUS.md#sync-order-and-recovery)). As a
cheap guard against the property failing anyway (a catalog restored from a
backup, say), the manifest records the highest `next_doc` it was built against.
An index whose high water is above the catalog's `next_doc` is discarded on open
and rebuilt through coverage.

So there is no two-phase commit, no catalog record type for the index, and the
catalog stays ignorant of content, as DESIGN's ownership table requires.

The index lives under the catalog's directory and uses the catalog's writer lock
(`lock`), held by the same owner as the `WriterSession`. A catalog with a new
incarnation (an explicit reset) discards the index.

### Coverage

A live DocId is **uncovered** in two cases. It falls in no segment range: the
index has not tokenized it yet. That happens during the first build, after a
tokenizer change, and between a catalog commit and the follow pass that covers
it. Or it is in the manifest's **unreadable** set: the follow pass could not
read it with its catalog key intact, because the file changed or vanished after
the catalog saw it. Unreadable documents fall inside a segment's range but have
no postings. The writer does not retry them, and they leave the set when the
catalog drops the document.

Queries treat uncovered documents as `Maybe` for every content atom (§ The
candidate seam), so the answer is always correct. The cost is verification
reads, which `Stats` and `explain()` report. For an unreadable document,
verification finds the change and drops the row.

A query whose uncovered set exceeds a bound is refused with a typed
`IndexIncomplete { uncovered, live }` error, unless the caller passes
`--scan-uncovered`. The bound defaults to 10,000 documents, which is a
judgement. Without it, a query during the first build would silently become a
30-minute scan. Status reports coverage beside the catalog census.

D9's own estimate. M1 and M2 replace them.


As a cross-check, the research's freq-only T1 estimate was 5.1% of text, and its
R6 put positional indexes at 10–30%. Splitting adds about a third, which puts
this design between the two.

At **10M entries** the content volume is the unknown. The 10M fixture has 8.13M
documents (S1PLUS § Cost model, normalised). But it is deliberately
document-heavy, and its sizes come from a stat dump, not from text. So the index
size is given against content bytes, and M1's census picks the row:

| Indexed text | Index, docs only (6.8%) | With freqs (9.0%) |
| -----------: | ----------------------: | ----------------: |
|        10 GB |                 0.68 GB |           0.90 GB |
|        30 GB |                  2.0 GB |            2.7 GB |
|       100 GB |                  6.8 GB |            9.0 GB |

The dictionary grows sublinearly with text (Heaps' law), so at 100 GB these
figures are pessimistic by up to the dictionary's share. They are still large
against the 0.6 GB catalog. That is why segments are read on demand rather than
held resident (D64), and why the density questions (D61, and the hash-like token
rule) are worth their measurements.

## Query surface and planning

### Syntax (open, D62)

Today's grammar is a conjunction of name and metadata atoms, and a bare word is
a **name substring**. That meaning stays. Content atoms need a prefix, and
booleans need a syntax that survives the shell and agents. D62's recommendation:

```text
atom    = ... (S1's atoms) | "text:" ARG
expr    = and ("OR" and)*
and     = unary+
unary   = "NOT" unary | "(" expr ")" | atom
```

`OR`, `NOT`, `(` and `)` are whole arguments, as in find(1), which agents
already quote correctly. A quoted argument with spaces is one atom, as now.
`case:text:Foo` makes the content atom case-sensitive: the postings for `foo`
give `Maybe`, and the verifier checks the exact bytes.

### What `text:ARG` means

The argument goes through the same tokenizer as documents do.

- **One token with no parts** (`text:serde`, `text:request`) is a term query.
  Its postings are exact, because a document contains the token, as a whole run
  or as a part, exactly when the tokenizer emitted it. There is no verification.
- **One run with parts** (`text:HttpRequest`) matches the whole token's postings
  (`httprequest`, `Yes`) **or** an `And` of the parts (`http`, `request`,
  `Maybe`), verified as a part sequence. It finds `HttpRequest`, `httprequest`,
  `parseHttpRequest` and `http_request`, which is what D9's splitting was for.
  The common case, the exact identifier, needs no read.
- **Several runs** (`text:"http request handler"`, `text:foo.bar`) make a
  phrase: an `And` of every part, `Maybe`. It is verified by tokenizing the
  document and finding the query's part sequence contiguously in the document's
  part stream, with any separators between. Matching on parts makes this
  independent of how the identifier was spelled, so `requestHandler` matches
  `text:"request handler"`.

The phrase matcher runs `ferret-text` over the bytes, so `ferret-verify` takes
the edge `ferret-verify → ferret-text` (a std-only leaf). The alternative,
lowering a part sequence to a regex, would restate the tokenizer's boundary
rules in a second language, and the two would drift.

### Planning order

1. Parse into the boolean tree, and split it into content and name subtrees.
2. Compile each content atom into its cursor tree, and ask every registered
   source for an `Estimate` per index atom. S2 has one source.
3. Within an `And`, sort the children by `Estimate::docs`. The smallest
   enumerable child drives, and `next_geq` probes the rest, in the order
   Lucene's conjunctions use. An `Or` materialises into a bitmap cursor when it
   has more than 64 children or its summed estimate exceeds `live / 32`. Both
   thresholds are starting points for M4's measurement.
4. Pick the driver side for each top-level conjunction, content or names, by
   comparing the two sides' estimates (§ Composition).
5. Map documents to rows, apply the name and metadata atoms, verify `Maybe`
   documents and emit rows (D15).

`explain()` prints the chosen driver, each atom's estimate and certainty, the
uncovered count and the verification count. The query log records them (DESIGN §
Experiments and metrics), and M4's latency classes come from it.

## Writer and daemon seam

### The content flow (D63)

The index **follows** the catalog rather than being fed by the crawl, which is
D63's recommendation A. The S1b writer queue is unchanged up to publication.
After each catalog publication the writer's turn continues:

```text
refresh / index_change      (unchanged: crawl, hash, decide DocIds, commit)
   → index.follow(view, budget)
        todo = live(view) ∖ covered(manifest) ∖ unreadable(manifest)
        for doc in todo, ascending:
            pick a live inode; open it by path under the observed root handles;
            fstat must equal the catalog row's D55 key; read; fstat again;
            tokenize into the segment buffer (term → DocIds, appended in order)
            stop at the budget: bytes read, buffer size, or a pause request
        write the segment, fsync, publish the manifest
   → index.merge_if_needed(view, budget)
```

DocIds are taken in ascending order, so the segment buffer is append-only per
term. There is no sort and no remapping, and memory is bounded: the buffer
flushes at 64 MiB of buffered postings, an assumption for M3 to tune. The same
code serves the first build, a tokenizer change, an index deleted by hand, and
the steady state, since all four are "cover what is uncovered".

This shape costs one extra read. Content that is new to the catalog is read
twice: once to hash it, and once to tokenize it. In the daemon's steady state
the second read is of the file the crawl read moments earlier, which is in the
page cache. In a first bulk build it is a second pass over every text byte. D63
has the arithmetic and the alternative, which is to tokenize during the hashing
read.

Reads by path go through the same `openat(O_NOFOLLOW)` and `(dev, ino)` checks
as the crawler (D21), the same per-thread nice 19, and the same shared byte
pacer (S1b M6). `follow` is therefore background bulk work under the existing
controller and battery rules. A fault (the open or read fails, or the key does
not match) puts the document in `unreadable`. It is never a coverage fault for
the catalog.

### What S5 needs, and no more

S5 owns keeping postings current from change events. The seam it needs is three
calls and one status block, on an `IndexWriter` that the engine owns beside the
`WriterSession`:

```rust
impl IndexWriter {
    /// Covers uncovered live documents of `view`, up to `budget`, publishing
    /// at most one segment. Returns what it did and what remains.
    pub fn follow(&mut self, view: &Catalog, budget: Budget) -> Result<Follow, Error>;
    /// One merge step, if the policy wants one, under `budget`.
    pub fn merge_if_needed(&mut self, view: &Catalog, budget: Budget) -> Result<Merged, Error>;
    /// The manifest a query pins with this view.
    pub fn manifest(&self) -> Arc<Manifest>;
}
```

- `Engine::pin()` returns a catalog view and the index manifest together, so a
  query never pairs a view with a manifest from another incarnation.
- The writer calls `follow` after each publication and at idle boundaries (D51
  A), with a budget the controller sets. S5 decides how often and how much. S2
  only guarantees that each call is bounded and leaves a consistent manifest.
- Status gains
  `index: { covered, uncovered, unreadable, segments, bytes, last_follow, last_merge }`
  beside the catalog census, in S1b M5b's typed status JSON.
- A one-shot `ferret index` (no daemon) runs `follow` to completion after its
  catalog commit, under the same budget rules as a bulk build.

Nothing in the seam knows about inotify, debouncing or queue priority. S5
decides those.

The file-inode count in the inverse row is the fixture's 9.96M inodes less its

The `DocId → [InoId]` inverse is the one new resident cost of note. D30 C
already chose to build it "lazily, when a query first needs it". So the first
content query that drives from the content side builds it, and it is cached per
epoch. If M4 shows the memory matters, it can be halved by storing the first
inode per document plus a sparse table for duplicates.

### M1 — Tokenizer and content census

- `ferret-text`: the allocation-free `tokenize`, the 64-byte cap, and `Token`
  with run ranges. The old implementation is kept as the test oracle.
- Tests: the oracle property test and invariants (§ Tokenizer, Tests), and the
  private golden corpus of about 2,000 documents.
- `ferret-bench census <catalog-dir>`: documents, and content bytes of `Hashed`
  inodes in total and per extension, deduplicated by DocId, with a size
  histogram. Run on `$HOME` and on the 10M fixture.
- `ferret-bench tokenize <corpus>`: MB/s for old and new; occurrences, parts,
  distinct terms, hapax share and hash-like-token share per content byte.
- **Measure:** content bytes on the real tree, which picks the cost model's row;
  tokenizer throughput; and inputs a, b, c and f of the estimate.

**Measured** (2026-10-07). `ac2feed` was run on a fresh isolated catalog of
`$HOME`, built with ignore rules on. The index took 43.7 s and covered
469,734 names and 10.7 GiB read.

- **Census.** 113,010 `Hashed` documents hold **4.03 GB** of text. That figure
  is the row the cost model should use for this tree.
  - By extension:
    - `jsonl` 1.19 GB (30%), from 1,993 files;
    - no extension 0.90 GB;
    - `js` 0.65 GB;
    - `json` 0.32 GB;
    - `rs` 0.22 GB.
  - 53% of bytes sit in files of 1 MiB or more, while the median document is
    1 to 2 KiB.
- **Sample.** `corpus-sample` picked 1,957 files (36.75 MB) by BLAKE3 and
  skipped 20 over 1 MiB. The sample is kept privately in the session
  scratchpad, not in a repository. The golden-token corpus is deferred: the
  oracle property test already pins byte-identity with today's tokenizer.
- **Throughput.** On the sample, best of five, repeated three times:
  - all files: 164–166 MB/s;
  - ASCII files: 185 MB/s;
  - non-ASCII files: 146 MB/s.

  That misses the 300 MB/s target. It doesn't matter for build time, though:
  tokenizing 4.03 GB costs about 24 core-seconds, while reading it under the
  32 MiB/s pacer takes about 120 s. No tuning is planned.
- **Inputs** (assumption → measured):
  - a: 6.5 → **8.09** B per whole run;
  - b: 0.18 → **0.136**;
  - c: 1.5 → **1.73**;
  - f: 1.26e-3 → **1.19e-2** distinct terms per byte, on the sample;
  - hapax share: 72%;
  - hash-like share: 7.3% of distinct terms, 0.5% of occurrences;
  - terms over 64 bytes: 2.1% of distinct terms, 0.13% of occurrences.

```text
postings per content byte = (1/8.09) × 0.136 × 1.73  = 0.0291   (was 0.0415)
doc-id bytes              = 0.0291 × 9.61 / 8        = 0.035 B/B
dictionary at the sample's f = 1.19e-2 × 10.5 × 1.3  = 0.162 B/B
```

At the sample's scale, the **dictionary would be about 82% of the index**,
far beyond the quarter that § Term dictionary sets as the FST trigger. That f
overstates the full tree, because distinct terms grow sublinearly with text
(Heaps). As an illustration only, with β = 0.6, scaling the sample up 110× to
4.03 GB gives f ≈ 1.8e-3 and a dictionary of about 0.025 B/B, which is 41% of
a 0.060 B/B index and still past the trigger.

So **M2 must count distinct terms over the whole tree** before it fixes the
dictionary format. The count streams the 4.03 GB through `tokenize` and a hash
set, roughly 10M terms in a few hundred MB.

Three things bear on dictionary size:

- the hapax share (72%);
- hash-like terms (7%);
- `jsonl`, which is 30% of the bytes and mostly agent transcripts that change
  constantly.

Excluding them is a policy question, and it can wait for the M2 number.
